# 数组理论基础

## 概述

数组（Array）是最基础的线性数据结构，说白了就是把一组相同类型的数据，放到一段连续的内存空间里，然后通过下标（索引）去访问里面的元素。你想啊，几乎所有更复杂的数据结构——栈、队列、哈希表的桶数组、堆的底层数组——都是直接或间接依赖数组来实现的，所以搞懂数组底层的这些特性，其实是后面学双指针、滑动窗口、二分查找这些技巧的基础前提。

## 内存特性

### 连续存储与随机访问

数组在内存里占的是一段**连续**的地址空间。假设数组的起始地址是 `base`，每个元素占 `size` 个字节，那第 `i` 个元素（下标从0开始）的地址就是：

```
address(i) = base + i * size
```

你看，这其实就是一个纯算术计算，根本不需要遍历，所以数组的随机访问——也就是按下标读写——时间复杂度是 **O(1)**。这也是数组相比链表最大的优势：链表要访问第 `i` 个节点，得从头节点开始一个一个跳过去，那就是 O(n) 了。

### 为什么增删元素是 O(n)

正因为数组的元素是连续存放的，所以你要在"中间插入"或者"中间删除"，就必须**搬移**其余的元素才能维持这个连续性：

- **插入**：想在下标 `i` 处插入一个新元素，得先把 `[i, n-1]` 这个范围内的所有元素依次往后挪一位，腾出空位，再把新元素写进去。最坏情况——插到最前面——就得搬 `n` 个元素，时间复杂度 O(n)。
- **删除**：在下标 `i` 处删除一个元素，得把 `[i+1, n-1]` 范围内的元素依次往前挪一位，覆盖掉被删除的位置。同样最坏情况也是 O(n)。

那什么时候才不用搬移呢？只有在数组**末尾**插入或删除，而且底层容量还够用的时候，才是 O(1)。这也是为什么很多"原地移除元素"类题目，都是用双指针把结果集中写到数组前部，而不是真的去做中间删除——说白了就是为了避开这个搬移的代价。

## 各语言数组实现对比

| 语言 | 底层实现 | 是否定长 | 扩容策略 |
|------|----------|----------|----------|
| C++ `array`/原生数组 | 栈上或静态连续内存 | 是 | 不支持扩容 |
| C++ `vector` | 堆上连续内存 + 容量管理 | 否（动态） | 容量不足时申请新内存（常见策略是 1.5x 或 2x），把旧元素整体拷贝过去，再释放旧内存 |
| Java `int[]`/`Object[]` | 堆上连续内存，长度写入对象头 | 是 | 不支持扩容；`ArrayList` 内部持有一个数组，扩容时创建约 1.5 倍大小的新数组并拷贝 |
| Python `list` | 底层是可变长度的指针数组（存储对象引用，不是值本身） | 否（动态） | CPython 采用"超额分配"策略，扩容时申请比当前需求略大的空间，均摊下来接近 O(1) 的追加操作 |
| Go `slice` | 一个包含指针（指向底层数组）、长度 `len`、容量 `cap` 的三元结构 | 否（动态） | `append` 超出 `cap` 时，运行时分配一个更大的底层数组（通常小容量时翻倍，大容量时增长约 1.25 倍），把旧数据拷贝过去，`slice` 的指针指向新数组 |

关于 `vector` / `slice` 扩容，有个关键点得说一下：**扩容本身是均摊 O(1) 的**。你想，虽然某一次扩容需要 O(n) 的拷贝代价，但因为每次扩容之后容量都是成倍增长的，所以触发扩容这件事的频率会随着元素数量增加而指数级降低，均摊到每一次插入操作上，代价其实就是常数级别的。这也就解释了为什么"频繁往动态数组尾部添加元素"整体是高效的，而"频繁在数组头部或中间插入"依然很低效——毕竟每次都要搬移，扩容这个优化对这个问题根本帮不上忙。

Go 的 `slice` 这里有个容易踩的坑：多个 `slice` 可能会共享同一个底层数组。对某个 `slice` 做 `append` 如果触发了扩容，它就会指向一个新的底层数组，其他仍然指向旧数组的 `slice` 不受影响；但要是没触发扩容（容量还够用），那这次 `append` 就会直接修改共享的底层数组，这时候就可能影响到其他持有同一个底层数组的 `slice`了，这一点面试的时候很容易被问到。

## 常见误区

1. **误以为数组下标访问也可能是 O(n)**：只要你知道下标，数组访问永远是 O(1)，跟数组长度没关系。真正是 O(n) 的，是"查找某个值在数组中的位置"（也就是未排序数组的线性查找），别把这两个搞混了。
2. **误以为 Python 的 `list` 和 C++ 的原生数组是一回事**：`list` 其实更接近 `vector`，是个动态数组；C++ 的裸数组和 Java 的数组才是真正定长、不能扩容的数组，容量需求一旦变化，就必须用 `vector`/`ArrayList` 这类封装类型了。
3. **误以为"删除元素"一定要真的去搬内存**：在算法题里，"移除元素"往往只需要用双指针把有效元素**原地覆盖**到数组前部，再返回一个新长度就行了，根本不需要用语言提供的 `erase`/`remove` 这种真正做内存搬移的接口。这样一来，每个元素的搬移次数就能控制在 O(1) 均摊，整体做到 O(n) 而不是 O(n²)。
4. **误以为 Go 的 `slice` 就是数组**：`slice` 说白了只是对底层数组的一个"窗口"描述——指针加长度加容量，它本身不存数据。你要是理解了这一点，就能解释清楚为什么修改一个 `slice` 的元素，有时候会莫名其妙影响到另一个看似完全不相关的 `slice`。
