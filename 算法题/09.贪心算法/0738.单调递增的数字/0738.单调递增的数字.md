
# 0738. 单调递增的数字

**题目描述**

给定一个非负整数 `N`，找出并返回小于或等于 `N` 的最大的整数，同时这个整数需要满足其各个位数上的数字是单调递增的。

（当且仅当每个相邻位数上的数字 `x` 和 `y` 满足 `x <= y` 时，我们称这个整数是单调递增的。）

```
示例 1：
输入: N = 10
输出: 9

示例 2：
输入: N = 1234
输出: 1234

示例 3：
输入: N = 332
输出: 299
```

## 思路

先明确一下"单调递增数字"的定义：从左到右看，每一位数字都不小于它前面的那一位。比如 1234 满足（1≤2≤3≤4），而 332 不满足，因为第二位的 3 大于第三位的 2（准确说是从左往右第二位到第三位发生了下降）。

题目要求找到小于等于 N 的最大的单调递增数，本质上是一个带约束的最大化问题：约束是"单调递增"且"不超过 N"，目标是"尽可能大"。这正是贪心算法的典型场景——在满足约束的前提下，让每一位数字尽可能取到能取的最大值。

**朴素的思路会怎么做？**

如果不用贪心，直接暴力从 N 开始往下枚举，每个数都检查是否单调递增，最先满足条件的就是答案。你想，这样做在最坏情况下效率很低（比如 N 本身个位数远小于十位数，需要枚举很多次才能找到答案），我们需要一个能直接构造出答案的方法，这就要用到贪心策略了。

**贪心的核心策略：从右往左扫描，发现"递减断点"就处理**

把 N 转成字符数组（或者说按位拆开），从右往左遍历每一位。设当前位是 `i`，前一位是 `i-1`。如果发现 `digits[i-1] > digits[i]`，也就是说前一位比后一位大，这就破坏了单调递增的性质，出现了一个"断点"。

这时贪心的处理方式是什么呢？把 `digits[i-1]` 减 1，然后把从 `i` 开始一直到最后一位，全部置为 9。

**为什么要把断点后面全部变成 9，而不是简单地调整一下就行？**

因为我们的目标是找"小于等于 N 的最大值"。你想啊，当我们把 `digits[i-1]` 减 1 之后，这一位比原来小了，那在满足"整体数值不超过 N"这个约束的前提下，后面的每一位我们都可以自由选择了——只要保证单调递增即可，因为前面已经比 N 小了，后面无论怎么取，只要不超过 9 位数字，整体一定还是小于 N 的。而单调递增数字里，后面的位数能取到的最大值就是 9（只要前一位不大于 9，这天然就满足）。所以贪心地把断点之后所有位都设为 9，就是在约束范围内让数值最大化的最优选择。

**为什么必须"从后往前"遍历，而不能"从前往后"？**

这是本题最容易出错、也最需要讲清楚的地方。假设我们尝试从前往后遍历并修改，会发生什么问题呢？

以 332 为例。从前往后看，第一位是 3，第二位是 3，两者相等，暂时没有问题，指针继续往后移动。到第三位，发现第二位的 3 大于第三位的 2，出现断点，于是我们把第二位减 1，变成 2，第三位及之后置为 9，得到 329。

但问题来了：现在检查一下 329 是不是单调递增——第一位是 3，第二位是 2，3 > 2，仍然不满足单调递增！也就是说，刚才那一次修改（把第二位从 3 减到 2）反而在第二位和第一位之间引入了一个新的断点。如果继续往后遍历（因为指针已经past了第二位，不会再回头检查），我们会直接得到一个错误的、并不单调递增的结果。

这就是"连锁反应"问题：从前往后修改时，对某一位做减 1 操作，可能导致这一位反而比它前面已经确定、不会再被访问的那一位更小，产生新的断点，而算法却已经把指针移过去了，不会再回溯检查前面的位，从而得到错误答案。要修正这个问题，从前往后遍历就必须引入"回退重新检查"的逻辑，实现会变得复杂，且每次回退还可能引发新一轮回退，最坏情况下退化成多次扫描。

而"从后往前"遍历则完全规避了这个问题。还是以 332 为例：

- 从右往左看，指针先在最后一位（下标2，值2）和倒数第二位（下标1，值3）之间比较：`digits[1]=3 > digits[2]=2`，出现断点。处理：把 `digits[1]` 减 1 变成 2，`digits[2]` 及之后置为 9。此时数字变成 329（下标0是3，下标1是2，下标2是9）。
- 指针继续往左移动，比较下标0（值3）和下标1（值2，刚被修改过）：`digits[0]=3 > digits[1]=2`，又出现断点！处理：把 `digits[0]` 减 1 变成 2，`digits[1]` 及之后全部置为 9。此时数字变成 299。
- 指针移动到最左端，遍历结束，最终结果是 299。

关键在于：从后往前走的时候，每次修改前一位（下标更小的位），这一位在接下来的遍历中**还会被再次作为"当前位的前一位"重新比较**（因为遍历方向就是往下标更小的方向走，下一步恰好就是比较这个刚被修改的位和它自己的前一位）。也就是说，从后往前遍历天然地把"修改可能引发的连锁反应"纳入了后续的比较范围，不需要额外的回退逻辑——因为遍历顺序和"需要重新检查"的顺序是一致的。而从前往后遍历,已经访问过的位不会再被自然地重新检查，"回退"和"遍历方向"是相反的，所以才需要额外处理。

**为什么这样贪心是全局最优的？**

因为每一次遇到断点时的处理（前一位减1，后面全部变9）都是在当前局部约束下能取到的最大值，且不会影响前面已经确定为"合法"的高位部分（因为只在断点处修改前一位，且这个修改只会让数字变小,不会不小心让数值超过 N）。而从后往前处理保证了每个断点在被处理之后，其影响会正确地传递到更高位，直到不再产生新断点为止。整个过程中数字只会变小（每次修改是减1），且每次都是必要的最小代价的调整，所以最终结果既满足单调递增，又是不超过原数 N 的最大值。

时间复杂度是 O(m)，其中 m 是数字 N 的位数，因为只需要从右到左扫描一次（加上最坏情况下可能连续触发的断点处理，但每一位最多被处理常数次）；空间复杂度是 O(m)，用于存储数字的每一位。

## 代码

### C++

```cpp
class Solution {
public:
    int monotoneIncreasingDigits(int N) {
        string s = to_string(N);              // 转成字符串方便按位处理
        int flagIdx = s.size();                // 记录从哪个下标开始需要置9，初始设为size（表示不需要置9）
        for (int i = s.size() - 1; i > 0; i--) { // 从右往左遍历，比较相邻两位
            if (s[i - 1] > s[i]) {              // 前一位比当前位大，出现断点
                s[i - 1]--;                      // 前一位减1，消除断点
                flagIdx = i;                     // 记录断点位置，之后统一处理
            }
        }
        for (int i = flagIdx; i < s.size(); i++) {
            s[i] = '9';                          // 断点之后全部置为9，让数值最大化
        }
        return stoi(s);
    }
};
```

```java
    }
```

```python
class Solution:
    def monotoneIncreasingDigits(self, N: int) -> int:
        s = list(str(N))            # 转成字符列表方便按位修改
        flag_idx = len(s)           # 记录从哪个下标开始需要置9，默认不处理
        for i in range(len(s) - 1, 0, -1):  # 从右往左遍历，比较相邻两位
            if s[i - 1] > s[i]:      # 前一位比当前位大，出现断点
                s[i - 1] = str(int(s[i - 1]) - 1)  # 前一位减1消除断点
                flag_idx = i         # 记录断点位置
        for i in range(flag_idx, len(s)):
            s[i] = '9'               # 断点之后全部置9，最大化数值
        return int(''.join(s))
```

```go
func monotoneIncreasingDigits(N int) int {
    s := []byte(strconv.Itoa(N)) // 转成字节切片方便按位修改
    flagIdx := len(s)             // 记录需要置9的起始下标，默认不处理

            s[i-1]-- // 前一位减1消除断点（字节运算，'3'-1='2'）
            flagIdx = i // 记录断点位置

    for i := flagIdx; i < len(s); i++ {
        s[i] = '9' // 断点之后全部置9
    }
    result, _ := strconv.Atoi(string(s))
    return result
}
```

## 总结

- 本题的核心是"从后往前扫描，遇到递减断点就把前一位减1、断点之后全部置9"的贪心策略，本质上是在满足单调递增和不超过原数的约束下，让每一位尽可能取最大值。
- 必须从后往前遍历的原因在于：修改前一位可能导致新的断点出现在更靠前的位置，而从后往前的遍历顺序恰好跟"需要重新检查"的方向一致，能自然地把连锁反应纳入后续比较，不需要额外回退逻辑；从前往后遍历则会跳过已修改位可能引发的新断点，得到错误结果。
- 用 332 → 329 → 299 这个例子可以清晰地看到连锁反应是怎么一步步向左传播、直到没有新断点产生为止的。
- 该题是贪心算法中"局部调整不会破坏全局最优性，且调整顺序至关重要"的典型例子，遍历方向的选择直接决定了算法的正确性。
