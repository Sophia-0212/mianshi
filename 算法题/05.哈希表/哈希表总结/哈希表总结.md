# 哈希表总结

**题目描述**

本篇不针对具体题目，而是对哈希表专题（0242、1002、0349、0202、0001、0454、0383、0015、0018）做一次系统性复盘，总结「什么场景用数组、什么场景用 set、什么场景用 map」的判断依据，以及「双指针法和哈希法在多数之和问题上的适用边界」。

## 思路

### 三种哈希载体的选择依据

把这一整个专题刷完你会发现，哈希表在这些题目里从来不是一个孤立的知识点，而是背后有一套很清晰的判断链条。做这类题的时候，你可以按下面这个顺序，自己问自己三个问题：

**第一步：你先看，值域是不是小而且连续的？**

如果 key 的取值范围是已知的、小的、连续的整数区间——最常见的就是 26 个小写字母，也可能是 ASCII 字符那 256 个值——这种情况下，优先考虑用**数组**去模拟哈希表。为什么呢？因为数组下标访问是 O(1)，而且完全不需要算哈希函数、也不用处理冲突，这个开销省下来了，所以它是三种载体里最快的一个。

这个专题里就有几个很典型的例子：
- 242 题字母异位词：用一个长度 26 的数组，去统计两个字符串的字符计数是不是完全一样。
- 1002 题查找常用字符：还是用长度 26 的数组，记录每个字符在所有字符串里的最小出现次数。
- 383 题赎金信：同样用长度 26 数组，统计并消耗 `magazine` 能提供的字符。

你会发现这三题有个共性：字符集是固定的、范围很小，而且题目关心的是「计数」，不是单纯的「有没有出现」。

**第二步：要是值域很大或者不确定呢？这时候你就要问，是不是只需要判断"存在"或者"去重"？**

当元素可能是任意整数——值域大、不连续，甚至可能是负数——这时候数组就不好用了。这时候要看题目是不是只需要判断某个值出没出现过，不需要额外记录别的关联信息。如果是这样，那就用 **set**。

本专题里的典型例子：
- 349 题两个数组的交集：这题只需要判断某个数是不是同时出现在两个数组里，用 set 求交集，顺便还天然去重了。
- 202 题快乐数：这题只需要判断某个中间计算结果之前是不是出现过，用来判断有没有环，不需要额外记录别的信息，所以用 set 就够了。

**第三步：如果你需要的是"键 到 值"的映射关系，那就得用 map**

当你需要记录一个值对应的额外信息——比如它的下标、或者出现次数——这种情况就必须用 **map** 了，因为 set 只能回答"存在不存在"这个问题，取不出对应的值来。

本专题里的典型例子：
- 1题两数之和：这题需要记录"数值对应的下标"，查到某个值存在之后，还得把它的下标取出来当答案。
- 454题四数相加II：这题需要记录"两两之和对应的出现次数"，因为不同的下标组合可能算出相同的和，得把这些组合数都累加起来才对。

用一句话总结一下这条判断链：**先看值域，小而且连续就用数组；值域大或者不确定的时候，就看是否需要关联值——不需要就用 set，需要就用 map。**

### 双指针法与哈希法在多数之和问题上的对比

哈希表专题的后半部分，也就是 15 题三数之和、18 题四数之和，反而放弃了哈希法，改用了「排序 + 双指针」。这是这个专题里最容易被忽视、但其实很重要的一个转折点，值得单独拿出来讲清楚。

**两数之和为什么用哈希法呢？**

你想啊，两数之和只要求返回**一组**满足条件的下标，不要求去重——题目已经保证答案是唯一的了。所以哈希法可以在一次遍历里，一边查询"这个配对值是不是已经存在了"，一边记录"值对应下标"，时间复杂度是 O(n)，这种"只找一组解、不涉及去重"的场景下，它就是最优解。

**那三数之和、四数之和为什么就放弃哈希法，改用双指针了呢？**

这两题要求返回的是**所有**满足条件、而且**不能重复**的组合，也就是三元组或四元组。这里的关键是，如果你还继续用哈希法——固定住若干个数之后去查表——问题就来了：

1. 哈希法找到的解，其实是基于下标的组合，但去重这件事要求的是基于"值"去重。这就导致同一组值，可能通过不同的下标组合被重复找到很多次，事后还得对结果本身再做一次去重，比如塞进 `set<vector<int>>` 里，或者排序后再比较，这一套逻辑绕来绕去，还要额外的开销。
2. 相比之下，先排序再用双指针就聪明多了。你可以利用「排序后相同的值必然挨在一起」这个性质，在遍历过程中**直接跳过**那些会产生重复结果的分支——比如三数之和里，一旦发现 `nums[i]==nums[i-1]`，直接 continue 就行。这样就从源头上避免了重复解的产生，根本不需要事后再处理。

**说白了，这条适用边界的本质是**：哈希法适合"只找一组解，不要求枚举所有解、不涉及去重"这种场景，比如两数之和；但一旦问题变成"要枚举所有解，而且要去重"，排序加双指针通常就比哈希法更优雅了，因为排序天然给去重提供了相邻比较的基础，而哈希表本身是无序的，这反而让去重变得麻烦。

反过来说，如果三数之和只要求"判断存在不存在"，不要求把所有解都返回，那哈希法依然是可行而且简洁的——固定一个数，剩下两个数用两数之和那套哈希思路去查找就行，因为这时候根本不涉及枚举所有解和去重的问题。所以说到底，选哪种方法，关键就看题目要的是"存在性判断/找一组解"，还是"枚举所有解且不能重复"。

## 总结

- 三种哈希载体的选择，说白了就是遵循一条清晰的判断链：值域小而且连续，就用数组，这是最快的；值域大或者不确定、又只需要判重或者求交并集，就用 set；需要键值映射关系——比如下标、计数这些——就用 map。
- 数组哈希的本质优势在于，它省去了哈希函数计算和冲突处理这两块开销，前提是你得能开辟出一个覆盖全部可能取值的固定大小数组才行。
- 两数之和为什么用哈希法？因为它只需要找一组解，不涉及去重。三数之和、四数之和为什么放弃哈希法改用排序加双指针？因为这两题需要枚举所有解而且要求去重，排序之后做相邻比较能从源头上避免重复，比哈希法先找到解再去重要优雅得多。
- 那到底该用哪种方法呢？你可以先问自己两个问题：值域大小是什么情况？是要找一组解，还是要枚举所有不重复的解？这两个问题的答案，基本就能帮你确定该往数组、set、map、还是双指针这几个方向去想了。
