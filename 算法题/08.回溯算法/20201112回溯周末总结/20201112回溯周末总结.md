# 20201112 回溯周末总结

本周学习了排列问题（0046 全排列、0047 全排列 II），本篇总结排列问题与之前学过的组合、子集问题在代码结构上的核心差异。

## 排列问题与组合/子集问题的核心差异

**是否需要 startIndex**：组合问题（0077/0216/0039/0040）和子集问题（0078/0090）都需要 `startIndex` 参数，用来保证每一层递归只能从"上一层选择位置之后"开始选，这是为了避免因为选择顺序不同产生的重复结果（因为组合/子集不强调顺序）。排列问题（0046/0047）恰恰相反——因为要枚举所有可能的顺序，每一层递归都必须从数组下标 0 开始遍历一遍，尝试把每个还没用过的元素放到当前位置，所以**排列问题不需要 `startIndex`**。

**是否需要 used 数组**：组合/子集问题用 `startIndex` 就足以避免同一个元素被重复选择了（因为下一层的起点严格大于当前层选择的位置，天然跳过了已选元素）。但排列问题不一样，因为每层都要从 0 开始遍历，没有 `startIndex` 帮忙跳过已选元素，所以必须额外维护一个 `used` 布尔数组，记录哪些下标的元素已经在当前路径中使用，for 循环遇到已使用的元素要跳过。这是排列问题独有的、组合/子集问题不需要的额外状态。

**结果收集的时机**：这一点组合和排列是相似的，都是在满足特定长度条件的"叶子节点"收集结果（组合问题是"选够 k 个数"，排列问题是"排列长度等于数组长度"），区别于子集问题"每个节点都收集"的方式。

## 一张表看清三类问题的代码特征

| 特征 | 组合问题（77/216/39/40） | 子集问题（78/90） | 排列问题（46/47） |
|---|---|---|---|
| 是否需要 startIndex | 需要 | 需要 | 不需要 |
| 是否需要 used 数组 | 不需要（39/40 靠 startIndex 或 i 控制） | 不需要 | 需要 |
| 结果收集时机 | 满足条件的叶子节点 | 每个节点（包括根节点） | 排列长度等于数组长度的叶子节点 |
| 树层去重判断条件 | `i > startIndex && nums[i]==nums[i-1]` | 同组合 | `i > 0 && nums[i]==nums[i-1] && !used[i-1]` |

## 为什么排列的去重条件更复杂

组合/子集问题的树层去重可以直接用下标位置（`i > startIndex`）判断"是否是本层的横向重复"，为什么呢？因为 `startIndex` 天然把"层"的边界固定下来了。但排列问题没有这个天然边界（每层都遍历全部下标 0 到 n-1），所以不能单靠下标判断层次关系，必须借助 `used` 数组的状态（`used[i-1]` 是否为 `true`）来间接推断"前一个相同的值，是刚被同层撤销的（要去重），还是挂在树枝祖先节点上的（不去重）"。这也是本周学习中最容易混淆、需要反复琢磨才能透彻理解的一点。

## 总结

- 排列问题不需要 `startIndex`，因为每层都要枚举所有未使用的元素以覆盖所有可能顺序，这是与组合/子集问题最根本的代码结构差异。
- 排列问题需要 `used` 数组来代替 `startIndex` 起到的"避免重复使用同一元素"的作用，这是排列问题特有的状态维护。
- 排列问题的去重判断比组合问题多了 `!used[i-1]` 这一层条件，本质是因为缺少 `startIndex` 天然的层次边界，只能借助 `used` 状态间接推断树层还是树枝关系。
- 通过对比三类问题在 `startIndex`、`used` 数组、结果收集时机、去重条件四个维度上的差异，可以在遇到新的回溯题目时快速判断它属于哪一类模型，进而套用对应的代码框架。
