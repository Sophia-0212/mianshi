# CRM 智能问答检索引擎：评测集相关

## Q1：你们评测集规模多大？你们是怎么做评测集的？

### 项目规模口径

| 项目 | 规模 |
| --- | ---: |
| 内部业务 Workspace | 18 个 |
| 注册用户 / 日活用户 | 1640 / 890 |
| RAG 日问答量 | 4,600 次 |
| 峰值 RAG QPS | 9 |
| 原始知识文档 | 126,400 篇 |
| 可检索 Chunk | 186 万个 |

### 完整回答

我们的知识库规模大约是 12.64 万篇原始文档、186 万个 Chunk，覆盖 18 个业务 Workspace，日均约 4,600 次 RAG 问答，峰值 9 QPS。

评测集不是一个单一的大文件，而是分层建设的。当前正式使用的核心 Golden Set 大约 300 条，主要作为每次上线前的发布门禁。从核心集中再抽取 80～120 条作为 PR 冒烟集，保证每次代码提交可以快速得到反馈。

除此之外，我们逐步建设 1,500 条完整回归集，主要在重大版本变更时运行；

针对安全方面，我们单独维护 300 条攻击与越权案例。



| 数据集 | 建议规模 | 运行时机 | 主要用途 |
| --- | ---: | --- | --- |
| PR 冒烟集 | 80～120 条 | 每次提交 | 快速发现明显回归 |
| 核心 Golden Set | 300～500 条 | 每次上线前 | 发布硬门禁 |
| 完整回归集 | 1,500～3,000 条 | 夜间、重大版本 | 业务长尾和细分场景 |
| 安全攻击集 | 300～800 条 | 安全相关发布、定期全量 | ACL、注入、隐私和越权 |

在评测集分类上，我们不是随机从文档里生成问题，而是按照系统的主要失败case进行分层。核心集覆盖八类案例：单事实、业务术语、多跳推理、多轮对话、时间版本、歧义与无答案、ACL 权限负例和 Prompt Injection。

我们评测集的来源主要有四类：

1. 脱敏后的线上员工问题。
2. 客服工单和用户负反馈。
3. 历史case
4. 同事和AI 一起想的 安全攻防案例。

AI 可以辅助生成候选问题、口语化改写和同义表达，但不能单独确定最终答案。

每条案例也不只是“问题加标准答案”。我们会人工标注租户、用户角色、提问时间、对话历史、预期动作、预期路由、相关证据、必须事实、禁止证据、禁止事实和风险等级。

例如销售询问折扣审批，我们不仅标注正确流程，还要标注当前角色是否有权查看、应该引用哪一个生效版本、必须回答哪些审批条件，以及内部底价等哪些内容绝对不能输出。

标注流程采用双人复核。RAG 评测人员先完成问题、动作、证据和事实标注，第二名标注者独立复核；业务结论有分歧时由他们的+1来决定。没有歧义、大家统一标注的案例才能进入正式数据集。



### 追问：12 万篇文档为什么只有约 300 条核心评测？

评测集规模不是按照文档数量一比一生成的。12.64 万篇文档的数据完整性，主要通过摄取测试检查解析、Chunk、ACL、版本、表格和下线状态；问答 Golden Set 覆盖的是业务意图和系统失败模式。

300 条核心集的目标是低成本、稳定地拦截发布回归，不是估计所有线上问题的真实正确率。真实长尾由 1,500～3,000 条完整回归集补充。因此我们同时建设快速稳定的核心门禁集和覆盖长尾的完整回归集。
