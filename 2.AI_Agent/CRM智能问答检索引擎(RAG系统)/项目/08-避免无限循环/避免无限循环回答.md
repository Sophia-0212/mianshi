你是如何兼顾模型的开销和模型决策效果的？


主要看下面四个指标：
- 剩余决策轮次；
- 剩余 Token；
- 剩余时间；
- 剩余检索和生成次数。

## 如何避免无限循环的

我的兜底是四层叠加。第一层是 `max_iterations`，设置 16 轮决策硬上限，防止 Agent 无限循环；第二层是 控制每一步的预算 和渐进收敛，单次请求累计 Token 上限为 10,560。系统根据剩余步数、Token、时间和动作次数动态切换 `explore`、`focus` 和 `finalize`：前期允许知识库和网页搜索，中期关闭新搜索，只处理已有证据，达到 80% 预算，也就是 8,448 Token 后，停止扩展检索，优先生成答案；第三层是 `(tool, input)` 指纹检测，连续三次重复调用就触发自救或终止；第四层是人工 escalation，自动兜底失败后推送百度内部如流，由真人接管。前面三层自动止损，最后一层人工接管，缺一不可。

我们项目里 `max_iterations` 设到16步、`step budget` 卡在10560 Token、80%预警阈值为8,448 Token、循环检测窗口设到3、escalation接的是百度内部通信工具如流，从上线到现在10个月没有过一次不可控超额的事故。


## 一、Agent 死循环的四种典型成因——先对号入座

**成因一：工具调用循环。** Agent 反复调用同一个工具，每次参数只做微调，但永远不收敛。最经典的场景是搜索 Agent——你让它“搜索 + 总结”，它一直在搜，永远不进入总结环节。每一次搜索它都觉得“我还缺一点信息”，所以再搜一次，结果越搜越乱，进入死循环。本质上是模型在每一步都“乐观地高估了下一次搜索的价值”。

**成因二：目标漂移。** Agent 在执行过程中把子目标当成了主目标，越走越远。让它写一段代码，它先写完，然后开始“优化错误处理”，优化完又觉得“可以再加点单元测试”，然后又觉得“测试覆盖率不够”……每一步看起来都“在前进”，但整个任务永远不交付。这是 Agent 把“局部最优”误当成“全局最优”。

**成因三：自我怀疑循环。** Agent 完成任务之后又反复 review 自己的输出，每次都觉得“还能更好”。典型的是写作 Agent，每写完一版都说“让我再改一版”，每一版的改动还都是同义替换。背后是 prompt 里“追求高质量”的指令过强，导致模型陷入“反复 polish”的无限循环。

**成因四：幻觉性进展。** Agent 觉得自己在推进，但实际上只是在换说法重复同一件事。调试 bug 时反复“分析 → 假设 → 验证”，但假设根本不变——只是把“可能是数据库连接问题”换成“可能是连接池配置问题”再换成“可能是 connection 超时设置问题”。模型在玩同义词游戏，但语义上等价。读它的 transcript 你以为这家伙在认真想，仔细看就发现它走了 8 步等于走了 1 步。
## 二、四层叠加防御——每一层防一种失败模式

很多人一谈兜底，第一反应是“加个 try/except”。这是最初级的想法。**生产级 Agent 的兜底是叠加防御——四层一起上，每一层防一种失败模式，任何一层兜不住下一层接住。**

### 第一层：`max_iterations`——硬上限

最简单也最有效。给 Agent 一个最大循环次数，到了强制停。代码 5 行：

```python
def run_agent(task, max_iterations=20):
    for step in range(max_iterations):
        action = agent.decide(task, history)
        if action.is_done:
            return action.result
        history.append(action.execute())
    raise AgentTimeoutError(f"超过 {max_iterations} 步未完成")
```

重点想清楚一件事：**`max_iterations` 不是为了让 Agent“做完”，是为了“止损”。** 一个 20 步还没收敛的任务，再跑 100 步大概率也收敛不了，与其继续烧 token，不如**立刻断电**让人工接手。这一层防的是**成因一（工具调用循环）和成因二（目标漂移）**。

LangGraph 把这个值叫 `recursion_limit`，配置在 `RunnableConfig` 里；超过会抛 `GraphRecursionError`。LangChain 早期的 `AgentExecutor` 就有 `max_iterations` 参数。这是行业共识的第一道兜底。

### 第二层：`step budget`——成本上限

`max_iterations` 是按“轮数”算，但每一轮的成本可能差很多——有些任务每一步调用大模型 1 万 token，有些只用 500 token。生产环境真正的硬约束往往是**钱**，不是轮数。所以第二层要按 token 或 API 调用次数做预算：

```text
budget = max_cost_usd / avg_cost_per_step
# 例：max_cost_usd = 2.0，avg_cost_per_step = 0.05 → budget = 40 步
```

更精细一点是**实时追踪累计花费**——每一步算一次 `total_cost`，超过阈值就停。这一层防的是“轮数没超但单步代价暴涨”的情况——比如某一轮 Agent 突然决定下载一个 50MB 的文件做向量化，单步成本翻 100 倍。两个一起设才完整。

### 第三层：循环检测——状态指纹

前两层是“撞墙才停”。第三层是**主动识别**——给 Agent 每一步的状态算 hash，连续 N 步 hash 相同就判定死循环，立刻停。

实现思路是把 `(tool_name, sha256(input))` 做指纹存到一个最近 N 步的滑动窗口里：

```python
window = collections.deque(maxlen=3)
for step in range(max_iterations):
    action = agent.decide(...)
    fingerprint = (action.tool, sha256(json.dumps(action.input, sort_keys=True)))
    if window.count(fingerprint) == 3:
        raise LoopDetectedError(f"连续 3 步重复: {fingerprint}")
    window.append(fingerprint)
```

这一层专门防**成因一（工具调用循环）**，也能部分防成因四（幻觉性进展），因为同义词游戏里 tool_name 通常不变、input 也几乎一样。

工程上有几个细节决定循环检测好不好用：第一，**窗口不能太短**，设 2 步就 break 会误伤“我先查这个再查那个再查回这个”的合理回溯；设 3-5 步是经验值。第二，**input 要做 normalize**——空格、引号、key 顺序差异都会让 hash 不一致，造成漏检；最佳实践是 `json.dumps(input, sort_keys=True)` 之后再 hash。第三，**break 之后不能简单返回失败**，要把“我检测到你在循环 `{tool}({input})`，可以换个策略吗？”这句话作为新一轮 observation 推回给模型，给它一次自救机会。如果新一轮还命中循环检测，再走 escalation。

### 第四层：人工 escalation——最后一道闸门

前三层兜不住的时候，**不是直接报错或重试，而是把当前状态打包推给人工**，附上完整的“我尝试了什么、卡在哪、需要你做什么决策”。生产级 Agent 必须有这一层，因为不能假设 Agent 能自己解决所有问题。

我们项目里这一层是接到百度内部如流 webhook，自动发一条消息：

> ⚠️ Agent 任务 #4729 已触发兜底  
> 已用 18 步 / 预算的 90%  
> 失败模式：循环检测  
> 最近 3 步：`search_docs(query="rag rerank") × 3`  
> [查看完整 transcript] [批准继续] [终止并退款]

这套从 `max_iterations` 到 `step budget` 到循环检测到人工 escalation 的叠加防御方案，是我们训练营 Agent 生产化部署那一周专门拉出来讲的内容。学员不只是听理论，而是真的拿一个会跑飞的 Agent 项目，从 0 实现四层兜底，max_iterations 给多少、step budget 怎么算、循环检测的 hash 函数选什么、escalation 通道接到哪，每一个决策都对应真实的踩坑。



| 状态 | 条件 | 处理 |
|---|---|---|
| 正常（探索阶段） | 消耗 < 80%，且任务有进展 | 继续执行 |
| 预警（收敛阶段） | 消耗达到 80%，即约 8,448 Token | 停止扩展检索，优先生成答案 |
| 升级 | 达到 10,560 Token 仍未完成，或发生严重异常 | 停止 Agent，发送如流通知 |
