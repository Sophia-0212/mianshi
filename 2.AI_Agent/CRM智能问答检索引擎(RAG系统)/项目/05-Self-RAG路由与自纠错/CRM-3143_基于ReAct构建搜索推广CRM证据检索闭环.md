## 请你说说路由和自救错机制
项目有两层路由。
>
> 第一层是问题路由：LLM 使用结构化输出，将问题分为三类：
>
> - CRM 问题：走 Milvus 向量检索；
> - 外部实时问题：走网络搜索；
> - 闲聊问题：直接生成。
>
> 第二层是检索结果路由：检索Top5后，使用 LLM 逐条判断文档是否相关，不相关的过滤掉。
>
> 如果文档全部不相关，系统会改写查询并重新检索；如果生成答案没有被证据支持，会重新生
> 成；如果答案不实用，则重新检索或进入证据 Agent。
>
> 达到重试次数、Token 或时间预算后，系统停止循环，返回澄清、拒答或降级结果，避免无限
> 重试。

一眼看流程：

  问题
   ↓
  外层路由
   ├─ CRM问题 → EvidenceLoop
   │              ├─ 搜索 / 读取
   │              ├─ 观察结果
   │              └─ 继续决策
   │                    ↓
   │                证据足够
   │                    ↓
   │              相关性过滤 → 生成 → 校验
   │
   ├─ Web问题 → Web搜索 → 生成
   └─ 闲聊    → 直接生成

  面试时只需记住五步：

  > 路由问题 → 收集证据 → 过滤证据 → 生成答案 → 校验答案。
  > EvidenceLoop 位于第二步，通过搜索、读取、观察和再决策实现 ReAct 闭环。

按项目离线评测结果，加入自纠错后，忠实度从 91% 提升到了 94%。不过它会增加模型调用和延迟，所以我会把质量收益与调用开销一起评估。

## 面试官问：为什么 ReAct 是现代 Agent 的底层逻辑？单靠 CoT 根本不够？

“LLM 是文本生成器，CoT 是思维增强，而 ReAct 才是把模型推向行动智能的关键一步。

企业需要的不是一个回答问题的 LLM，而是能完成任务、能纠错、能连续行动的 Agent。

所以 ReAct 是当下最重要的 Agent 底层范式。”


## 我的项目里是如何实现ReAct思想的
项目在 Graph 2 中通过 EvidenceLoop 实现 ReAct。模型每轮先根据当前问题和已有证据进行
决策，再执行一个动作，例如检索、读取证据、澄清或结束；工具结果回写 State，作为下一
轮决策依据。

流程是：

思考 → 选择工具 → 执行 → 观察结果 → 再决策

对 CRM 问题，Agent 可以先搜索，再读取候选证据；证据不足时继续检索，信息缺失时澄清，
证据充分后生成答案。

每轮都有动作、Token、时间和重试预算；达到上限后终止，避免无限循环。所有证据还会经过
权限、引用和答案校验。

**“你能解释一下 ReAct 框架吗？为什么现在主流 Agent 都采用 ReAct？”**

简单来说：

> “ReAct = Reason + Act，先思考再执行，上一步的思考决定下一步如何执行。”

 CoT 的局限 → Action 补足执行能力 → Observation 提供反馈 → ReAct 闭环支持纠错 → 为什么成为常见 Agent 范式。

- 为什么 CoT（思维链）不够？
- 为什么需要 Action、Observation？
- ReAct 完整闭环如何解决 Agent 的“行动稳定性问题”？
- 为什么 ReAct 是目前所有 AGI、Agent 框架的底层范式？

大模型底层逻辑是ReAct也是慢慢发展过来的，说到ReAct就不得不先说 CoT。CoT 能帮助模型分步骤分析问题，但想清楚怎么做，不等于真正做了，也不等于知道做得对不对。

以下搜索推广 CRM 示例沿用项目中的模拟业务语料，不代表百度真实内部制度。

 “例如查询广告主的投放准入条件，模型可以用CoT分析出‘先查开户要求，再核对合同生效条件，最后梳理上线流程’，但这些仍然是计划。要真正取得相关制度证据，就需要调用知识检索工具。”

## 为什么 CoT（思维链）不够？

### 1. LLM 最大的问题：只能“想”，不会“做”，更不会“纠错”

LLM 本质是“被动生成式”的。

它能写计划、能回答问题，但缺乏：

- **可执行能力（Execute）**
- **状态意识（Environment State）**
- **错误感知能力（Feedback Loop）**

例如：

> “帮我查一下，搜索推广广告主的账户审核通过、合同审批通过后，是不是就能投放？还需要满足哪些条件？”

纯 LLM 会出现：

- 输出一堆自然语言描述
- 和真正的 API 没有联动
- 甚至会“编造投放准入条件”，把合同审批通过误认为合同已经生效

你把这种能力接到企业系统里，十之八九会“幻觉狂飙”。

所以，LLM 必须从“语言模型”升级成“Agent 模型”，而这一步的关键就是 **ReAct 框架**。

### 2. CoT 只能“思考”，却无法让系统真正可靠运行

CoT 的核心问题：

- **只能生成“思维链”，无法执行真实动作**
- **没有环境反馈，思考永远不会修正**
- **只是一段文本，无法保证结构化输出**

举个例子：

> “回答广告主是否具备投放条件前，需要先查询开户、合同生效和首发上线规则。”

CoT 会写出类似：

```text
// 搜索推广 CRM 问答示例
Step 1：查询广告主开户后的投放准入要求
Step 2：核对合同审批通过与合同生效的区别
Step 3：结合首发上线 SOP，说明还需满足的条件
```

它会思考，但不执行，你也不知道它思考对不对。 这在企业里是无法落地的。


面试官很可能继续追问下面三个问题：

## 1. “已经有 Rerank，为什么还需要相关性判断？”

> Rerank 主要解决候选之间的排序问题。即使所有候选都不相关，它也可以排出前五名。后面的相关性判断承担的是过滤职责，允许
> 把这五条全部判为不相关，从而触发重新检索。不过这一层会增加调用开销，是否值得保留，需要通过消融评测验证。

## 2. “模型判断自己有没有幻觉，可靠吗？”

> 不能保证完全可靠。我们让检查节点基于生成时实际使用的证据判断，约束它只输出结构化结果，但模型仍可能误判。因此，这是
> 一层质量检查，不能当成正确性证明；还需要用人工标注和离线评测验证它能发现多少错误、会误拒多少正确答案。

## 3. “知识库查不到，就直接 Web 搜索吗？”

这里要区分当前实现与改进方案：

> 当前代码在没有相关文档、查询改写预算耗尽且 Web 搜索预算允许时，存在转外部搜索的分支。但对于内部 CRM 问题，外部信息
> 未必适用，因此这部分还需要增加外搜适用性判断。对内部制度、客户信息等问题，缺少证据时应提示补充信息或无法确认，不能
> 直接用外部资料替代。
