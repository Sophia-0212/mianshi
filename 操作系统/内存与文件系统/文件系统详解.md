# 文件系统详解：inode、软硬链接、日志文件系统、磁盘调度

## 文件系统职责

文件系统要负责的事：

1. **命名**：给文件一个人可读的名字
2. **组织**：维护目录树结构
3. **定位**：把"文件名 + 偏移量"翻译成磁盘上具体的数据块位置
4. **空间管理**：分配和回收磁盘块
5. **权限与元数据**：记录文件的所有者、权限、大小、时间戳等
6. **缓存与崩溃恢复**：Page Cache 加速读写，日志（journaling）保证崩溃后文件系统结构不损坏

值得注意：`tmpfs`（内存文件系统）、`procfs`（进程信息伪文件系统）、NFS（网络文件系统）都不是直接基于磁盘的，但都通过 **VFS（虚拟文件系统）** 这层抽象统一了接口。

## 文件、目录、inode、dentry 的关系

一个容易搞混的点：**文件名其实不存在 inode 里**。真实的关系是：

- **目录项（dentry / directory entry）**：记录"文件名 → inode 号"的映射，存在目录文件的数据块里
- **inode**：记录文件的元数据（权限、大小、时间戳）和数据块的位置信息，但**不包含文件名**
- **dentry（VFS 层的内存对象）**：VFS 用来缓存"路径 → inode"查找结果的内存结构，加速路径解析。查找一个不存在的路径也会被缓存下来（负 dentry），避免下次重复走一遍完整查找

常用命令：

```bash
ls -li app.log      # 查看 inode 号
stat app.log         # 查看详细元数据
df -i                # 查看 inode 使用情况
```

## open() 的大致流程

1. 从路径的第一段开始，逐段解析路径（先查 dentry 缓存，没命中再查磁盘上的目录结构）
2. 找到最终的 inode
3. 做权限检查
4. 内核内部创建一个"打开文件对象"
5. 在当前进程的文件描述符表里分配一个空闲的 fd，指向这个打开文件对象

有个细节要注意：`dup()` 和 `fork()` 出来的 fd，会**共享同一个打开文件对象**（包括读写偏移量）；但如果是两次分别调用 `open()` 打开同一个文件，会得到**两个独立的打开文件对象**，各自维护自己的偏移量。

## 文件在磁盘上的存储方式

三种典型的数据块组织方式：

1. **连续分配**：文件的数据块物理上连续存放，读取速度快，但容易产生外部碎片
2. **链式分配**：每个数据块里存下一个块的地址，灵活但随机访问性能差（想读文件中间某个位置，得从头顺着链表走）
3. **索引分配**：单独用一块（或多块）索引块记录所有数据块的地址，随机访问快，但索引本身有额外开销

实际的文件系统：ext2/ext3 用的是"直接块指针 + 间接块指针"的组合方式；ext4 改用了 **extent（区间）树**，用"起始块 + 长度"描述一段连续块，对大文件的连续存储效率更高。

## 硬链接 vs 软链接

| 对比项 | 硬链接（Hard Link） | 软链接（Symbolic Link） |
|---|---|---|
| 底层原理 | 指向**同一个 inode** | 是一个新文件，内容是**目标路径的字符串** |
| 是否新建 inode | 不新建 | 新建一个 inode |
| 源文件删除后 | 数据依然存在（inode 引用计数没归零） | 变成"悬空链接"，指向的目标不存在了 |
| 能否跨文件系统 | 不能 | 能 |
| 能否链接目录 | 普通用户不能 | 能 |

```bash
echo hello > a.txt
ln a.txt hard.txt      # 硬链接
ln -s a.txt soft.txt   # 软链接
ls -li a.txt hard.txt soft.txt
```

**硬链接为什么不能跨文件系统**：inode 号只在它所属的那个文件系统内部才有意义，换一个文件系统，同样的 inode 号可能指向完全不同的文件。软链接存的是路径字符串，是在访问时才动态解析的，所以可以跨文件系统。

## write() 之后数据真的落盘了吗

普通的 buffered `write()` 调用成功，通常只代表数据被写进了 **Page Cache**，变成了一个"脏页"（dirty page），**并不代表已经写到磁盘上**。

想要更强的持久化保证，需要：

- `fsync()` / `fdatasync()`：强制把脏页刷到磁盘
- `O_SYNC` / `O_DSYNC`：打开文件时就要求每次写都同步落盘

另外要注意：`write()` 可能发生"部分写"（没写完你要求的全部字节数），调用方要自己处理这种情况；如果要保证"创建新文件"或"重命名"这类操作真正持久化，往往还需要对**父目录**也做一次 `fsync()`。

## 日志文件系统（journaling）

日志文件系统解决的问题：某次操作要修改好几处元数据，如果中途断电/崩溃，可能出现"改了一半"的不一致状态。解法是先把要做的改动写进一份日志，确认日志写完整了再真正提交改动，崩溃后靠日志回放/回滚保证结构一致。

ext4 有三种日志模式：

| 模式 | 说明 |
|---|---|
| `data=writeback` | 只保证元数据有日志，不保证数据先于元数据写入磁盘 |
| `data=ordered`（默认） | 写元数据日志之前，先把对应的数据写进主文件系统 |
| `data=journal` | 数据和元数据都先写日志，写放大更明显，但一致性最强 |

要强调一点：日志保证的是**文件系统结构层面的一致性**，不等于应用层的数据持久化保证——应用如果要确保数据真的落盘，还是得自己调用 `fsync()`。

## 怎么提高文件系统性能

大致可以从这几个角度着手：

1. 尽量用**顺序 I/O**，减少随机寻址
2. 合理利用 **Page Cache**，减少直接绕过缓存的读写
3. 减少小文件数量和元数据操作的频率（小文件多，元数据开销占比就大）
4. 控制 `fsync()` 调用频率（太频繁会拖慢吞吐，太少又有丢数据风险）
5. 根据场景选择合适的文件系统和挂载参数（ext4 / XFS / Btrfs 各有取舍）
6. 硬件层面上 SSD/NVMe/RAID 也是重要因素

排查命令：

```bash
df -h          # 磁盘空间使用
df -i          # inode 使用情况
lsof +L1       # 找已删除但还被进程占用的文件
iostat -x 1    # 磁盘 I/O 状态
```

## 磁盘调度算法

机械磁盘时代，磁头移动是最耗时的操作，所以出现了一系列磁盘调度算法来决定"下一个该处理哪个 I/O 请求"：

1. **FCFS（先来先服务）**：按请求到达顺序处理，简单但不做任何优化
2. **SSTF（最短寻道时间优先）**：每次挑离当前磁头最近的请求处理，寻道时间短，但可能导致某些请求一直被"插队"（饥饿）
3. **SCAN（电梯算法）**：磁头像电梯一样朝一个方向扫过去，处理完这个方向上所有请求再掉头，公平性比 SSTF 好
4. **C-SCAN（循环扫描）**：只朝一个方向处理，到头后直接跳回起点，再重新开始扫描，避免中间位置的请求被过度优先
5. **LOOK**：SCAN 的变种，如果前方已经没有请求了，提前掉头，不用扫到物理边界
6. **C-LOOK**：C-SCAN 的变种，同理提前折返

![常见的磁盘调度算法](https://oss.javaguide.cn/github/javaguide/cs-basics/operating-system/disk-scheduling-algorithms.png)

举个例子：磁头当前在 50 号磁道，待处理请求是 82、170、43、140、24——FCFS、SSTF、SCAN/LOOK 处理这批请求的顺序和总寻道距离都不一样，这也是磁盘调度算法教学里的经典例子。

要注意的是：**SSD/NVMe 没有机械寻道这个概念**，上面这套模型并不直接适用。Linux 现在的 `blk-mq` 多队列框架和 I/O 调度器，会根据设备类型（机械盘/SSD）和内核版本采用不同的吞吐/公平性策略，不能简单套用机械磁盘时代的调度算法。
