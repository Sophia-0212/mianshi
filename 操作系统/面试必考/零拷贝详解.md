# 零拷贝详解：mmap、sendfile 与 splice

## 传统 read/write 到底拷了几次

服务端把磁盘文件发给客户端，最直接的写法：

```c
while ((n = read(file_fd, buf, BUF_SIZE)) > 0)
    write(socket_fd, buf, n);
```

数据要经过：磁盘 → 内核缓冲区 → 用户缓冲区 → socket 缓冲区 → 网卡，一路搬运。拆开看 `read` 和 `write` 各自的步骤，整个过程涉及：

- **4 次上下文切换**（用户态 ↔ 内核态来回切换）
- **4 次数据拷贝**，其中 2 次是 **DMA 拷贝**（磁盘↔内核缓冲区、内核缓冲区↔网卡），2 次是 **CPU 拷贝**（内核缓冲区↔用户缓冲区、用户缓冲区↔socket缓冲区）

![传统 read/write 的数据拷贝路径](https://oss.javaguide.cn/github/javaguide/cs-basics/operating-system/zero-copy-traditional-read-write.png)

这两次 CPU 拷贝其实是纯浪费——数据本身根本不需要被应用程序处理，只是"路过用户空间打了个转"，白白占用了 CPU 时间和带宽。

## 零拷贝的"零"，零的是哪个拷贝

一个常见误解是"零拷贝=一次拷贝都没有"，这是不对的。零拷贝真正的含义是：**让 CPU 不再参与数据在内存之间的搬运，从而减少 CPU 拷贝次数和用户态/内核态切换次数**。DMA 拷贝（硬件搬运，不占 CPU）依然可能存在。

## 四种技术路线

### 1. mmap + write

利用虚拟内存机制，让内核缓冲区和用户空间映射到同一块物理内存上，这样应用可以"直接看到"内核缓冲区的数据，省掉一次 CPU 拷贝（内核缓冲区→用户缓冲区这一步没了）。

代价：涉及缺页异常处理的开销；如果文件在映射期间被 `truncate` 缩小，之后访问越界部分会触发 `SIGBUS`。

### 2. sendfile

一次系统调用就完成"文件 → socket"的整个传输，数据全程留在内核态，不用来回用户态倒腾。

### 3. sendfile + SG-DMA（Scatter-Gather DMA）

结合网卡的 scatter-gather DMA 硬件能力，把"内核缓冲区 → socket 缓冲区"这一步也变成 DMA 搬运（只搬 fd + offset + length 这些描述信息，不搬真正的数据本体）。这种情况下：

- **2 次上下文切换**
- **2 次数据拷贝，且都是 DMA 拷贝**
- **payload 的 CPU 拷贝次数 = 0**

这是真正意义上的"零拷贝"。

### 4. splice

借助 Linux 管道（pipe）在两个 fd 之间传递数据页的引用，而不搬运真实数据。适用于 `sendfile` 覆盖不到的场景——比如 socket 到 socket 的转发。代价是需要两次系统调用（先从源 fd splice 到管道，再从管道 splice 到目标 fd）。

## 四种方式对比

![拷贝次数与模式切换对比](https://oss.javaguide.cn/github/javaguide/cs-basics/operating-system/zero-copy-four-ways-comparison.png)

| 方式 | payload 的 CPU 拷贝 | DMA 拷贝 | 上下文切换 |
|---|---|---|---|
| 传统 read + write | 2 | 2 | 4 |
| mmap + write | 1 | 2 | 通常 ≥2 |
| sendfile | 0 或 1（取决于是否有 SG-DMA） | 通常 2 | 2 |
| splice | 通常可避免 | 通常 2 | 4 |

## mmap、sendfile、splice 怎么选

一个简单的判断原则：

- 需要**修改数据内容**再发出去，用 `mmap`（因为你本来就得把数据读到用户空间处理）
- 只是把**文件原样转发到 socket**，不需要改内容，用 `sendfile`
- 需要在**更通用的两个 fd 之间转发**（比如 socket 到 socket），再考虑 `splice`

零拷贝并不是万能的：一旦数据真的需要被处理（TLS 加解密、压缩、内容过滤等），或者文件很小、访问模式是随机读，零拷贝带来的收益就会明显打折。

## Java 与实际应用

- **Java NIO 的 `MappedByteBuffer`** 对应 `mmap` 这条路线
- **`FileChannel.transferTo`** 接近 `sendfile` 路线，但具体是不是真的走系统调用层的零拷贝，取决于 JDK 版本、操作系统、以及目标 Channel 的类型
- **Kafka** 消费端走 `sendfile` 路线做日志转发，性能收益明显
- **RocketMQ** 的 CommitLog 采用 `mmap`，因为它需要更灵活地直接操作内存里的数据

要注意区分：Rust 生态里的 `zerocopy` crate（`google/zerocopy`）和操作系统层面讲的"零拷贝"是完全不同的概念——前者说的是"类型安全的内存转换"（避免序列化/反序列化时的多余拷贝），跟这里讲的内核数据搬运没有关系，面试时别搞混。
