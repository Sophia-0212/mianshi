# 中断、异常与系统调用

## 用户态和内核态

CPU 有不同的特权级别，操作系统用这个机制把执行环境分成两档：

- **用户态**：权限受限，普通程序跑在这里，不能直接操作硬件、修改页表等敏感资源
- **内核态**：权限完整，能做页表管理、中断处理、直接访问设备等特权操作

搞这层区分的原因：**安全和稳定性**。用户态程序出错崩溃，不会直接把整个系统带崩；敏感操作被限制在内核态，普通程序想干坏事也做不到。

## 从用户态切到内核态的三种方式

1. **系统调用（Trap）**：同步的，由应用程序主动发起（比如调用 `read()`、`send()`），是程序"主动申请"进入内核态
2. **硬件中断（Interrupt）**：异步的，由硬件设备触发（比如网卡收到数据、定时器到期），跟当前正在执行的指令没关系，是"外部事件"打断了 CPU
3. **同步异常（Exception）**：由当前正在执行的指令本身触发（比如除零、非法指令、缺页异常），是"CPU 执行过程中自己发现问题"

要理清一个容易混的点：中断、异常、系统调用这三者解释的是"怎么进入内核态"，而**信号（Signal）**是完全独立的一套软件层面的通知机制，不要把它们混在一起。

## 系统调用是什么

系统调用是内核对外提供的一个**受控接口**，用户程序想访问硬件资源或者做特权操作，只能通过这个接口"申请"，不能直接绕过去操作。常见分类：

- 设备管理
- 文件管理
- 进程管理
- 内存管理
- 网络通信

### read() 系统调用的大致流程

1. 程序调用 glibc 提供的 `read()` 包装函数
2. glibc 把参数放进约定好的寄存器，触发一条特殊指令切换到内核态
3. 内核根据系统调用号找到对应的处理函数
4. 走 VFS（虚拟文件系统）→ 具体文件系统 / 设备驱动，完成真正的读取
5. 结果通过寄存器返回给用户态的调用方

有个细节要注意：**发生系统调用不一定意味着线程会被挂起切换**。只有当这次系统调用需要**阻塞等待**（比如等磁盘 I/O、等锁）时，才会触发调度器把 CPU 让给别的线程；如果数据已经现成（比如 Page Cache 里已经有），系统调用可以很快返回，根本不需要发生线程上下文切换。

## 中断的分类

- **可屏蔽中断**：可以通过设置 CPU 标志位暂时忽略（比如普通设备中断）
- **不可屏蔽中断（NMI）**：无法被屏蔽，通常用于硬件严重故障通知

中断处理通常也会分成两部分：**上半部（Top Half）** 快速响应、记录必要信息，**下半部（Bottom Half）**（比如软中断、tasklet、工作队列）延后处理耗时的部分，避免中断处理程序占用 CPU 太久影响系统响应性。

## 异常的分类

- **可恢复异常**：处理完还能回去继续执行原来的程序，比如缺页异常处理完后重新执行触发异常的那条指令
- **不可恢复异常**：程序本身出了严重问题，比如非法内存访问，通常会导致进程被终止（收到 `SIGSEGV` 之类的信号）

## 面试里怎么答

被问到"用户态和内核态怎么切换"，可以按这个逻辑组织：先讲清楚为什么要区分两种模式（安全、隔离），再讲三种切入内核态的具体触发方式（系统调用是主动的、中断是异步外部事件、异常是当前指令自己触发的），最后可以顺势讲一下系统调用的典型流程，以及"系统调用不等于一定线程切换"这个细节，体现对底层机制的理解深度。
