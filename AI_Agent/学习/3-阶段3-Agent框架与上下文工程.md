# 阶段3：Agent框架与上下文工程（LangChain/LangGraph/Context Engineering）（20-25天）— 工程落地必修

## 学习目标

- 理解LangChain解决的核心问题（把LLM调用、工具、记忆、提示词模板串成可复用链路），知道什么时候该用、什么时候纯手写更合适
- 掌握LangGraph的图/状态机思维：节点、边、状态传递、条件分支，理解它相比LangChain链式结构解决了什么问题
- 建立Context Engineering（上下文工程）意识：知道"喂给模型什么上下文"比"用什么模型"往往更决定最终效果
- 了解Harness Engineering（工程脚手架/运行时框架设计）的基本思路：Agent的执行循环、工具调用协议、错误恢复怎么设计
- 掌握上下文压缩的几种常见手段，理解为什么长对话/长任务必须做压缩，不能无限拼接历史

## 学习内容

- LangChain核心概念：Chain、Prompt Template、Memory、Tool、Retriever封装；何时用框架、何时该自己撵一个轻量实现
- LangGraph核心概念：图结构建模Agent工作流（节点=一步操作，边=流转条件）、状态（State）在节点间传递、条件边实现分支/循环
- LangChain vs LangGraph：链式（DAG，单向流程）vs 图式（可循环、可回退、更适合复杂多步Agent）
- Context Engineering：上下文窗口是稀缺资源；哪些信息该放进上下文（当前任务、必要工具结果、精简后的历史）、哪些不该放（无关历史、重复信息、可以按需检索的大段原文）
- Harness Engineering：Agent的执行循环（观察-思考-行动-观察，即ReAct的落地）、工具调用的输入输出协议设计、失败重试与降级策略、如何限制Agent的行动边界（安全护栏）
- 上下文压缩：摘要压缩（把历史对话/长文档压缩成摘要再放入上下文）、滑动窗口（只保留最近N轮，配合摘要兜底更早的内容）、关键信息抽取（只保留结论性/决策性内容，丢弃过程性废话）、分层记忆（短期上下文 + 长期记忆库，按需检索长期记忆而不是全塞进上下文）

## 阶段末自测

给一个需要多步骤、多工具调用、且对话轮次较长（10轮以上）的任务场景，你能说清楚：这个场景该用LangChain还是LangGraph实现更合适、为什么；如果对话历史超出上下文窗口限制，你会用哪种压缩策略、为什么选它而不是别的。

## 知识点详解（STAR法则）

### 1. LangChain核心概念：Chain、Prompt Template、Memory、Tool、Retriever

**S**：直接调用LLM API只是"发一句话、收一句话"，真实业务场景往往需要"套用模板生成提示词→调用模型→解析结果→决定下一步→可能再调用工具→再调用模型"这样一整条流程，如果每次都手写这些胶水代码，重复劳动多、容易出错，需要一套标准化的抽象来组织这条流程。

**T**：理解LangChain这几个核心抽象各自解决什么问题，以及它们怎么组合起来构成一条完整的应用逻辑。

**A**：
- **Prompt Template（提示词模板）**：把提示词里"固定部分"和"变化部分"分开——模板里留占位符（比如`{question}`、`{context}`），运行时填入具体值，避免每次手动拼接字符串，也方便统一管理和复用同一套提示词结构（跟阶段2讲的"系统提示 vs 用户消息"结构化思路是一致的，LangChain只是把这个思路工程化成了可复用的组件）。
- **Chain（链）**：把"prompt模板填充→调用模型→解析输出"这几步串成一个可以整体调用的单元，甚至可以把多个Chain串接（上一个Chain的输出是下一个Chain的输入），本质是把一段固定的处理流程封装成一个可复用、可组合的黑盒。
- **Memory（记忆）**：管理多轮对话的历史上下文——不用自己手写"把之前几轮对话拼进prompt"的逻辑，Memory组件按约定的策略（比如保留全部历史、只保留最近K轮、自动摘要旧历史）自动维护并注入历史上下文，这跟本阶段后面讲的"上下文压缩"是直接相关的实践载体。
- **Tool（工具）**：把外部能力（查数据库、调API、跑计算、搜索引擎）包装成一个模型可以"调用"的标准接口——本质就是阶段4会讲的Function Calling机制的应用层封装，让模型知道"有哪些工具可用、每个工具需要什么参数、返回什么格式"。
- **Retriever（检索器）**：对接向量数据库等检索源的标准接口，是阶段3（RAG，编号已调整为阶段4）里"召回"这一步的工程化封装，可以直接插入到Chain里，组成"检索增强生成"的完整链路。
- **何时用框架 vs 自己写**：简单场景（比如单轮调用+格式解析）用框架反而增加理解成本和依赖负担，直接手写HTTP调用+简单解析更清爽；场景涉及多个组件组合（记忆+工具+检索都要用上）、且需要快速原型验证时，用框架能省掉大量胶水代码和边界情况处理，工程团队协作时也有统一的组件抽象方便交接。

**R**：能解释LangChain五个核心组件各自解决的问题（模板复用、流程封装、历史管理、外部能力接入、检索接入），以及"什么时候该用框架、什么时候手写更合适"的判断依据（组件组合复杂度 vs 理解和依赖成本）。

### 2. LangGraph核心概念：图结构建模、状态传递、条件分支

**S**：LangChain的Chain本质是链式（DAG，有向无环图，单向往前走）的，但真实的Agent任务经常需要"走一步看结果，可能要退回去重试，也可能要根据结果走不同分支，甚至要循环执行直到满足某个条件"——这种带循环、带条件分支的复杂流程，用单向链式结构很难自然表达，需要一种新的建模方式。

**T**：理解LangGraph用"图"来建模Agent工作流的核心思路，以及状态（State）、节点（Node）、边（Edge）分别承担什么角色。

**A**：
- **为什么是图而不是链**：图（Graph）天然支持循环（一个节点可以再走回之前的节点）、支持条件分支（根据当前状态决定下一步走哪个节点），而链式结构本质上要求"从头到尾单向走一遍"，遇到"Agent需要反复尝试直到成功"或"根据中间结果选择不同后续步骤"这类场景，图的表达能力明显更贴合实际需求。
- **节点（Node）**：图里的每个节点代表一步具体操作——可以是"调用一次LLM"、"执行一个工具调用"、"做一次数据校验"，每个节点接收当前状态、做完自己的事、产出新的状态。
- **状态（State）**：贯穿整个图执行过程、在节点之间传递的数据结构——可以理解成一个不断被各节点读取和更新的"共享数据包"（比如包含对话历史、当前任务进度、工具调用结果等），每经过一个节点，状态可能被更新，再传给下一个节点。这跟普通函数调用"入参→处理→返回值"的模式类似，但图执行的是"状态在多个节点间流转"而不是简单的一次性函数调用。
- **边（Edge）与条件边**：普通边规定"节点A执行完，固定走到节点B"；条件边则是"节点A执行完，根据当前状态的某个字段/某个判断逻辑，决定走到节点B还是节点C"——这就是分支逻辑的落地方式。循环则是"某个条件边的目标节点，指向了图中更早的一个节点"，形成可以反复执行直到条件满足才跳出的循环结构。
- **典型应用场景**：一个Agent需要"调用工具→检查结果是否满足要求→不满足就调整参数重新调用→满足了才继续下一步"，这种"尝试-检查-可能重试"的模式，用LangGraph的条件边+循环结构可以很自然地表达，而这在纯链式结构里需要额外写很多外层控制逻辑才能模拟。

**R**：能解释"为什么LangGraph用图而不是链"（图天然支持循环和条件分支，更贴合Agent"走一步看情况再决定下一步"的实际执行模式），以及节点/状态/边三个概念各自的角色（节点=一步操作，状态=在节点间流转的共享数据，边=流转规则，条件边支持分支和循环）。

### 3. LangChain vs LangGraph：链式 vs 图式的选择

**S**：两个框架经常被放在一起讨论甚至混淆，面试官常问"这两个到底什么区别、什么时候该用哪个"，需要有清晰、可落地的判断标准，而不是笼统地说"LangGraph更强大"。

**T**：理解两者在设计哲学上的根本差异，以及具体场景下该怎么选。

**A**：
- **核心区别**：LangChain的Chain是单向流程（DAG），适合"流程明确、步骤固定、不需要根据中间结果走不同路径"的场景；LangGraph是图结构，适合"流程需要根据中间状态动态决策下一步、可能需要循环重试"的场景——本质区别不是"谁更新更强"，而是"你的任务流程本身是不是单向确定的"。
- **该用LangChain的场景**：固定的"检索→拼接prompt→生成答案"RAG流程、固定的"输入校验→格式化→调用模型→解析输出"处理流水线——这些流程步骤和顺序是确定的，不需要中途根据结果改变走向，链式结构足够表达且更简单直接。
- **该用LangGraph的场景**：需要多轮"思考-行动-观察"循环直到任务完成的复杂Agent（比如需要反复调用工具、检查结果、决定是否需要换一种方式重试）、需要根据中间结果走不同分支逻辑的多路径任务（比如"先判断用户意图属于哪一类，再走向完全不同的处理子流程"）、需要人工介入检查再继续的流程（图结构可以在某个节点暂停等待外部输入再继续）。
- **不是互斥关系**：实践中LangGraph的节点内部经常直接复用LangChain已有的Chain/Tool封装——图负责编排"复杂的控制流"，链/组件负责"具体某一步怎么执行"，两者是不同层次的抽象，可以组合使用而不是二选一。

**R**：能准确说出"链式适合流程确定的场景，图式适合需要动态决策/循环/分支的场景"这个判断标准，并能举例说明各自的典型适用场景，同时能指出两者并非互斥、常组合使用。

### 4. Context Engineering：上下文窗口是稀缺资源

**S**：很多人调优Agent效果时第一反应是"换个更强的模型"，但实践中经常发现，同一个模型，喂给它的上下文内容组织得好不好，对最终效果的影响甚至超过换模型——上下文窗口是有限且昂贵的资源（消耗token、影响延迟、影响模型注意力分配），怎么"喂"直接决定了效果上限。

**T**：建立"上下文工程"的意识，理解哪些信息该放进上下文、哪些不该放，以及为什么这个判断本身是一项核心工程能力。

**A**：
- **为什么上下文窗口是稀缺资源**：即使模型支持很长的上下文窗口（比如128K、200K token），实际使用中依然存在多重限制——token数直接影响调用成本和响应延迟；更关键的是，研究和实践都表明模型对超长上下文里"中间部分"信息的关注度会下降（常说的"lost in the middle"现象），塞得越多不代表模型真正"看懂"了越多，反而可能因为无关信息稀释了对关键信息的关注度。
- **该放进上下文的信息**：当前任务的明确目标和约束；为完成当前这一步真正必要的工具调用结果；经过压缩/摘要后的关键历史信息（而不是原始全量历史）；如果是RAG场景，是经过召回+重排后真正相关的文档片段（不是随便扔一堆检索结果）。
- **不该放进上下文的信息**：跟当前任务无关的历史对话内容；已经检索过一次、可以按需重新检索而不必一直占用上下文空间的大段原始文档；重复出现、没有新信息增量的内容（比如同样的系统说明反复出现在每一轮里，如果内容不变，应该只在必要时提供一次而不是每轮都完整重复）。
- **Context Engineering和Prompt Engineering的关系**：Prompt Engineering（阶段2）关注"这一次调用的提示词怎么写效果最好"，是相对静态、单次的优化；Context Engineering关注的是"整个任务执行过程中，动态地决定每一轮该往上下文里放什么、不放什么"，是贯穿多轮交互的、更系统性的工程决策，两者不冲突，是不同粒度的优化层面——Prompt Engineering解决"怎么问"，Context Engineering解决"该带着什么信息去问"。

**R**：能解释"为什么上下文窗口是稀缺资源而不是越长越好"（token成本、延迟、以及模型对长上下文中间部分关注度下降的现象），并能具体列举"该放/不该放进上下文"的判断标准，同时能区分Context Engineering和Prompt Engineering的关注层面差异。

### 5. Harness Engineering：Agent执行循环与工具调用协议设计

**S**：一个Agent能"跑起来"，背后需要一套运行时框架（Harness，脚手架）来支撑——包括怎么组织"模型输出决策→执行动作→观察结果→再决策"的循环、工具调用的输入输出怎么规范化、出错了怎么处理——这套脚手架设计得好不好，直接决定Agent在真实场景下是稳定可靠还是频繁失控/卡死/瞎跑。

**T**：理解Agent执行循环的基本结构、工具调用协议设计要考虑的要点，以及错误恢复和安全边界的设计思路。

**A**：
- **Agent执行循环的基本结构（ReAct落地）**：对应阶段4会讲的ReAct范式——模型先"思考"（生成一段推理，判断下一步该做什么）、再"行动"（调用某个工具或给出最终答案）、系统执行这个行动并把结果"观察"反馈给模型、模型基于新的观察继续下一轮思考，如此循环直到任务完成或达到终止条件（比如最大轮次限制）。Harness就是负责把这个"思考-行动-观察"循环真正跑起来的运行时代码——解析模型输出判断它想调用什么、执行对应的工具、把结果格式化后重新喂回模型。
- **工具调用协议设计**：需要明确定义每个工具的"名称、功能描述、输入参数格式、输出格式"，让模型能理解"什么时候该调用这个工具、需要传什么参数"（这部分具体机制在阶段4的Function Calling里详细展开）；同时协议要考虑清楚"工具执行失败时返回什么格式"，让模型能理解调用失败了、可以据此决定重试还是换个方式。
- **错误恢复与重试策略**：工具调用可能因为各种原因失败（网络问题、参数错误、外部服务限流）——Harness需要设计"失败后怎么办"的策略，比如自动重试几次、重试失败后把明确的错误信息喂回模型让它自己决定换个方式、或者达到重试上限后直接终止并给用户一个明确的失败反馈，而不是让Agent陷入死循环或者报错崩溃。
- **安全护栏（行动边界限制）**：Agent有自主决策和行动的能力，如果不加限制，可能执行超出预期范围的操作（比如错误调用了危险的工具、无限循环消耗资源）——Harness层面通常要设置最大执行步数/轮次上限、对高风险工具调用加人工确认环节、限制Agent能访问的工具范围（不是把所有工具都无差别开放给它），这些边界控制是Agent能安全落地到生产环境的前提条件。

**R**：能说清楚Agent执行循环的基本结构（思考-行动-观察循环，Harness负责真正跑起来这个循环），工具调用协议要包含的关键信息（名称/描述/输入输出格式/失败反馈格式），以及为什么需要错误恢复策略和安全护栏（避免死循环、避免执行超出预期的危险操作）。

### 6. 上下文压缩：摘要、滑动窗口、关键信息抽取、分层记忆

**S**：长对话、长任务执行过程中，历史信息会不断累积，如果无限制地把所有历史都拼进上下文，很快就会超出上下文窗口限制，或者即使没超限，也会因为信息过多而稀释模型对关键内容的关注度（跟上面Context Engineering讲的道理一致）——必须有系统性的压缩手段来控制上下文规模，同时尽量不丢失真正重要的信息。

**T**：掌握几种常见的上下文压缩策略，理解各自的原理、适用场景和代价（trade-off）。

**A**：
- **摘要压缩（Summarization）**：定期（比如每隔几轮，或者当历史长度接近阈值时）用模型把已有的对话历史或长文档压缩成一段更短的摘要，后续上下文里只保留这段摘要而不是原始全文/全部对话。优点是能大幅缩减token占用；代价是摘要过程本身可能丢失一些细节信息（尤其是摘要没有明确指出保留哪些关键点时），且每次摘要都需要额外一次模型调用（增加延迟和成本）。
- **滑动窗口（Sliding Window）**：只保留最近N轮对话的完整内容，更早的历史直接丢弃或者用摘要兜底（滑动窗口+摘要经常组合使用——最近的内容保留原文保证细节准确，更早的内容用摘要保留大致脉络）。优点是实现简单、能保证近期上下文的完整性；单纯丢弃更早内容（不配合摘要）的代价是，如果早期对话里有后续仍然需要用到的关键信息（比如用户在第一轮就设定的重要约束条件），会彻底丢失。
- **关键信息抽取**：不是简单地"压缩全部内容"，而是有针对性地从历史里提取"结论性、决策性"的内容（比如"用户最终选择了方案B"、"已确认的关键参数是X"），丢弃"过程性、探讨性"的废话（比如中间反复讨论、试错的过程）。这种方式信息密度更高，但需要更精细的判断逻辑（怎么识别哪些是真正的结论，哪些是可丢弃的过程内容），实现复杂度比单纯摘要或滑动窗口更高。
- **分层记忆（短期上下文 + 长期记忆库）**：把"当前正在处理的、需要保持在上下文里的内容"（短期记忆）和"曾经出现过但当前任务不一定用得到、需要时才检索出来的内容"（长期记忆，通常存进一个外部存储比如向量数据库）分开管理——日常对话只占用短期上下文的空间，一旦当前任务需要用到很久之前提到过的信息，再按需从长期记忆库里检索出来临时放入上下文（这个检索机制本质上跟阶段4的RAG召回思路是相通的）。这是最能兼顾"上下文精简"和"信息不丢失"的方案，但工程复杂度也最高，需要额外维护一套长期记忆的存储和检索系统。
- **怎么选择**：任务轮次不多、对早期细节要求不高的场景，滑动窗口足够简单有效；需要保留长期脉络但可以接受一定细节损失的场景，摘要压缩合适；对信息密度和准确性要求都很高、又需要控制上下文规模的场景，关键信息抽取更合适；需要支撑长期、跨会话的复杂任务（比如一个持续几周的项目型Agent），分层记忆是更彻底的解决方案，代价是工程复杂度显著增加。

**R**：能说出四种上下文压缩策略各自的原理（摘要=模型总结历史、滑动窗口=只留最近N轮、关键信息抽取=只留结论丢弃过程、分层记忆=短期上下文+按需检索的长期存储），以及各自的优缺点权衡（压缩比 vs 信息丢失风险 vs 实现复杂度），并能根据任务特点（轮次多少、对细节准确性的要求、是否需要跨会话记忆）判断该选哪种。
