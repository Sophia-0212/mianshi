# 技术选型 — 面试STAR问答集

单个技术点也用STAR讲：S/T是"这个技术要解决的问题场景"，A是"这个技术的做法+特点，刚好对上这个场景"，R是"用了它带来的效果"。

---

## 术语逐个讲解（STAR）

### dense（稠密向量）

**一句话定性**：一种把文本表示成"每一维都有数值、没有0"的固定长度浮点数数组，用于承载语义信息。

**S**：文本要给机器做语义相似度比较，但机器不懂"意思"，只能算数字。

**T**：需要把一段文字变成机器能算距离的东西，且要保留语义信息（"贵"和"价格高"要能算出"离得近"）。

**A**：用Embedding模型把文字映射成一个固定长度、每一维都有数值的向量（本项目512维），维度之间没有稀疏的0，全是稠密的浮点数——这就是dense向量。特点是"语义相近的文字，向量空间里距离也相近"。

**R**：能做语义检索，"客户嫌贵"能查到"价格异议"相关内容，字面完全不重叠也能匹配上。

### sparse（稀疏向量）

**一句话定性**：一种基于词频统计、绝大多数维度是0的向量表示，用于承载词汇重叠信息。

**S**：dense向量对专有名词、精确型号、系统术语不敏感（embedding会把这些"模糊化"），比如"ERP同步失败"这种固定术语，语义向量检索可能排不到前面。

**T**：需要一种能精确捕捉"这几个词有没有出现"的检索方式，弥补dense的短板。

**A**：用词频统计的方式表示文本——向量长度等于词表大小，绝大多数维度是0，只有出现过的词对应维度有值（非0值），这就是sparse（稀疏）向量。特点是"字面词汇重叠度高的排前面"，不管语义，只管词有没有出现、出现频率高不高。

**R**：能精确命中"ERP同步失败""审批流程"这类强关键词查询，补上dense检索的短板。

### Milvus

**一句话定性**：专为向量检索设计的开源分布式数据库。

**S**：项目要同时做dense检索、sparse检索、字段过滤（`category="content"`），如果用普通检索库自己拼这几个能力，得自己搭存储层+过滤逻辑+多套索引管理。

**T**：需要一个数据库级的解决方案，一站式管好向量存储、索引、过滤、混合检索融合。

**A**：Milvus是专门为向量检索设计的数据库，`documents/milvus_db.py`里用它建的collection原生支持一个表里同时挂dense字段和sparse字段，且sparse能靠内置BM25 Function自动从文本生成，不用额外搭分词服务。

**R**：一套数据库解决语义检索+关键词检索+字段过滤三件事，架构简化。

### Faiss

**一句话定性**：Meta开源的向量最近邻搜索算法库（不是数据库）。

**S**：需要选一个向量检索方案时，遇到"只做向量最近邻搜索"这个诉求。

**T**：如果诉求真的只是"给一堆向量算最近邻"，不需要数据库那些重量级能力。

**A**：Faiss是Meta开源的纯算法库，专注ANN（近似最近邻）搜索算法本身，没有持久化、没有Schema、没有过滤能力，是"库"不是"数据库"。

**R**（对本项目而言）：**没选**它，因为诉求不只是"查最近邻"，还要Schema管理+字段过滤+混合检索，Faiss这层能力它没有，得自己在外面搭，工程量更大，所以排除。

### Chroma

**一句话定性**：轻量级、上手快的开源向量数据库。

**S**：同样是选向量检索方案时的备选项。

**T**：需要轻量、好上手、适合中小规模场景的向量库。

**A**：Chroma是轻量级向量数据库，Python原生集成方便，上手快，是"够用型"方案。

**R**（对本项目而言）：**没选**它，因为它的生产级分布式能力、以及原生混合检索（dense+sparse）的完整度不如Milvus，本项目要混合检索这个硬需求，Chroma覆盖不够。

### collection

**一句话定性**：Milvus里组织数据的基本单位，类似关系数据库里的"表"。

**S**：Milvus里存数据总要有个"表"的概念来组织数据。

**T**：需要定义一批文档字段结构（有哪些列、每列什么类型）、并管理这批数据的索引。

**A**：collection是Milvus里的核心概念，类似关系数据库里的"表"——本项目`t_collection01`这个collection定义了`id`、`text`、`category`、`dense`、`sparse`等字段（`documents/milvus_db.py:22-33`），每次存文档、查文档都是对这个collection操作。

**R**：所有文档统一存进一个结构化管理的collection，字段类型、索引类型都在这一层定义清楚。

### Elasticsearch

**一句话定性**：以倒排索引+BM25为核心能力的老牌开源搜索引擎。

**S**：需要关键词检索能力时的常见备选方案。

**T**：想要成熟的搜索引擎能力（倒排索引、BM25打分）。

**A**：Elasticsearch是老牌搜索引擎，倒排索引+BM25是它原生的核心能力，向量检索是后来加的插件功能，不是它的主场。

**R**（对本项目而言）：**没选**它做主力方案，因为本项目要的是"一个库同时管dense+sparse"，Elasticsearch的向量能力是外挂的，不如Milvus原生这么完整，选它会导致"关键词检索用ES的主场能力、向量检索用它的弱项能力"这种不对等组合，所以最终统一用Milvus内置BM25 Function代替单独搭ES。

### BM25 Function

**一句话定性**：Milvus内置的、能从原文自动生成BM25稀疏向量的服务端能力。

**S**：项目要sparse向量，但如果手动实现"分词→统计词频→算BM25权重→生成向量"这套逻辑，得额外写代码或接一个独立服务。

**T**：需要一种"存文档时自动把文本转成BM25稀疏向量"的能力，不想自己维护这层逻辑。

**A**：BM25 Function是Milvus 2.4+的内置特性（`documents/milvus_db.py:35-56`），声明`input_field_names=["text"]`、`output_field_names=["sparse"]`后，写入`text`字段时数据库自动完成分词（本项目配了jieba中文分词）、算BM25权重、生成sparse向量这一整套流程，应用层完全不用手写。

**R**：把本来需要额外服务（比如Elasticsearch）才能做的事，收进数据库内部，代码里只管写`text`，`sparse`字段自动就有了。

### BGE Embedding

**一句话定性**：智源研究院开源的中文优化Embedding模型系列。

**S**：dense向量要靠某个具体模型算出来，模型选型影响中文语义理解效果和调用成本。

**T**：需要一个能把中文文本转成语义向量、且高频调用（每次入库/查询都要用）成本可控的模型。

**A**：BGE（BAAI General Embedding）是智源研究院开源的中文优化Embedding模型系列，本项目用`BAAI/bge-small-zh-v1.5`（`llm_models/embeddings_model.py:12-16`），本地CPU跑，输出512维dense向量。特点：中文语义编码效果优于通用英文模型，模型体积小、能在CPU上跑，不依赖GPU或外部API。

**R**：语义相近但字面不同的表达（"客户嫌贵"vs"价格异议"）能在dense向量空间里算出高相似度，且完全本地化，无网络依赖。

### BGE Embedding vs BM25 Function 对比表

俩都是给字段"填值"的生成器，但解决的问题、算的位置完全不同：

| | BGE Embedding | BM25 Function |
|---|---|---|
| 解决的问题 | 语义相似度（意思像不像） | 词汇重叠度（词一样不一样） |
| 底层原理 | 深度学习模型，把文本压缩成稠密向量 | 统计算法（词频×逆文档频率的改进版），生成稀疏向量 |
| 产出字段 | `dense`（FLOAT_VECTOR，512维，`documents/milvus_db.py:33`） | `sparse`（SPARSE_FLOAT_VECTOR，`documents/milvus_db.py:32`） |
| 计算发生在哪 | **客户端**（本地CPU跑模型，langchain-milvus调用时算好再传） | **服务端**（Milvus内部Function，写入`text`时自动算） |
| 需不需要额外托管/部署 | 需要（模型文件本地加载，占内存） | 不需要（数据库自带，声明即用） |
| 是否需要训练/预训练模型 | 是，用的是别人预训练好的BGE模型 | 否，BM25是纯规则算法，没有"模型"这个概念 |
| 擅长场景 | 语义化表达（"客户不想续约怎么办"） | 精确术语/型号（"ERP同步失败""审批流程"） |
| 不擅长场景 | 生僻专有名词、精确数字（会被模糊化） | 语义相近但字面不同的表达 |
| 本项目对应文件 | `llm_models/embeddings_model.py`（`bge_embedding`） | `documents/milvus_db.py:35-56`（`bm25_function`定义+索引配置） |
| 检索时的融合方式 | 两者产出的排序结果最终用RRF融合（见下方第3节） | 同左 |

**一句话记忆**：BGE管"懂不懂意思"，BM25 Function管"字对不对得上"——一个是模型算出来的语义向量，一个是数据库内置算法算出来的词频向量，两条完全独立的技术路线，靠RRF在检索时才汇合。

### dense/sparse写入路径的不对称性

两个字段各自靠不同东西填值，`documents/milvus_db.py:80-88`创建连接时能看出这个双通道设计：

```python
self.vector_store_saved = Milvus(
    embedding_function=bge_embedding,        # dense靠这个：客户端本地算
    builtin_function=BM25BuiltInFunction(),  # sparse靠这个：服务端自动算
    vector_field=['dense', 'sparse'],
    ...
)
```

| | dense | sparse |
|---|---|---|
| 计算发生在哪 | **客户端**（langchain-milvus本地跑BGE模型） | **服务端**（Milvus内部BM25 Function） |
| 靠什么 | `embedding_function=bge_embedding` | `builtin_function=BM25BuiltInFunction()` |
| Schema里的标记 | 没有`is_function_output` | `is_function_output=True`（`documents/milvus_db.py:32`） |
| 为啥这么分 | Embedding模型跑在哪由应用层决定（本项目选本地CPU跑） | BM25是纯统计算法，Milvus内置了，没必要客户端自己实现 |

`add_documents(datas)`调用时（`documents/milvus_db.py:92`），`langchain-milvus`客户端在发请求给Milvus之前，先在本地用`bge_embedding`把每条文档的`text`过一遍模型算出dense向量一起发过去；`sparse`则标记交给服务端Function处理，客户端只传原始`text`，不参与计算。两个字段"一个客户端算、一个服务端算"，是必然的不对称——底层机制本来就不对称，代码只是如实反映。

## 技术选型对比（组间对比 + STAR）

### 1. 向量数据库：Milvus vs Faiss vs Chroma vs Elasticsearch

**一句话定性**：四者都能存/查向量，但只有Milvus是"原生一站式管好dense+sparse+过滤"的专业向量数据库，其余三个各有能力缺口。

| | Faiss | Chroma | Elasticsearch | Milvus |
|---|---|---|---|---|
| 定位 | 检索算法库 | 轻量向量库 | 搜索引擎+向量插件 | 专业向量数据库 |
| 持久化/Schema | 无（需自建） | 有，较简单 | 有 | 有，完整 |
| 混合检索(dense+sparse) | 不支持，需外部拼接 | 不支持 | 支持，但BM25是主场、向量是外挂 | **原生支持，一个collection两种字段+RRF融合** |
| 多字段过滤 | 不支持 | 支持基础过滤 | 支持 | 支持，且可与向量检索同时进行 |
| 分布式/生产能力 | 无 | 弱 | 强 | 强 |

**S（背景）**：CRM场景用户提问既有语义化表达（"客户不想续约怎么办"），也有精确术语查询（"ERP同步失败""审批流程卡住"）。项目需要按`category`字段过滤检索结果（只查正文块，排除孤立标题块），也需要dense+sparse两路检索同时进行。

**T（任务）**：要在一个数据库里同时满足"语义检索+关键词检索+字段过滤"三个能力，且不想因为混合检索额外引入独立的分词/BM25服务（比如单独搭Elasticsearch）增加运维复杂度。

**A（行动）**：选Milvus。核心原因是它原生支持一个collection里同时挂`dense`（FLOAT_VECTOR）和`sparse`（SPARSE_FLOAT_VECTOR）两种向量字段，且`sparse`字段可以标记`is_function_output=True`，由内置的BM25 Function直接从`text`字段自动生成。Faiss因为没有Schema和过滤能力被排除；Chroma因为生产级分布式能力和混合检索的完整度不够被排除；Elasticsearch因为向量能力是外挂而非原生被排除。

**R（结果）**：一栈式方案代替"多组件拼接方案"，检索层代码只需要维护一个Milvus客户端，语义题和术语题都能精准命中（实测案例：检索"客户对价格有异议该怎么处理"精准命中价格异议FAQ段落）。

### 2. Embedding模型分层：本地BGE vs API大模型

**一句话定性**：同为BGE系列语义编码模型，一个跑在本地CPU（小模型，管高频调用），一个走远程API（大模型，管低频调用），按调用频次分层而非二选一。

代码位置：`llm_models/embeddings_model.py`

```python
openai_embedding = OpenAIEmbeddings(model="bge-large-zh", base_url="https://qianfan.baidubce.com/v2", ...)  # 千帆网关BGE大模型API，切块判断用
bge_embedding = HuggingFaceEmbeddings(model_name="BAAI/bge-small-zh-v1.5", model_kwargs={"device": "cpu"})  # 本地小模型，存储/检索用
```

| | API Embedding (bge-large-zh，千帆网关) | 本地Embedding (bge-small-zh-v1.5) |
|---|---|---|
| 效果 | 更强（large规模） | 略弱（small规模），中文语义已经足够 |
| 延迟 | 有网络往返 | 本地计算，无网络延迟 |
| 成本 | 按调用计费 | 一次性部署，无边际成本 |
| 可用性风险 | 依赖远程服务，服务不可用则功能瘫痪 | 本地跑，不受外部服务影响 |
| 调用频次适配 | 适合低频调用 | 适合高频调用 |

**S（背景）**：项目里有两个完全不同频次的Embedding调用场景——文档入库/查询时"每次都要调"的高频场景，分块阶段"偶尔判断两段内容语义是否该分开"的低频场景。

**T（任务）**：如果两个场景都用同一套模型，高频场景走外部API会带来延迟、成本、且有"Embedding服务挂了导致检索整体瘫痪"的单点风险；低频场景用本地小模型则在切块判断精度上打折扣（但切块判断容错空间大，不需要顶级精度）。

**A（行动）**：按调用频次分层选型——`bge_embedding`（本地小模型）用在每次文档入库和每次用户查询都要触发的Milvus存储/检索环节，消除网络延迟、调用成本、服务单点故障三个风险；`openai_embedding`（API大模型，走千帆网关）只用在`SemanticChunker`语义切块这个低频、一次性的判断场景，用更强模型换切分边界判断的准确度。

**R（结果）**：检索路径完全不依赖外部网络服务，即使Embedding API临时不可用，核心的"存文档、查文档"功能不受影响；BGE系列本身对中文场景优化过，比通用英文Embedding模型更适配CRM全中文文档场景。

### 3. 混合检索排序：RRF融合 vs 加权平均分数融合

**一句话定性**：两种把dense排序和sparse排序合并成一个最终排序的方法，一个直接加权原始分数，一个只用排名算倒数分数相加。

代码位置：`tools/retriever_tools.py:11-14`

```python
search_kwargs={"k": 4, "ranker_type": "rrf", "ranker_params": {"k": 100}, "filter": {"category": "content"}}
```

| | 加权平均分数融合 | RRF融合 |
|---|---|---|
| 输入 | 原始分数（dense是[-1,1]相似度，BM25是无固定上限的统计值） | 只用排名，不用原始分数 |
| 量纲问题 | 两种分数量纲完全不同，直接加权会失真 | 无量纲问题，排名是统一尺度 |
| 调参成本 | 需要手动调权重系数，且不同数据分布下最优权重不同 | 只有一个平滑常数k，鲁棒性更高 |
| 排序逻辑 | 谁的加权分数高谁靠前 | 只要在任意一路排名靠前就能获得高融合分 |

**S（背景）**：Milvus混合检索要融合dense（相似度分数，范围[-1,1]）和sparse（BM25分数，理论无上限的统计值）两路排序结果，这两种分数量纲完全不同，不能直接比较或加权平均。

**T（任务）**：需要一种融合方式既能避免手动调权重（不同query分布下最优权重会漂移），又能保证"任意一路检索里排名靠前的文档都不会被另一路的分数体系压制"。

**A（行动）**：采用RRF——只用两路各自的排名转成倒数排名分数相加，`ranker_params: {"k": 100}`里的k是平滑常数，避免排名第一和第二的分数差距过大导致另一路检索完全没有话语权。

**R（结果）**：语义题（"客户对价格有异议"）和术语题（"ERP同步失败"）都能各自在对应的检索方式里排名靠前从而被RRF放大，不需要为不同类型的query手动调权重系数。

### 4. LLM调用中的Temperature策略：0 vs 更高的值

**一句话定性**：控制LLM输出随机性的参数，0代表几乎确定性输出，越高越有创造性和多样性。

代码位置：`llm_models/all_llm.py:6-10`（当前实际配置：Ducc内部网关，模型`gpt-5.5`）

```python
llm = ChatOpenAI(temperature=0, model='gpt-5.5', api_key=OPENAI_API_KEY, base_url="https://oneapi-comate.baidu-int.com/v1")  # Ducc内部网关
```

| | Temperature=0 | Temperature>0 |
|---|---|---|
| 输出稳定性 | 高度确定，同输入同输出 | 有随机性，同输入可能不同输出 |
| 适用场景 | 分类判断（yes/no、路由选择） | 创造性生成、追求表达多样性 |
| 本项目用到的判断类调用 | `grade_documents`、`hallucination_grader_chain`、`answer_grader_chain`、`question_router_chain` | （本项目`generate`节点目前也复用了0，属于可优化但非最优的地方） |

**S（背景）**：`graph2`里有多个环节需要LLM做"分类判断"而非"自由生成"——文档相关性打分（yes/no）、幻觉检测（yes/no）、答案相关性评估（yes/no）、问题路由（web_search/vectorstore）。

**T（任务）**：这类判断类调用要的是"确定性分类结果"，如果同一份文档同一个问题在不同时刻判断出不同的yes/no，会导致整个LangGraph的执行路径不可预测，调试困难、线上行为不稳定。

**A（行动）**：所有判断类LLM调用统一复用`temperature=0`的同一个LLM实例，牺牲输出多样性换取分类结果的可复现性，让图的执行路径可预测、可调试。

**R（结果）**：文档相关性、幻觉检测、路由判断这些决定图走向的关键节点行为稳定。诚实指出一点可优化项：`generate`最终生成回答这一步理论上可以用更高的temperature换取表达多样性，本项目目前也复用了0，是"能用但非最优"的地方（面试如果被问到，直接说明这是已知可优化点）。

### 5. 图结构框架：LangGraph vs LangChain Chain

**一句话定性**：两者都是LangChain生态的流程编排工具，Chain是单向执行的DAG，LangGraph是支持循环和条件分支的状态图。

| | LangChain Chain | LangGraph |
|---|---|---|
| 执行方向 | 单向，从头到尾一遍 | 支持循环、条件分支、回边 |
| 状态管理 | 隐式，靠链式传参 | 显式State对象，所有节点共享同一份状态 |
| 适用场景 | 固定流程、无需重试的简单任务 | 需要"检索不相关就改写重试""生成有幻觉就重新生成"这类带反馈的控制流 |

**S（背景）**：RAG流程里存在"检索到的文档跟问题不相关，需要改写问题重新检索""生成内容被判定为幻觉，需要重新生成"这类失败后要绕回去重试的场景。

**T（任务）**：需要一种能表达"检索失败→改写问题→重新检索"这种带反馈环路的控制流，而不是从头到尾单向执行一遍就结束。

**A（行动）**：用LangGraph搭建`graph1`和`graph2`两条Pipeline，用`StateGraph`定义节点和条件边，把`rewrite→agent`（graph1）、`transform_query→retrieve`（graph2）、`"not supported"→generate`（graph2）这几条回边显式建模成图结构里的边，配合`GraphState`（如`transform_count`）传递决策所需的中间状态。

**R（结果）**：`graph2`落地了完整的Self-RAG自纠错思路（路由判断+文档相关性打分+生成质量双重校验+查询转换收敛），这种带循环的多轮自我修正流程如果用Chain实现，得手写外层while循环+手动维护状态字典，代码会远比LangGraph的声明式图结构混乱。

### 6. 日志库：Loguru vs 标准库logging

**一句话定性**：两者都是Python日志库，标准库`logging`需要手动配置Handler，Loguru是开箱即用、默认配置已经好用的第三方库。

代码位置：`utils/log_utils.py`

```python
from loguru import logger
self.logger = logger
self.logger.remove()  # 清空默认配置
self.logger.add(sys.stdout, level='DEBUG', format="...")  # 自定义格式后统一复用
```

**S（背景）**：项目有多个模块（`agent`、`graph`、`graph2`、`documents`等）都需要打日志，且`write_milvus.py`里还有多进程场景（`multiprocessing.Process`），日志格式最好能带上进程名/线程名方便区分是哪个进程输出的。

**T（任务）**：需要一个全局共用、配置简单、且能清晰标出模块名/函数名/行号/进程名的日志方案，减少每个模块重复配置Handler的成本。

**A（行动）**：选Loguru，在`utils/log_utils.py`里封装成一个全局单例`log`，格式里带上`{process.name}`、`{thread.name}`、`{module}.{function}:{line}`，所有模块统一`from utils.log_utils import log`导入复用，不需要每个模块自己`getLogger(__name__)`再配置。

**R（结果）**：多进程环境下（`write_milvus.py`的双进程流水线）能通过日志直接看出是解析进程还是写入进程在输出，且格式统一、彩色区分等级，调试效率优于手动配置标准库logging。
