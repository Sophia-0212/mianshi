# 检索工具封装 & 多轮对话历史管理

简历原文：
> 封装检索工具供Agent调用，实现基于会话维度的多轮对话历史管理，支撑销售/客服连续追问场景。

对应代码：`tools/retriever_tools.py`（工具封装）+ `agent/rag_agent.py`（历史管理，用的`RunnableWithMessageHistory`）+ `graph/graph1.py`（`MemorySaver`+`thread_id`，LangGraph原生持久化）

⚠️ 项目里实际有**两种历史管理机制**同时存在：`agent/rag_agent.py`用的是LangChain传统的`RunnableWithMessageHistory`+`session_id`；`graph/graph1.py`用的是LangGraph原生的`MemorySaver`checkpointer+`thread_id`。这是面试官如果深挖会发现的关键点，务必分清楚讲。

## 一、整体流程（30秒话术）

销售/客服在用智能助手时经常是连续追问的场景——比如先问"客户对价格有异议怎么处理"，接着追问"那如果客户还是不接受呢"，第二句话如果没有第一句的上下文，Agent根本不知道"客户"指的是什么场景。所以做了两块工作：一是把Milvus检索封装成一个标准LangChain工具（`retriever_tool`），让Agent能按需自主决定要不要调用检索、传什么查询参数；二是做了会话维度的历史管理，让同一个session/thread内的多轮对话共享上下文，Agent能看到之前问过什么、追问的时候能正确理解指代关系。

代码链路：`retriever_tools.py`里用`create_retriever_tool`把Milvus检索器包装成Agent可调用的tool，配置了`filter`、`k`、`ranker_type`等检索参数；历史管理在`rag_agent.py`里用`RunnableWithMessageHistory`包一层`AgentExecutor`，用一个进程内字典`store`按`session_id`存取`ChatMessageHistory`；`graph1.py`是另一条路线，用LangGraph自带的`MemorySaver`作为checkpointer，状态图本身按`thread_id`持久化整个消息列表。

## 三、标准答案

### Q2a：检索工具怎么封装的，Agent怎么决定调用

用LangChain的`create_retriever_tool`把Milvus的retriever包装成一个标准Tool对象，这个Tool有名字（`rag_retriever`）和描述文本，绑定给Agent之后（`llm.bind_tools([retriever_tool])`或者`create_tool_calling_agent`），Agent每次收到用户输入时，由LLM自己根据问题内容和工具描述文本，判断这个问题是否需要调用检索工具、需要的话生成什么查询参数传给工具——这是tool calling的标准机制，不是代码里写死的规则判断，完全由模型的推理能力决定要不要调用、怎么调用。

```python
mv = MilvusVectorSave()
mv.create_connection()
retriever = mv.vector_store_saved.as_retriever(
    search_type='similarity',
    search_kwargs={
        "k": 4,
        "score_threshold": 0.1,
        "ranker_type": "rrf",
        "ranker_params": {"k": 100},
        'filter': {"category": "content"}
    }
)

retriever_tool = create_retriever_tool(
    retriever,
    'rag_retriever',
    '搜索并返回关于 "CRM系统" 的信息, 内容涵盖：销售SOP流程、产品功能模块、系统操作与故障排查、客户异议处理话术等'
)
```

retriever底层走Milvus混合检索：dense（BGE embedding）+ sparse（BM25），`ranker_type: rrf`做召回融合排序，`k=4`取top4，`filter={"category":"content"}`做元数据过滤（排除标题类等非正文块）。**工具化的意义**：把检索能力做成可复用、可插拔的原子能力，Agent层不用关心Milvus细节，只需要拿到一个描述清晰的Tool，模型自己决定"这个问题要不要查知识库"。

### Q2b：工具描述怎么写的，为什么这么写

工具描述写的是"搜索并返回关于CRM系统的信息, 内容涵盖：销售SOP流程、产品功能模块、系统操作与故障排查、客户异议处理话术等"。这段描述本质上是给LLM看的"这个工具能干什么"的说明，LLM做工具选择决策时主要依据的就是这段文字和用户问题的匹配程度，所以描述写得越具体、越覆盖实际知识库包含的主题范围，Agent判断"要不要调用这个工具"的准确率就越高——如果描述写得太笼统（比如只写"搜索知识库"），Agent可能对一些边界问题（该查库但描述没提到）判断不准。

### Q2c：`filter={"category": "content"}`是干嘛的

这是检索时的过滤条件，只在Milvus里`category`字段等于`content`的记录里做检索。回看`markdown_parser.py`的合并逻辑，处理完的document里，标题+正文合并后的完整块会被标记成`category='content'`（合并逻辑里`parent_dict[parent_id].metadata['category'] = 'content'`），而单独的Title类型document本身category还是`'Title'`。这个过滤条件的作用是确保检索只返回"标题+完整正文"这种语义完整的内容块，避免检索到孤立的、没有正文内容的标题本身作为答案来源，防止检索结果质量下降。

（这一层`category`过滤是Milvus检索阶段的第一次过滤；graph2里还有第二次LLM语义过滤，详见《1.两条Agentic工作流.md》第6节"两阶段过滤"，两者不是同一件事。）

### Q2d：不需要检索直接回答，谁在判断

这也是tool calling机制内置的能力——LLM在推理阶段本身就有权决定"这次要不要调用工具"，如果LLM判断当前问题不需要查知识库（比如纯闲聊或者常识问题），可以直接不触发工具调用、直接生成文本回复。在graph1里对应`tools_condition`这个LangGraph内置的条件判断，检查LLM返回的消息里有没有工具调用请求，有则路由到`retrieve`节点，没有则直接走`END`，这一层路由判断也是基于LLM自身的输出内容做的，不是额外写的规则。

### Q3a：会话维度历史管理怎么实现的，用什么做key

**两套实现方式并存**，key都是显式传入的字符串标识：

- `rag_agent.py`用的是LangChain的`RunnableWithMessageHistory`，`session_id`作为key，历史存在一个进程内字典`store = {}`里，`get_session_history(session_id)`按需创建或复用`ChatMessageHistory`对象。
- `graph1.py`用的是LangGraph原生的`MemorySaver`checkpointer，用`thread_id`作为key，整个`AgentState`（包括完整的消息列表）在每次调用后自动被checkpointer持久化，下次用同一个`thread_id`调用时会自动恢复之前的状态。

```python
# rag_agent.py
store = {}

def get_session_history(session_id: str) -> BaseChatMessageHistory:
    if session_id not in store:
        store[session_id] = ChatMessageHistory()
    return store[session_id]

agent_with_history = RunnableWithMessageHistory(
    executor,
    get_session_history,
    input_messages_key='input',
    history_messages_key='chat_history'
)

agent_with_history.invoke(
    {'input': '客户对价格有异议该怎么处理？'},
    config={'configurable': {"session_id": 'zs123'}}
)
```

本质上两者都是"用一个会话标识区分不同用户/不同对话，各自维护独立的消息历史"，只是实现层级不同——一个是手动管理`ChatMessageHistory`对象，一个是LangGraph状态图自带的checkpoint机制。

### Q3b：历史存在哪里，进程重启后还在吗

目前两套实现都是**存在内存里**，没有持久化到磁盘或数据库：`rag_agent.py`的`store`是一个普通Python字典，`graph1.py`的`MemorySaver`也是内存版checkpointer（LangGraph也提供`SqliteSaver`/`PostgresSaver`等持久化版本，但当前代码用的是内存版）。这意味着一旦进程重启，之前所有会话的历史记录都会丢失——这是当前实现的一个局限，如果要支持真正跨进程重启保留历史，需要换成持久化的checkpointer实现（比如接Redis或数据库）。

### Q3c：历史消息会不会无限增长，超出上下文窗口

会。当前两套实现都没有做历史截断或摘要压缩——`ChatMessageHistory`和`MemorySaver`都是简单地把每轮新消息追加进去（`add_messages`就是append语义），随着对话轮次增多，传给LLM的历史消息会越堆越长，理论上有超出模型上下文窗口的风险，也会增加每轮调用的token成本。这是当前实现的已知局限，如果要优化，常见做法是加窗口截断（只保留最近N轮）、或者对早期历史做摘要压缩后再拼接。

### Q3d：多用户会不会串会话

不会串——只要每个用户/每次对话分配的`session_id`/`thread_id`是唯一的（比如按用户ID或者每次新对话生成一个UUID），字典/checkpointer内部都是按这个key做隔离存取的，不同key之间数据互不干扰。`graph1.py`里就是用`str(uuid.uuid4())`每次启动生成一个新的`thread_id`。需要注意的是如果两个不同用户不小心用了同一个`session_id`（比如硬编码或者ID生成逻辑有bug），历史就会串——这是使用层面需要保证ID唯一性的前提条件，不是框架自动保证的。

### Q4a/Q4b：两套机制是同一套吗，为什么存在两套

**不是同一套**，是两条独立技术方案在两条不同pipeline（graph1和rag_agent.py那条更简单的纯agent链路）里各自实现的历史管理。存在两套的原因是这两个模块本身就是相互独立开发、没有共享代码的（对应项目里"两条graph各自独立实现、重复度高"的已知问题）——`rag_agent.py`是更早期/更基础的LangChain AgentExecutor方案，用的是LangChain通用的历史管理组件；graph1是升级到LangGraph状态图之后，改用了LangGraph原生的checkpointer机制。如果要统一，理想情况应该保留一套（LangGraph的checkpointer更适合状态图场景，功能也更完整，支持中断/恢复/时间旅行等能力），把`rag_agent.py`这条也迁移过去，减少重复实现。这是当前代码里可以优化的架构一致性问题。

### Q5a：连续追问场景举例，怎么解决指代消歧

举例：用户先问"客户对价格有异议该怎么处理"，Agent检索知识库回答了价格异议处理话术；用户接着追问"那如果客户还是不接受呢"——这句话本身没有提到"客户"、"价格异议"这些关键词，如果没有历史上下文，Agent或者检索工具根本不知道要查什么。有了会话历史后，这轮追问连同前面的完整对话历史一起传给LLM，LLM能结合上一轮的问答内容理解"客户还是不接受"指的是"价格异议进一步升级的场景"，从而生成更准确的检索查询或者直接基于已有上下文追加回答，不需要用户把完整背景重新说一遍。指代消歧本质上依赖的是LLM自身基于历史上下文做推理的能力，历史管理机制负责的是"把正确的历史喂给它"这个基础设施部分。

### Q5b：有没有测试过多轮追问的效果

目前主要是人工交互测试——像`rag_agent.py`里那样手动构造几轮连续提问（先问价格异议处理，再追问后续场景），观察Agent是否能正确理解追问的指代关系、给出连贯回答。还没有做系统化的多轮对话测试集或者量化评估（比如构造一批"首轮问题+追问"的测试样本，统计指代消歧的准确率），这是可以补充的测试工作。

## 四、Agent层Prompt结构补充

```python
prompt = ChatPromptTemplate.from_messages([
    ('system', '你是一个智能助手，尽可能的调用工具回答用户的问题'),
    MessagesPlaceholder(variable_name='chat_history', optional=True),
    ('human', '{input}'),
    MessagesPlaceholder(variable_name='agent_scratchpad', optional=True),
])

agent = create_tool_calling_agent(llm, [retriever_tool], prompt)
executor = AgentExecutor(agent=agent, tools=[retriever_tool])
```

`create_tool_calling_agent`用LLM原生function-calling能力驱动，模型看到用户问题和工具描述，自主决定是否调用`rag_retriever`，调用后把检索结果拼回上下文继续生成。Prompt关键点：`MessagesPlaceholder('chat_history')`放历史对话，`MessagesPlaceholder('agent_scratchpad')`放Agent中间的工具调用轨迹（ReAct式thought/action/observation）。

## 五、核心提醒

Q4a/Q4b这条"两套历史管理机制并存"是这段简历里唯一一个纯代码事实类问题（不是设计权衡，是真实存在的技术债），如果面试官顺着代码问下去必须能讲清楚现状+原因+怎么统一，别含糊说"就是一套机制"——这种在细节上被抓到说法不一致，比承认技术债本身更减分。

## 六、局限性总览（面试官追问时诚实作答，加分项）

- 当前`store`是进程内内存字典，重启即丢，没做持久化（Redis/DB），生产场景要换成持久化的`BaseChatMessageHistory`实现。
- 没做历史长度截断/摘要，长会话会让prompt越滚越大，可提历史窗口裁剪或摘要压缩作为优化方向。
- 检索环节本身没根据历史做query rewrite（graph2 pipeline里有`transform_query`这类改写机制，可对比讲，展示对两条pipeline差异的理解，详见《1.两条Agentic工作流.md》）。

## 一句话总结话术

> 我把Milvus混合检索封装成LangChain Tool交给tool-calling agent自主调度，再用RunnableWithMessageHistory按session_id维度管理对话历史，实现销售/客服场景下的连续追问能力。
