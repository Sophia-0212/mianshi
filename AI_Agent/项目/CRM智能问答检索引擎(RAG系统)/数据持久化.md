# CRM RAG 项目的数据持久化

## 核心回答

**Milvus管理知识检索，PostgreSQL保存会话和请求执行状态，Redis负责多实例协调与限流。本地开发保留SQLite后端。**

三者不是存储同一份数据的三个副本，也不是所有数据都需要长期保存在Redis中。

## 一、当前项目有没有使用Redis？

代码已经接入Redis。选择PostgreSQL状态后端时，运行时要求同时配置Redis，用于跨实例会话协调和租户限流。

2026-09-09读取的本地配置如下：

| 配置 | 当前值 |
| --- | --- |
| 状态后端 `state_backend` | `sqlite` |
| PostgreSQL连接 | 未配置 |
| Redis连接 | 未配置 |
| 自动请求恢复 | 关闭 |

因此，按这份本地配置启动时，使用SQLite保存状态，使用进程内锁和令牌桶进行协调。**代码支持Redis，不等于当前本地环境已经启用Redis。** 其他部署环境是否启用，需要检查对应配置。

## 二、三种存储分别保存什么？

| 存储 | 项目中保存的数据 | 主要用途 |
| --- | --- | --- |
| **Milvus** | Chunk正文、Dense向量、BM25 Sparse向量，以及租户、ACL、来源、文档版本、生效时间、章节路径等元数据 | 找到有权限、符合条件的知识证据 |
| **PostgreSQL** | 会话归属与摘要、LangGraph checkpoint、请求运行台账、最终结果、问答轮次、恢复租约等 | 保存会话和执行状态，支持幂等与故障恢复 |
| **Redis** | 会话锁的持有者标识与TTL、租户限流令牌数及更新时间、维护任务锁 | 多实例之间协调并发、限流和任务互斥 |

## 三、Milvus：存“要查的知识”

例如，一条合同状态说明在Milvus中的内容可以理解为：

    正文：审批通过不代表合同已经生效……
    Dense向量：本地BGE模型生成的语义向量
    Sparse向量：BM25对应的稀疏表示
    元数据：tenant_id、acl_principals、source_id、version_id、chunk_id
            effective_from_ms、effective_to_ms、section_path等

员工提问后，系统先通过租户、权限、状态和有效期等条件限制检索范围，再进行混合召回。

**Milvus不只是存向量，也存Chunk正文和用于过滤、引用溯源的字段。** 原始Markdown文件仍由文件系统保存，不是整份源文件作为附件存进Milvus。

## 四、PostgreSQL：存“谁在问、执行到哪、结果是什么”

| 数据类型 | 对应表或机制 | 具体内容 |
| --- | --- | --- |
| 会话信息 | `rag_conversations` | 租户、用户、conversation_id、关联thread_id、摘要、更新时间与过期时间 |
| 图执行快照 | LangGraph PostgreSQL checkpointer | 问题、候选证据、工具反馈、生成结果、执行计数等图状态及恢复信息 |
| 请求运行台账 | `rag_request_runs` | 请求ID、输入内容及哈希、执行状态、重试次数、最终结果、错误类别、恢复窗口和租约信息 |
| 问答轮次 | `rag_conversation_turns` | 持久化请求流程中提交的问题与最终答案，通过请求ID约束重复提交 |
| 状态迁移记录 | `rag_state_migration_runs` | 状态迁移的标识、状态、时间与详情 |

例如，一个问答请求已经完成检索，但服务进程在生成前退出。图checkpoint用于恢复执行状态，请求台账用于判断这次请求是否完成、是否允许重试以及由谁接管。

**checkpoint与请求台账不是一回事：前者记录图执行状态，后者记录业务请求生命周期和最终结果。**

虽然Milvus管理知识，PostgreSQL的checkpoint也可能保存本次检索证据的副本。因此，不能说PostgreSQL里完全没有文档正文。

另外，当前会话表中的`summary`主要通过问答文本拼接和长度裁剪维护，不能仅凭字段名称就认为已经实现了LLM语义摘要。

## 五、Redis：存“当前谁能执行、还能接多少请求”

当前Redis主要保存三类带过期时间的协调数据：

| 数据 | Key形式 | 保存内容与作用 |
| --- | --- | --- |
| 会话锁 | `rag:conversation-lock:<线程标识哈希>` | 随机持有者token和TTL，限制同一会话同时被多个实例处理 |
| 租户令牌桶 | `rag:quota:<租户标识哈希>` | Hash字段`tokens`与`updated_at`，通过Lua原子计算剩余额度 |
| 维护任务锁 | 复用会话锁机制，使用固定维护任务标识 | 防止多个实例同时执行过期会话清理 |

例如，两个API实例同时收到同一会话的请求，会尝试取得同一把Redis会话锁。取得锁的执行者继续处理，另一个在等待期限内无法取得锁时返回会话繁忙。

锁会续期，释放时会检查持有者token，避免一个请求误删其他执行者的锁。Redis协调失败时，PostgreSQL模式不会自动退化为进程内锁。

**当前Redis没有承担问答结果缓存、Embedding缓存或聊天记录主存储。** 也没有作为本项目知识入库的持久化消息队列。

需要区分两种租约：

- **Redis会话锁**：协调同一会话的并发处理。
- **PostgreSQL请求恢复租约**：记录请求由哪个执行者持有，通过心跳和fencing token约束恢复与结果提交。

Redis可以配置自身的持久化机制，但这些临时协调数据不是项目的长期业务事实来源，不能用它们替代PostgreSQL请求台账。

## 六、还有哪些数据保存在文件系统？

| 数据 | 当前保存方式 |
| --- | --- |
| 原始知识文档 | Markdown文件及原始知识源 |
| 入库Manifest | 本地JSON文件，记录文档版本、处理指纹和chunk集合 |
| 入库操作checkpoint | 本地JSON文件，记录完成与失败的入库操作 |
| 本地开发状态 | SQLite数据库文件 |

因此，不能说“项目所有持久化数据都在Milvus、PostgreSQL和Redis里”。尤其要区分：**问答工作流checkpoint可以在PostgreSQL，入库操作checkpoint目前仍是本地JSON。**

## 七、面试时怎么回答？

“我们的RAG项目对存储做了职责划分。Milvus保存知识Chunk、稠密和稀疏向量，以及权限和版本等元数据，主要用于知识检索。

PostgreSQL保存会话归属、图执行checkpoint和请求台账，记录一次问答执行到了哪里、最终结果是什么，支撑幂等提交和故障恢复。

Redis主要承担多实例协调，保存会话锁和租户限流状态，不是聊天记录或知识正文的主存储。本地开发保留SQLite模式，是否启用PostgreSQL和Redis由运行配置决定。”
