# 双进程知识库批量入库流水线

简历原文：
> 参与开发双进程知识库批量入库流水线：解析进程与写入进程并行解耦，支持海量文档批量增量写入。

对应代码：`documents/write_milvus.py`

## 一、整体流程（30秒话术）

批量往 Milvus 灌入知识文档时，如果解析（读文件、切块）和写入（调用 Milvus API 落库）写成一个串行流程，两边会互相等待——解析一个文件耗时的时候写入进程闲着，写入 Milvus 网络耗时的时候解析进程也闲着，整体吞吐上不去。所以设计成两个独立进程通过队列解耦：一个进程专门扫描目录、解析 markdown 文件、切块，攒够一批（20条）就丢进队列；另一个进程专门从队列里取数据往 Milvus 写，两边并行跑，互不阻塞，解析快的时候写入进程可以持续消费，避免了单进程模式下"解析和写入互相等"的空闲浪费。

代码链路：`file_parser_process()` 扫描目录→逐文件调 `MarkdownParser` 解析切块→攒批 20 条放入 `Queue`→解析完发送 `None` 终止信号；`milvus_writer_process()` 阻塞式从 `Queue.get()` 取数据→调 `MilvusVectorSave.add_documents()` 写库→收到 `None` 退出循环；主进程 `multiprocessing.Process` 分别启动两个进程，`join()` 等待收尾。

## 三、标准答案

### Q2a：为什么用多进程不用多线程

因为解析阶段是 CPU 密集型工作（markdown 解析、语义切块要跑 embedding 模型算相邻句子的相似度，涉及大量数值计算），Python 的多线程受 GIL 限制，同一时刻只有一个线程真正执行 Python 字节码，多线程在 CPU 密集任务上没法真正并行、提速有限。用多进程可以绕开 GIL，让解析进程和写入进程（写入阶段也有网络 IO 等待，但配合解析进程的 CPU 计算可以更好地重叠时间线）分别独占一个 CPU 核心，真正做到两边同时工作。

### Q2b：为什么这样拆分

按"解析"和"写入"这两个逻辑阶段拆分，是因为这两个阶段的耗时特征不同、且有明显的先后依赖关系（写入依赖解析的输出），符合经典的流水线（pipeline）拆分思路——把一个串行任务拆成职责单一的阶段，通过队列串起来，前一阶段处理完一批就交给下一阶段，两阶段可以同时在不同批次上工作（解析进程在处理第 3 批文件的同时，写入进程可能正在写第 1 批的数据），从而提升整体吞吐。

### Q2c：是不是生产者-消费者模型

是的，这是标准的生产者-消费者模式：`file_parser_process` 是生产者，负责生产文档批次放入队列；`milvus_writer_process` 是消费者，负责从队列取出并处理。用队列（`multiprocessing.Queue`）而不是别的通信方式，是因为队列天然支持阻塞式的 `get()`/`put()`，自带线程/进程安全的同步机制，不需要自己写锁去做进程间的数据同步和顺序保证，用标准库现成的工具就能满足需求，不用额外引入更复杂的通信机制。

### Q3a：队列大小怎么定的，为什么要限制

`queue_maxsize=20` 是为了防止内存溢出——如果队列不限制大小，一旦写入进程速度跟不上解析进程（比如 Milvus 网络延迟突然变高），解析进程会不停地往队列里堆积数据，队列无限增长会占用越来越多内存，最终可能撑爆机器内存。限制队列大小之后，队列满了解析进程的 `put()` 会自动阻塞，等写入进程消费掉一些数据、队列有空位了才能继续放入，这样就自然形成了背压（backpressure）机制，把两个进程的速度匹配起来，避免生产者远超消费者导致的内存问题。20 这个数字目前是一个经验值，没有做过针对具体机器内存和平均单批数据大小的专门压测调优。

### Q3b：批次大小怎么选的

`batch_size=20` 决定了解析进程攒够多少篇解析后的文档才打包放进队列。批次太小（比如每解析出 1 条就放一次）会导致队列操作（进程间通信、锁开销）过于频繁，通信开销占比变高，反而拖慢整体效率；批次太大（比如攒 1000 条才放一次）会导致写入进程长时间等不到数据、也会导致一旦某批处理失败影响的数据量更大、且内存里同时缓存的未提交数据更多。20 是一个折中的经验值，兼顾通信效率和批处理粒度，没有做过严格的批次大小与吞吐量关系的量化测试。

### Q3c：队列满了会怎样

会阻塞。`multiprocessing.Queue` 的 `put()` 方法在队列达到 `maxsize` 后默认是阻塞式的，解析进程调用 `output_queue.put(doc_batch.copy())` 时如果队列已满，会一直卡在这一行等待，直到写入进程消费掉数据让队列腾出空位，解析进程才能继续往下走。这也是前面说的"背压"机制的具体体现。

### Q3d：终止信号怎么设计的

用的是往队列里放一个 `None` 作为哨兵值（sentinel）：解析进程处理完所有文件后，无论是否还有剩余未攒够批次的数据，都会先把剩余数据 `put()` 进队列，然后额外 `put(None)`；写入进程在循环里 `input_queue.get()` 拿到数据后先判断 `if datas is None: break`，收到这个信号就跳出循环结束进程。这是一种简单常见的做法，好处是实现极简单，不需要额外的进程间状态同步机制；如果要做得更规范，可以考虑用 `multiprocessing.Event` 显式发信号，或者用更成熟的任务队列框架（自带完成通知机制），但对于当前这种一次性批处理脚本场景，`None` 哨兵值已经足够、且代码可读性更直接。

### Q4a：解析某个文件失败会影响整体流程吗

不会导致整体崩溃。`file_parser_process` 里对每个文件的解析用了 `try/except` 包裹，单个文件解析抛异常时会记录日志（`log.error` + `log.exception`）然后 `continue` 处理下一个文件，不会让整个解析进程崩掉、也不会影响其他文件的正常处理，保证了批量处理时个别脏文件不拖累整体任务。

### Q4b：写入进程处理某批数据抛异常会怎样

`milvus_writer_process` 里的写入逻辑也包了 `try/except`，某一批数据写入失败会记录日志然后继续从队列取下一批，不会导致写入进程整体退出。但需要注意的是，当前实现里失败的那一批数据没有做重试或者落盘记录（没写入失败日志文件保留失败批次的具体内容），如果这批数据写入失败了，这批文档目前就永久丢失了，没有补偿机制——这是当前实现的一个可以优化的点，理想情况应该把失败批次记录下来供后续重试或人工排查。

### Q4c：主进程怎么知道子进程执行完的

用标准 `multiprocessing.Process` 的 `join()` 方法——主进程调用 `parser_proc.join()` 会阻塞等待解析进程真正执行结束（不管是正常结束还是异常退出）才往下走，紧接着 `writer_proc.join()` 同理等待写入进程结束。两个 `join()` 都返回之后，主进程才会打印"所有任务完成"。这里有个隐含的正确性依赖：写入进程是靠"收到 `None` 终止信号"才退出的，而这个信号是解析进程处理完所有文件之后才发出的，所以实际上写入进程的退出天然依赖解析进程先完成，`join()` 顺序（先等解析再等写入）和这个依赖关系是吻合的。

### Q5a：增量体现在哪里，会不会有重复数据风险

严格来说，当前代码里"增量"更多是流水线处理方式上的（新增的文件放进目录跑一次流程就能加进去，而不需要重跑全量),但没有做"去重"或者"变更检测"的机制——如果同一个 markdown 文件内容改了，重新跑一遍这套流程会把新解析出的内容作为全新的 document 再插入一遍（因为 Milvus schema 里 `id` 字段是 `auto_id=True` 自增主键，没有基于文件名/内容哈希的唯一性约束），旧版本的内容不会被自动清理或覆盖，会导致新旧内容同时存在于向量库里造成冗余甚至检索结果里出现过时信息。这是当前实现的一个已知局限，如果要支持真正意义上的增量更新，需要额外加一层基于文件路径或内容 hash 的去重/更新逻辑（比如写入前先按 filename 过滤删除旧记录，再插入新记录）。

### Q5b：文件量非常大时这个架构够用吗

当前架构（一个解析进程+一个写入进程）本质上是流水线深度为 2 的简单并行，能吃到"两阶段重叠执行"的收益，但解析这一侧仍然是单进程串行处理所有文件——如果文件数量非常大（上万个）且解析本身很耗 CPU（比如很多文件都超过 5000 字符触发语义二次切分需要频繁调 embedding），解析进程会成为瓶橆。如果要进一步扩展，可以考虑把解析这一侧也做成多进程池（比如用 `multiprocessing.Pool` 并行解析多个文件），多个解析 worker 共享往同一个写入队列 `put`，写入端保持单进程避免和 Milvus 的连接争用问题，这样能进一步提升整体吞吐。目前的实现是先验证流水线解耦本身的收益，还没有做到多解析进程这一层扩展。

### Q5c：为什么不用 Celery / RabbitMQ 这类成熟框架

目前这是一个跑在单机上的一次性批量入库脚本，任务规模和复杂度还没到需要引入分布式任务队列的程度——`multiprocessing.Queue` 是 Python 标准库自带的机制，不需要额外部署中间件（RabbitMQ/Redis 之类都要单独维护服务），部署和调试成本更低，对于当前"单机跑批处理任务"这个场景是合适的最简方案。如果未来这套入库流程要做成常驻服务、支持多机分布式处理、或者需要任务失败重试/持久化队列这些能力，那时候引入 Celery 或者消息队列会更合适，但目前规模下用标准库能满足需求，不引入过度设计。

## 四、核心提醒

这段简历问题不算深奥，但很容易在"为什么不用更专业的工具/框架"这类问题上被质疑成"设计简单"——回答思路统一是：先讲清楚当前规模下这个方案已经解决了什么问题（两阶段解耦、背压控制），再诚实说明当前实现的局限（Q5a 增量去重、Q4b 失败重试都是真实缺口），最后给出如果要扩展会怎么做。不要试图把一个单机批处理脚本包装成分布式系统，面试官一问细节就会露馅，坦诚讲清楚"规模决定方案"的判断逻辑反而更加分。
