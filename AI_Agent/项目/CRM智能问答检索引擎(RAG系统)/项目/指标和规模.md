# 指标和规模

## 1. 模拟业务背景与结果总览

### 1.1 业务问题

CRM 运营、销售支持和客户成功人员需要查询产品政策、客户归属规则、操作 SOP，并执行客户标签、归属变更、批量任务和通知等动作。旧流程存在三个问题：

1. 知识分散在文档、工单和内部 Wiki，平均一次有效查询需要 6.8 分钟。
2. 跨系统操作依赖人工复制信息，步骤多且审计链不完整。
3. 大模型试点只做问答，没有企业数据权限、动作审批和稳定性闭环。

#### 1.2.1 评测集推荐分层

首期离线 Golden Set 的 220～300 条用于从零建立评测资产；随着系统进入稳定迭代阶段，评测数据按运行成本、反馈速度和风险覆盖分层建设，而不是要求每次提交都运行全部案例。

| 数据集 | 建议规模 | 运行时机 | 主要用途 |
| --- | ---: | --- | --- |
| PR 冒烟集 | 80～120 条 | 每次提交 | 快速发现明显回归 |
| 核心 Golden Set | 300～500 条 | 每次上线前 | 发布硬门禁 |
| 完整回归集 | 1,500～3,000 条 | 夜间、重大版本 | 业务长尾和细分场景 |
| 安全攻击集 | 300～800 条 | 安全相关发布、定期全量 | ACL、注入、隐私和越权 |

安全攻击集可以与完整回归集存在样本重叠，但必须作为独立分桶统计并执行硬门禁。

### 1.3 模拟结果

| 指标 | 基线 | 上线后 | 变化 |
| --- | --- | --- | --- |
| 离线端到端正确率 | 66.4% | 80.1% | +13.7 个百分点 |
| Claim Groundedness | 82.8% | 93.6% | +10.8 个百分点 |
| Recall@10 | 71.3% | 85.1% | +13.8 个百分点 |
| 线上有帮助率 | 68.7% | 76.5% | +7.8 个百分点 |
| 人工转接率 | 21.9% | 16.2% | -5.7 个百分点 |
| RAG P95 完整响应 | 4.85 秒 | 3.08 秒 | -36.5% |
| 平均 Token/请求 | 4,980 | 3,760 | -24.5% |
| 审批恢复成功率 | 99.61% | 99.93% | +0.32 个百分点 |
| 重复副作用事故 | 2 次/月 | 连续 5 个月为 0 | 消除已知重复路径 |

解释：RAG 延迟与 Token 的基线是“所有请求无条件运行两轮校验”，上线后通过快慢路径和按需自纠错降低，因此质量提升与效率提升并不矛盾。上述全部为模拟数字。

### 1.4 容量口径补充

以模拟峰值 9 QPS 和 3.08 秒 P95 做保守槽位估算约为 27.7 个在飞请求，因此初始配置采用 36 个应用并发槽位（3×12）。这只是容量规划起点，不是用 P95 推导出的精确平均并发；最终值必须以目标环境压测和 PostgreSQL/Redis 观测校准。

恢复面单独部署 2 个 Worker、每 Pod 恢复并发 2，默认最多尝试 3 次、恢复窗口 300 秒。该配置用于避免故障积压挤占 API 正常流量；恢复吞吐和重复模型成本必须通过故障压测校准，不能从日均问答量直接推导。

### 1.5 模型选型口径补充

选型不是先定模型再找理由，是先看约束：企业内部 CRM 系统的客户数据、价格信息属于敏感数据，数据不出境是硬性要求；日问答量 4,600 这个规模，若按海外模型 API 计费方式持续跑一年，成本会明显偏高。这两条约束把方向锁定在国产、成本可控、支持私有化部署的模型上，按 Graph 各环节任务特点分层选型：

| 环节 | 任务特点 | 选型方向 |
| --- | --- | --- |
| 路由判断 / 文档评分 | 结构化、轻量判断，不需要复杂语言表达 | 更便宜的小模型 / DeepSeek 这类，成本优先 |
| 改写查询 / 生成最终答案 | 需要语言表达质量，直接影响用户体感 | 豆包这类中文对话能力强的模型 |

评判模型（LLM Judge）与回答模型选不同厂商/系列，降低同源模型评分时的自我偏好偏差；评判调用量按离线 Golden Set 规模（220-300 条）估算，不跟日常问答量级（4,600/天）走，成本影响远小于生产侧调用。

## RAG 问答规模与模型费用估算

> 按当前规模年化估算，不是首年实际账单。内部结算价按公开价三折假设，不代表百度实际采购价格。

### 1. 计算口径

| 项目 | 假设 |
| --- | --- |
| 全年天数 | 365天：261个工作日、104个周末日 |
| 工作日问答量 | 4,600次／天 |
| 周末问答量 | 工作日的十分之一，即460次／天 |
| 平均 Token／请求 | 3,760，假设包含单次问答全部模型调用的计费 Token |
| 输入／输出占比 | 85%／15% |
| 计价模型 | GPT-5.5 |
| 公开输入／输出单价 | $5／$30，每百万 Token |
| 内部结算折扣 | 假设为公开价的30% |
| 汇率 | 1美元＝6.7766元人民币 |

### 2. 年化结果

| 项目 | 估算结果 |
| --- | ---: |
| 年问答量 | 1,248,440次，约124.84万次 |
| 全年日均问答量（含周末） | 约3,420次 |
| 年 Token 量 | 4,694,134,400，约46.94亿 |
| 年模型调用费用 | 约83,502元，即8.35万元 |
| 月均模型调用费用 | 约6,958元 |

```text
年问答量 = 261 × 4,600 + 104 × 460
         = 1,248,440次

年 Token = 1,248,440 × 3,760
         = 4,694,134,400

每百万 Token 综合公开单价 = 85% × $5 + 15% × $30
                         = $8.75

年费用 = 4,694.1344 × 8.75 × 6.7766 × 30%
       ≈ 83,502元
```

### 3. 表述口径

> 工作日日均约4,600次问答，周末约为十分之一，按当前规模年化约125万次、47亿Token。假设内部结算为公开价三折，线上模型费用约8.4万元／年。

4,600次是工作日日均，不是全年日均。未另算法定节假日、调休及首年逐步放量。

费用仅含本假设下的线上 RAG 模型调用，不含离线评测、Embedding、精排、基础设施及人工。若采用多模型分层调用，应按各模型实际用量与内部单价分别核算；缓存优惠不再额外叠加到本次三折假设中。

## CRM 智能问答业务验收指标

> 以下为按项目规模构造的一周模拟数据，用于理解指标与练习汇报，不是生产实测结果。解决确认、问题关联及人工转接记录均为本次模拟的采集前提，不代表代码已实现。

### 周报样本口径

- **业务规模**：18个 workspace，注册用户1,640人，日活约890人。
- **问答请求**：5个工作日×4,600次＋2个周末日×460次＝23,920次。
- **可评价回答**：23,800份；另120次未形成完整可评价回答，不进入反馈指标分母。
- **业务问题**：按问题编号合并追问后，共16,000个；观察至周末结束后7天，按该时间点状态结算。
- **人工抽检**：从可评价回答中随机抽取100份，分批完成判定；高风险专项抽检另报，不混入这100份。

### 指标表

按周计算

| 优先级 | 指标 | 计算口径 | 意义 | 模拟数据（一周） |
| --- | --- | --- | --- | --- |
| 核心 | 助手独立解决率 | 经确认由助手独立解决、无需人工接手的问题数 ÷ 已到观察截止时间的有效问题数 | 衡量助手独立解决业务问题的能力 | 10,400 ÷ 16,000＝**65.0%** |
| 核心 | 平均有效查询耗时 | 助手独立解决的问题，从首次查询到确认解决的耗时之和 ÷ 对应问题数 | 衡量员工查询并解决问题的时间成本 | 24,960分钟 ÷ 10,400＝**2.4分钟／问题** |
| 核心 | 系统转人工率 | 系统内发生人工转接的问题数 ÷ 已到观察截止时间的有效问题数 | 衡量系统内人工支持依赖 | 2,592 ÷ 16,000＝**16.2%**；其中2,080个已解决 |
| 核心 | 人工抽检正确率 | 人工判定正确的回答数 ÷ 已完成最终判定的抽检回答数 | 衡量答案是否符合业务事实、必要条件、适用范围及版本 | 88 ÷ 100＝**88.0%**；100份均已完成判定 |
| 核心 | 关键错误率 | 存在至少一项关键错误的回答数 ÷ 已完成最终判定的抽检回答数 | 衡量可能导致错误操作或决策的风险 | 3 ÷ 100＝**3.0%**；另9份为非关键错误 |
| 辅助 | 整体已确认解决率 | 经确认已解决的问题数（含人工接手后解决）÷ 已到观察截止时间的有效问题数 | 衡量问答与人工支持共同完成问题闭环的效果 | （10,400＋2,080）÷ 16,000＝**78.0%** |
| 辅助 | 有帮助率／点赞率 | 点赞回答数 ÷ 收到有效评价的回答数 | 衡量主动评价用户对答案的认可 | 1,821 ÷ 2,380≈**76.5%** |
| 辅助 | 负反馈率 | 点踩回答数 ÷ 收到有效评价的回答数 | 发现用户不满并定位改进方向 | 559 ÷ 2,380≈**23.5%** |
| 辅助 | 评价覆盖率 | 收到有效评价的回答数 ÷ 已到评价观察截止时间的可评价回答数 | 说明用户反馈覆盖范围 | 2,380 ÷ 23,800＝**10.0%** |

### 数据核对

```text
16,000个问题：
10,400个助手独立解决＋2,080个人工接手后解决
＋1,600个明确未解决＋1,920个未确认＝16,000。

2,592个转人工问题：
2,080个已解决＋512个尚未确认解决＝2,592。
后512个属于上面的未解决或未确认问题，不再重复相加。

100份抽检回答：88份正确＋9份非关键错误＋3份关键错误＝100。
2,380份有效评价：1,821份点赞＋559份点踩＝2,380。
```

### 模拟汇报表述

> 按这一周的模拟数据，约2.4万次问答对应1.6万个业务问题，助手独立解决率65%，独立解决的问题平均查询耗时2.4分钟，系统转人工率16.2%。随机抽检100份回答，88份正确、3份存在关键错误，需要单独跟进。有帮助率76.5%，但评价覆盖率只有10%，因此不能仅凭点赞判断整体质量。

旧流程是6.8分钟
