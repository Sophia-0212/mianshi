## 请你说说路由和自救错机制
第一步是问题路由。 我们让模型根据问题输出结构化的数据源类型，限定为三种：CRM 操作、销售 SOP 等内部业务问题走知识库；需要实时或外部信息的问题走 Web 搜索；问候、寒暄等不需要检索的问题直接回答。程序校验路由结果，再通过条件边进入对应节点。

第二步是检索后的相关性检查。 知识库采用 Dense 和 BM25 混合检索，两路各取 Top20，RRF 融合后保留 Top20，再经过权限校验、去重和 BGE 精排取 Top5。之后由模型逐篇判断文档与问题是否相关，过滤无关片段。如果有相关文档，就进入生成；如果没有，就尝试改写查询、重新检索。
  
第三步是生成后的双重检查。 先检查答案中的业务事实能否被证据支持，再检查答案是否真正回答了用户原始问题。这两个检查对应不同的纠错动作：如果答案缺乏证据支持，就基于现有证据重新生成；如果答案有依据但没有解决问题，在知识库链路中就改写查询，重新寻找证据。

最后是控制纠错的退出条件。 我们对检索、生成、查询改写分别设置次数上限，同时控制请求总时长、总步骤和 Token 预算；如果重复检索没有获得新的证据，也会结束流程。达到限制后返回明确的失败原因或提示用户补充信息，避免无限循环。

按项目离线评测结果，加入自纠错后，忠实度从 91% 提升到了 94%。不过它会增加模型调用和延迟，所以我会把质量收益与调用开销一起评估。

“LLM 是文本生成器，CoT 是思维增强，而 ReAct 才是把模型推向行动智能的关键一步。

企业需要的不是一个回答问题的 LLM，而是能完成任务、能纠错、能连续行动的 Agent。

所以 ReAct 是当下最重要的 Agent 底层范式。”


## 我的项目里是如何实现ReAct思想的

第一层，让模型决定下一步要做什么。

- search_knowledge：补查知识。
- read_evidence：读取已有证据的原文片段。
- answer、clarify、refuse：申请回答、追问或拒答。

第二层，由后端真正执行 Action。

第三层，把真实结果作为 Observation，送回下一轮决策。

             ├─ clarify → 返回澄清问题

## 为什么 CoT（思维链）不够？

### 1. LLM 最大的问题：只能“想”，不会“做”，更不会“纠错”

LLM 本质是“被动生成式”的。

它能写计划、能回答问题，但缺乏：

- **可执行能力（Execute）**
- **状态意识（Environment State）**
- **错误感知能力（Feedback Loop）**

例如：

> “帮我查一下，搜索推广广告主的账户审核通过、合同审批通过后，是不是就能投放？还需要满足哪些条件？”

纯 LLM 会出现：

- 输出一堆自然语言描述
- 和真正的 API 没有联动
- 甚至会“编造投放准入条件”，把合同审批通过误认为合同已经生效

你把这种能力接到企业系统里，十之八九会“幻觉狂飙”。

所以，LLM 必须从“语言模型”升级成“Agent 模型”，而这一步的关键就是 **ReAct 框架**。

### 2. CoT 只能“思考”，却无法让系统真正可靠运行

CoT 的核心问题：

- **只能生成“思维链”，无法执行真实动作**
- **没有环境反馈，思考永远不会修正**
- **只是一段文本，无法保证结构化输出**

举个例子：

> “回答广告主是否具备投放条件前，需要先查询开户、合同生效和首发上线规则。”

CoT 会写出类似：

```text
// 搜索推广 CRM 问答示例
Step 1：查询广告主开户后的投放准入要求
Step 2：核对合同审批通过与合同生效的区别
Step 3：结合首发上线 SOP，说明还需满足的条件
```

它会思考，但不执行，你也不知道它思考对不对。 这在企业里是无法落地的。

### 3. ReAct 的核心：让模型“先思考，再行动，再根据反馈继续思考”

Agent 的动作流如下：

> **Thought → Action → Observation → Thought → Action → …**

这就是 ReAct 的完整循环。

我们拆一下：

#### ① Thought（思考）

LLM 分析任务：“需要查询搜索推广广告主审核通过后的投放准入条件”。

#### ② Action（行动）

LLM 用 Function Call：

```jsonc
// 搜索推广 CRM 知识检索示例
{
  "name": "search_knowledge",
  "args": {
    "query": "搜索推广广告主账户审核通过后，首次投放需要满足哪些条件"
  }
}
```

这是实际可执行的结构化动作。

#### ③ Observation（观察结果）

后端执行知识检索，返回授权知识片段（示意）：

```jsonc
// 搜索推广 CRM 工具反馈示例
{
  "status": "OK",
  "evidence": [
    {
      "evidence_id": "E1",
      "text": "账户审核通过不等于可以投放。首次充值到账、合同生效且风险状态为“可投放”后，运营才能创建首个上线任务。"
    }
  ],
  "new_evidence_count": 1
}
```

#### ④ Thought（反思）

模型发现：用户只说“合同审批通过”，而证据要求“合同生效”，需要继续查清两者的区别。

#### ⑤ Action（执行下一步）

继续调用 `search_knowledge`，补查“合同审批通过与合同生效的区别，以及搜索推广首发上线条件”。如果预览没有展示完整条款，再用 `read_evidence` 读取本次请求已有证据的原文片段。

**这套流程，让 LLM 从“生成式模型”升级成“问题求解模型”。**

## 为什么 ReAct 是目前所有 AGI、Agent 框架的底层范式？

因为它完美解决了企业所有痛点：

### 1. 可控性：每一步都能审查、校验、回滚

在 ReAct 中：

- 思考（Thought）可以禁用或隐藏
- Action 每次都可验证
- Observation 可判断是否异常
- 可以让系统自动 Retry / Reflection

这让 Agent 具备“工程级的可靠性”。

### 2. 可复现性：每一个决策链都是明确的

企业最怕“不确定”，ReAct 在日志中会留下：

```text
用户询问投放条件 → 分析证据缺口 → 检索开户规则 → 返回合同生效要求 → 补查合同状态 → 带引用回答
```

完整链路可复盘，可监控，可调优。

### 3. 错误可恢复：有 Feedback 才能自我纠错

例如查询搜索推广投放条件时没有取得可用证据，ReAct 能够在原授权范围和重试预算内这样处理：

```text
Observation: {"status": "NO_AUTHORIZED_EVIDENCE", "evidence": []}
Thought: "当前查询没有取得授权证据，需要补查广告主准入、合同生效和首发上线规则"
Action: 调用 search_knowledge，query 为“广告主准入、合同生效、首发上线条件”
```

这就是智能。

### 4. 可扩展性：轻松支持多步骤、多工具、多策略

例如，搜索推广 CRM 场景中的 Agent 可以接入：

- 广告主开户、客户归属和投放 SOP 知识库
- CRM 广告主与商机状态查询接口
- 合同生效、充值到账状态查询接口
- 创意审核与投放准入状态查询接口

当前项目已实现知识检索与证据读取，以上业务状态查询接口属于可扩展接入范围。

ReAct 天然支持多工具组合。

## 为什么所有 Multi-Agent 都是基于 ReAct？

> **多 Agent = 多个 ReAct Agent 互相发送 Thought/Action/Observation。**

这意味着：

- 一个 Agent 负责拆分广告主投放准入问题，规划需要查证的条件
- 一个 Agent 负责检索开户规则、合同状态说明和投放 SOP
- 一个 Agent 负责检查回答是否遗漏准入条件、引用是否支持结论
- 一个 Agent 负责维护本次 CRM 问答的上下文和已取得的知识证据

这是搜索推广 CRM 场景下的职责拆分示例；当前代码使用单个证据决策循环配合固定校验节点。

整个 AI 系统像“多人团队协作”，而基础全是 ReAct 循环。

如果你能讲到这里，面试官会知道你真的理解 Agent 底层机制。


面试官很可能继续追问下面三个问题：

  ## 1. “已经有 Rerank，为什么还需要相关性判断？”

  > Rerank 主要解决候选之间的排序问题。即使所有候选都不相关，它也可以排出前五名。后面的相关性判断承担的是过滤职责，允许
  > 把这五条全部判为不相关，从而触发重新检索。不过这一层会增加调用开销，是否值得保留，需要通过消融评测验证。

 ##  2. “模型判断自己有没有幻觉，可靠吗？”

  > 不能保证完全可靠。我们让检查节点基于生成时实际使用的证据判断，约束它只输出结构化结果，但模型仍可能误判。因此，这是
  > 一层质量检查，不能当成正确性证明；还需要用人工标注和离线评测验证它能发现多少错误、会误拒多少正确答案。

 ##  3. “知识库查不到，就直接 Web 搜索吗？”

  这里要区分当前实现与改进方案：

  > 当前代码在没有相关文档、查询改写预算耗尽且 Web 搜索预算允许时，存在转外部搜索的分支。但对于内部 CRM 问题，外部信息
  > 未必适用，因此这部分还需要增加外搜适用性判断。对内部制度、客户信息等问题，缺少证据时应提示补充信息或无法确认，不能
  > 直接用外部资料替代。
