# 对话历史太长，怎么管理上下文？

## 核心答案

对话历史太长时，不能把全部消息都塞进 Prompt，也不能机械地只保留最近几轮。我会把对话上下文分成两部分：

- **近期窗口**：保留最近的原始消息和当前任务状态，保证近几轮对话连贯。
- **历史摘要**：将超出近期窗口的旧消息压缩为摘要，保留仍会影响当前任务的目标、限制、进度和未解决问题。

每轮调用模型时，按“历史摘要 + 近期原始消息 + 当前问题”组装 Prompt。这样既能控制 Token，又不会丢失较早但仍然重要的条件。

## 一、近期窗口

### 1. 近期窗口保存什么

近期窗口保存最近的原始消息、当前任务状态和临近上下文。它主要保留：

- 用户最近一轮输入。
- 用户刚刚确认的对象和条件。
- 尚未完成的任务状态。
- 当前问题中“它、这个、那项”等指代所需的上下文。

近期窗口的优点是信息原始、更新快，模型可以直接看到用户刚刚说过的内容。它的缺点是容量有限，超出窗口的旧消息会被移出。

### 2. 为什么不能只用“最近几轮”定义窗口

一轮对话可能只有几十字，也可能包含上千 Token 的表格或引用。因此“保留最近 5 轮”并不能稳定控制上下文长度。

更稳妥的方法是同时考虑：

- **消息数量**：防止大量短消息占据上下文。
- **Token 预算**：保证近期消息不超过模型输入预算。
- **消息重要度**：优先保留用户确认项、未完成状态和会影响当前回答的条件。

裁剪时，先删除无关寒暄、重复表达和已经完成且不影响当前问题的过程信息。

### 3. 近期指代示例

对话历史：

~~~text
用户：这条高意向线索已经连续两个工作日没有有效跟进。
助手：我可以根据当前线索治理规则说明回收时间。
用户：那到第三个工作日上午会怎样？
~~~

当前问题中的“那”和“第三个工作日”都依赖最近对话。近期窗口必须保留“高意向线索”和“已经连续两天没有有效跟进”两个条件，查询改写才能得到完整问题：

~~~text
一条高意向线索连续两个工作日没有有效跟进，到第三个工作日上午会如何处理？
~~~

### 4. 近期窗口不应保留什么

- 与当前任务无关的寒暄。
- 已经被后续消息明确更正的旧值。
- 可以通过当前输入直接得到的重复信息。
- 与当前问题完全无关的旧话题细节。

## 二、历史摘要

### 1. 为什么需要历史摘要

如果每轮都把从第一轮开始的全部对话交给模型，Token 会随对话持续增长，旧话题和已经失效的条件也会干扰当前问题。

但如果只保留最近几轮，又会丢掉较早但仍然有效的条件。例如，用户第一轮确认了客户行业、预算范围和推广目标，随后讨论了十几轮开户材料。如果最初条件已经移出近期窗口，模型就可能忘记客户属于特殊行业。

历史摘要的作用就是：

> 将已经移出近期窗口的旧对话压缩为较短、可校验的任务背景。

### 2. 历史摘要保存什么

历史摘要适合保存：

- 用户已经确认的目标。
- 仍然生效的关键限制和数字。
- 当前任务已经完成到哪一步。
- 尚未解决的问题。
- 用户明确做出的选择和更正。

它不应把每句话换一种说法重写，也不应将模型推测写成用户已经确认的事实。

### 3. 历史摘要示例

较早的对话包含：

~~~text
用户：这是医疗行业客户，预算是 30 万元。
用户：推广目标是获取有效线索。
用户：客户主体材料已经提交，但行业资质还缺一项。
~~~

可以压缩为：

~~~text
当前客户属于医疗行业，预算 30 万元，推广目标为获取有效线索。客户主体材料已提交，尚缺一项行业资质。
~~~

不能总结成：

~~~text
客户材料已齐全，可以正常开户。
~~~

错误摘要丢失了“医疗行业”和“还缺一项资质”两个关键条件，还创造了原对话中不存在的“可以开户”结论。

### 4. 如何降低摘要失真

自由文本摘要有两个主要风险：

- 模型可能漏掉否定词、例外条件和关键数字。
- 多次递归总结后，早期误差可能被当作事实继续累积。

可以使用以下措施：

1. 保留摘要版本和生成时间。
2. 记录该摘要覆盖的原始消息 ID 范围。
3. 将预算、客户类型、当前步骤等高风险字段结构化保存。
4. 摘要生成失败时，回退到近期窗口，不把空摘要或错误摘要传给下一轮。
5. 当近期消息与历史摘要冲突时，优先使用用户刚刚确认的新信息。

## 三、如何组装 Prompt

模型输入中要明确区分历史摘要、近期原始消息和当前问题：

~~~text
[历史摘要]
当前客户属于医疗行业，预算 30 万元，尚缺一项行业资质。

[近期对话]
用户：补充材料今天已经提交了。
助手：需要继续确认审核状态。

[当前问题]
那现在能承诺今天开户吗？
~~~

如果近期消息已经明确更正了历史摘要，系统应优先使用近期新值，并在本轮结束后刷新摘要，不能让旧摘要持续覆盖新信息。

## 四、如何评测近期与历史上下文

### 1. 近期指代

用户刚刚确认一个对象，下一轮用“它、这个、那项”追问。检查近期窗口是否保留正确对象。

### 2. 较早条件保留

将关键条件放在第一轮，随后加入十几轮对话，确保该条件移出近期窗口。检查历史摘要是否仍保留该条件。

### 3. 摘要否定信息

在较早对话中写入“不能承诺当天开户”或“还缺一项材料”，检查历史摘要是否丢失“不”和“还缺”。

### 4. 新旧信息冲突

历史摘要保存旧预算，用户在近期对话中明确修改预算。正确行为是当前回答使用新值，并更新摘要。

### 5. Token 预算

构造长对话，检查“历史摘要 + 近期窗口”是否稳定控制在预算内，且不会为了截断长度而丢失当前问题。

评测不能只演示一次“它记住了”，还要分别统计：

- 近期指代理解正确率。
- 较早关键条件保留率。
- 摘要关键事实覆盖率。
- 摘要数字、否定和例外信息的丢失率。
- 旧摘要覆盖近期新值的冲突率。
- 平均 Prompt Token 数和长对话下的 P95 Token 数。

## 五、一条可复现的上下文 Trace

如果多轮对话答错，日志不能只记录最终 Prompt。最小 Trace 应包含：

- 近期窗口选中了哪些消息 ID。
- 哪些消息因超出数量或 Token 预算被移出。
- 本轮使用了哪个历史摘要版本。
- 历史摘要覆盖哪一段原始消息 ID。
- 最终注入 Prompt 的近期消息和摘要分别有多少 Token。
- 本轮是否产生了新的历史摘要版本。

出现错误时，按以下顺序排查：

1. 关键消息是否被错误移出近期窗口。
2. 历史摘要是否漏掉关键条件。
3. 摘要是否改变了数字、否定或例外含义。
4. 近期新值是否被历史旧值覆盖。
5. 当前问题是否因 Token 预算不足被截断。

## 六、面试官继续追问，怎么接

### 为什么不把全部历史直接交给大模型？

因为历史会持续增长，而且旧话题和失效信息会干扰当前任务。应用历史摘要压缩较早消息，同时保留近期原始消息，而不是把上下文窗口当数据库。

### 为什么不能只留最近几轮？

因为较早的消息可能仍保存着当前任务的核心条件，例如客户行业、预算和用户已经做出的选择。固定轮数会机械地丢掉这些信息。

### 摘要为什么不能直接替代原始消息？

摘要可能漏掉否定、数字和例外条件。近期消息应尽量保留原文；历史摘要应带原消息来源和版本，发生冲突时能回查原文。

### 近期消息和历史摘要冲突怎么办？

用户刚刚确认的近期新值优先。本轮回答使用新值，并在对话结束后刷新历史摘要，不能让两个矛盾值同时进入 Prompt。

### 怎么证明这套方案有效？

不能只做一次“它记住了”的演示。要使用近期指代、较早条件保留、摘要否定信息、新旧值冲突和长对话 Token 预算等测试集验证。

## 七、最后把答案完整说一遍

我不会把全部对话历史都塞进 Prompt，也不会只按固定轮数截取。我会把上下文分成近期窗口和历史摘要两部分。

近期窗口保留最近原始消息、当前任务状态和指代所需上下文，同时受消息数、Token 预算和重要度约束。超出窗口的较早消息被压缩为历史摘要，只保留已确认目标、关键限制、任务进度和未解决问题。

每轮按“历史摘要 + 近期原始消息 + 当前问题”组装 Prompt。摘要保留版本和原消息 ID 范围，并重点检查数字、否定和例外条件。当近期新信息和历史摘要冲突时，优先使用用户刚刚确认的新值，再刷新历史摘要。

评测时我会分别检查近期指代理解、较早条件保留、摘要事实完整性、新旧值冲突和 Prompt Token 预算。这套方案的目标不是“保留得越多越好”，而是在有限上下文中保留当前任务真正需要的信息。
