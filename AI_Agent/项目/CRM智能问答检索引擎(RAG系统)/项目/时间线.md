## 各类指标如何获得

| 指标 | 通常如何获得 |
| --- | --- |
| Recall@5、Precision@5、MRR | 在固定评测集上运行检索，用相关性标签计算 |
| 忠实度、答案相关性 | 对固定评测集上的答案调用Judge评判，并人工抽检 |
| 检索P99 | 在明确并发、请求量和硬件条件下压测，或从生产监控获得 |
| 用户满意度、人工查询时间等业务收益 | 从真实使用反馈或线上实验获得 |

离线评测不是断网，也不意味着不调用大模型；它是在预先准备的测试集上进行评测，可以调用回答模型和Judge模型的API。

## Recall@5

    = 检索到的相关Chunk数 ÷ 全部相关Chunk数
    = 2 ÷ 3
    = 66.7%

它说明：

> 系统找回了三分之二的正确证据，但漏掉了“下一步跟进时间”。

## Precision@5：

    = 前5条中相关Chunk数 ÷ 前5条结果数
    = 2 ÷ 5
    = 40%

它说明：

> 系统返回的5条内容中，只有2条有用，另外3条是噪声。

**MRR越高，说明第一条相关证据通常越靠前。**

## 忠实度：答案中的事实是否有证据支持：

模型回答：

- 需要充值到账。
- 需要合同生效。
- 审核通过后，系统会自动赠送推广金。

前两条有依据，第三条没有。按逐条陈述支持的口径：

    忠实度 = 有上下文支持的陈述数 / 答案总陈述数
           = 2 / 3 ≈ 66.7%

**忠实度高不代表答案完整。** 模型只回答“需要充值到账”，也可能全部有依据，但漏掉另外两个必要条件。

### 忠实度达到94%后，剩下6%的典型原因

如果94%按全部陈述汇总计算，剩下6%是Judge认为无法从实际上下文中得到支持的陈述，不等于6%的问题全部答错。以下是搜索推广CRM场景中的典型原因示例，规则仅作示例，不是已经确认的失败样本统计。

| 原因 | 实际提供的证据 | 模型回答中的问题 |
| --- | --- | --- |
| **混淆业务状态** | 合同审批通过只表示内部审批完成，签章后才生效 | “合同审批通过，已经满足合同生效条件。”把两个状态合并了 |
| **遗漏条件后作出过度结论** | 预算调整在规定范围内，**且余额充足**时，由运营执行 | “调整幅度在规定范围内，运营就能直接执行。”省略条件后，将有条件规则变成无条件结论 |
| **补充不存在的时限或承诺** | 特殊行业需要增强审核，未给出确定完成时间 | “材料齐全后，两个工作日内一定完成审核。”模型补出了时限和保证 |
| **拼接不同规则** | 上下文分别包含标准客户与特殊客户的审批要求 | 把标准客户的适用条件和特殊客户的审批角色组合成一条不存在的流程 |
| **把用户描述当成已核验状态** | 用户说“客户已经充值”，知识库只解释到账要求 | “系统已确认充值到账，可以继续上线。”当前并没有查询到账状态的工具或结果 |
| **沿用历史对话中的旧信息** | 当前用户已更正合同状态，历史摘要仍保留旧状态 | 回答沿用摘要中的“合同已生效”，与当前证据不一致 |
