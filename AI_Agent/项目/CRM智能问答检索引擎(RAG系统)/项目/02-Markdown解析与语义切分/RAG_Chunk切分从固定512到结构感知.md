# 阿里面试官怒了："RAG 你 chunk 还在用固定 512，跨页表格截断、超长章节全挂，召回率 67% 你觉得正常？"

## 一、为什么切分是 RAG 系统的地基？

先说一个结论：经历固定长度、句子级和结构感知三版切分，并进一步完善表格与列表处理，Recall@5 从 **67% 提升到 84%**，提高了 **17 个百分点**。该切分阶段按固定 Embedding 模型和检索配置进行对照，不包含后续混合检索、精排和上下文治理的收益。

本文主线数值按[时间线](../时间线.md)统一，属于当前面试材料的待核实口径，不代表已复现的实测结论；正式使用时需对应同口径评测报告。时间线未覆盖的原文实验数据单独标为待核对，不计入主线增益。

这个数字说明一件事：切分不对，检索不可能好。

原因很简单。向量检索的本质是：把用户的 query 和知识库里的 chunk 分别编码成向量，算余弦相似度，找最近的 k 个。如果一个 chunk 里的文本语义不完整——只有一半内容、表头丢失、前导句不见了——那这个 chunk 的向量就是一个"信息残缺"的向量，和任何 query 都不可能对上。

百度搜索推广 CRM 知识库有 126,400 篇原始文档，覆盖线索治理、客户归属、广告主准入、商务审批和投放运营等业务。如果 30% 的 chunk 是信息残缺的，那这 30% 里藏的知识，无论召回策略怎么调，都找不到。

## 二、三代方案对比：从 67% 到 84% 的演进路径

| 时间 | 方案阶段 | Recall@5 | 相比上一阶段 |
| --- | --- | ---: | ---: |
| 2025.03 | V1：固定512切分、纯向量检索 | 67% | 基线 |
| 2025.04 | V2：句子边界切分 | 74% | +7个百分点 |
| 2025.05 | V3：结构感知切分 | 81% | +7个百分点 |
| 2025.06 | V3完善：表格保真、列表前导句补全 | 84% | +3个百分点 |

### 第一代：固定长度切分（召回率 67%）

实现最简单：按 token 数量切，每个 chunk 不超过 512 token，相邻 chunk 重叠 50 token。

问题很直观：
这种切法对结构化文档是灾难性的。一份三千字的"客户归属与撞单处理"章节被切成六个 chunk，每个 chunk 都在句子中间断开，用户问"区域交叉客户发生撞单时应该归属哪个团队"，对应的答案在第三个 chunk 的中段，但那个 chunk 里既没有前文的章节标题，也没有后文的结论句，向量相似度算出来根本排不到前几名。

我们用 200 份文档、每份 10 个问题构建了 2000 个 QA 对的测试集，V1 的 Recall@5 是 **0.67**。

### 第二代：句子级切分（召回率 74%）

改进思路：不在句子中间切，只在句号、问号、分号等自然边界切。

判断：当前 Chunk 加上新句子后，是否超过512个Token。
overlap_sentences: = 2

句子级切分解决了"在句子中间截断"的问题，召回率提升到 **0.74**。但还有两个核心问题没解决：一是不理解文档层级结构，把一级标题和二级标题下的正文混在一个 chunk 里；二是没有处理表格和列表这种特殊结构——列表项"（1）未确认推广目标""（2）缺少有效触达证据"被拆开，每条都变成只有几十字的 chunk，信息密度极低。

### 第三代：结构感知切分（Recall@5 81%，结构保真完善后84%）

V3 的核心思路是：**先识别文档的层级结构，优先按章节和子标题边界切分，超长章节递归细切，特殊元素单独处理**。

按时间线的阶段口径，结构感知切分使 Recall@5 从 **74% 提升至81%**；进一步完善表格保真和列表前导句后，提升至 **84%**。切分阶段相比 V1 合计提高 **17个百分点**。

## 三、V3 的技术细节

### 3.1 文档结构识别：多策略融合

百度搜索推广 CRM 文档的编号体系异常复杂——有的用数字（`1. → 1.1 → 1.1.1`），有的用中文（`第一条 → （一） → 1.`），有的混用（`第3章 客户归属 → 3.1 区域交叉客户 → （1）撞单处理`）。仅靠单一的编号匹配规则，难以统一处理这些情况。

我们的方案是多策略融合：

- Markdown 原生标题标记判断基础层级。
- 数字、中文序号等正则识别非标准标题。
- 结合缩进、上下文和父子关系，区分标题与普通列表项。
- 规则冲突时按照优先级裁决；无法确定时保留原文并记录结构告警，不让系统擅自猜测。

识别出层级之后，切分的基本原则是：**同一个章节下的内容尽量放在同一个 chunk 里**，跨章节绝不合并。

### 3.2 超长章节的递归细切

章节粒度是正确的，但百度搜索推广 CRM 文档里"客户归属与撞单处理"这类核心章节经常超过 3000 字，远超模型上下文窗口的合理使用范围。

对超长章节，V3 做递归细切：

第一种情况：当前章节没有超过最大长度。那么不需要继续拆分，整个章节直接作为一个Chunk返回。

第二种情况：当前章节超过了max_size。先尝试根据子标题拆分。

第三点情况：当前章节超过max_size，但里面没有可以继续使用的子标题。这时只能退化为句子级切分：优先在句号、问号、分号等自然边界切开，避免直接从一句话中间截断。


关键点：对不同类型的章节，`max_size` 不同。"商务审批"和"广告主准入"这两类关键规则，设置了更大的 `max_size = 1536`，因为条件、结论和例外的任何截断都可能导致错误业务操作。

### 3.3 表格的专项处理

这一项与下一节的列表前导句补全共同归入2025.06的V3完善阶段，整体 Recall@5 从81%提升至84%；不能将这3个百分点分别重复归给表格和列表。

这是 V1 和 V2 都没解决的问题。百度搜索推广 CRM 文档里的审批权限表、行业准入表和错误码对照表分两种：

**小表格（≤300 token）：** 整体作为一个 chunk，不切分。

**大表格（跨页或超过 300 token）：** 按行切分，但每个 chunk 都要复制表头。

表头必须复制到每个 chunk 的原因很简单：如果 LLM 收到的 chunk 只有"A 类：10 万元、区域负责人""S 类：50 万元、销售总监"这样没有表头的数据，它不知道金额是预算调整上限还是折扣审批门槛，也不知道人名列表示审批人，只能胡编。

### 3.4 列表项的处理：前导句不能丢

这是我们项目里遇到的高频 badcase 来源。

百度搜索推广 CRM 文档里大量的内容是这种结构：

```text
以下情况不得转为商机：
 （1）未确认明确的推广目标
 （2）客户主体尚未完成确认
 （3）缺少可审计的有效触达证据
 ...
```

V1 和 V2 的切法会把"（1）未确认明确的推广目标"切成一个独立 chunk。用户问"还没确认推广目标，能先转商机吗"，这个 chunk 的向量里没有"不得转为商机"这个关键语义，会导致系统找到了这个 chunk 但 LLM 给出错误答案：看到"推广目标"出现了，却不知道这是一条禁止转化的条件。

V3 的做法：识别列表结构，把前导句和所有列表项合并为一个 chunk。如果合并后超长，至少保留前导句到每个切分出来的 chunk 里。

前导句的处理过程是：
1. UnstructuredMarkdownLoader 先识别出连续的 ListItem。
2. V3 查看列表前面的最后一个正文元素。
3. 如果正文以 ： 或 : 结尾，或者以“包括、如下、分别为、要求为、情形有”等表达结尾，就判定为前导句。
4. 列表切成多个 Chunk 时，将前导句复制到每个 Chunk。

### 3.5 Overlap 策略与待核对的独立实验

Overlap 需要通过同口径参数对照选择。以下保留原文的独立实验数据，但时间线没有提供对应记录，其结果均待核对，不能用于解释切分主线的67%到84%。

先说理论：Overlap 解决的是"关键信息恰好落在两个 chunk 边界处"的问题。比如用户问"单日预算上调超过 30% 需要谁复核"，相关内容是"预算上调不超过原值 30% 且余额充足时由运营执行（第 N 行）；超过 30% 时，需客户在可审计渠道确认并由销售主管复核（N+1 行）"。如果这两行被切在不同 chunk 里，每个 chunk 单独算向量都不能完整表达语义，加了 overlap 之后第二个 chunk 会包含第一行，语义就完整了。

原文实验结果（待核对，不纳入主线）：

| Overlap 大小 | 原文 Recall@5（待核对） | 原文存储增加（待核对） |
|---|---:|---:|
| 0 token | 0.81 | 基准 |
| 50 token | 0.86 | +5% |
| 100 token | 0.89 | +10% |
| 200 token | 0.90 | +20% |
| 300 token | 0.90 | +30% |

原文据此选择100 token。按这张表计算，0.81到0.89是提高8个百分点，相对提高约9.9%，不是提高10个百分点；存储增加10%的结果也需对应实验记录。不能仅依据这组未核对数据认定当前项目的最优参数。

在100 token的基础上，还可以采用：**基于句子边界的智能 overlap**。

固定 overlap 有个问题：可能恰好切在句子中间，上一个 chunk 的最后一段话只保留了半句。智能 overlap 在确定重叠区域后，向后扫描到最近的句子结尾才真正截断。

原文报告“避免87%的句子在overlap区域被截断，Recall@5从0.89提升到0.91”，这组结果同样待核对，不作为本项目切分阶段的结果。本文切分主线终点为84%，时间线中的91%属于后续检索与上下文治理阶段。

## 四、Chunk 的元数据设计

Chunk 的文本内容切好了，元数据同样重要。我们在每个 chunk 里存了以下字段：

```python
@dataclass
class ChunkMetadata:
    doc_id: str          # 文档ID（对应原始CRM制度文档）
    chunk_id: str        # chunk的唯一ID
    section_path: str    # 层级路径："第3章 商务审批 > 3.2 预算调整"
    chunk_type: str      # "text" | "table" | "list"
    is_key_section: bool # 是否是关键规则（审批/权限/底价）
    prev_chunk_id: str   # 前一个chunk的ID
    next_chunk_id: str   # 后一个chunk的ID
    token_count: int     # token数量
    page_range: str      # 来源段落或页码范围
```

这几个字段的用途：

**section_path**：用于答案溯源。用户问"A 类客户上调 8 万元预算需要谁审批"，系统能回答"根据第3章商务审批 > 3.2 预算调整 > A 类客户，10 万元以内需要区域负责人审批。"这比直接回答更有说服力，也更容易让用户验证。

**is_key_section**：用于标识关键规则，识别方法是关键词匹配（"审批""权限""底价""准入"）加章节标题判断。原文的“检索加1.5倍权重、识别准确率94%”属于待核对的独立参数与分类结果，不是整体答案正确率，也不计入本次固定检索配置的切分收益。

**prev/next_chunk_id**：上下文扩展。如果检索到的 chunk 语义不完整（比如只检索到了"以下情况不得转为商机："这个前导句），自动拉取同一章节的相邻 chunk 补全上下文。

## 五、切分质量怎么评估？

切分质量的评估不能靠人眼看，必须量化。我们用的核心指标是**召回完整率**：对一个问题，正确答案所需的 chunk 是否都在 Recall@5 里。

具体流程：

1. 构建 QA 测试集：从线索治理、客户归属、广告主准入、商务审批和投放运营中抽取 200 份百度搜索推广 CRM 文档，每份人工编写 10 个问题，总计 2000 个 QA 对。每个问题标注了"正确答案应来自哪个 Chunk"。
2. 跑端到端检索：对每个 query，看系统返回的 Top 5 Chunk 是否包含标注的 ground truth chunk。
3. 分维度拆解：表格类问题的召回率多少？列表类问题多少？超长章节类问题多少？哪类场景是短板？

分维度评估用于发现V2在表格与列表等结构上的短板，指导V3及其后续完善。原文的“V2表格类召回率0.51、文本类0.82”是待核对的分桶结果；时间线未给出对应分桶数据，不能用整体81%或84%直接替换。

构建测试集是有成本的——2000 个 QA 对，我们花了两个人一周的时间标注。但这个投入是一次性的，后续每次改切分方案，跑评估只需要 10 分钟，立刻知道有没有提升。很多团队不愿意做这个前置投入，导致改了方案之后"感觉更好"，但说不清好了多少。项目答辩或者面试时被追问"你怎么知道这个方案更好"，只能含糊其辞——这是很减分的回答。

## 六、实际踩过的三个坑

### 坑一：chunk_size 太小，语义不完整

我们最初 chunk_size 设 512，是参考了大量博客文章。但百度搜索推广 CRM 文档中的审批、归属和行业准入规则通常同时包含前置条件、结论和例外，512 token 切出来的 chunk 经常只有半个段落。

通过标题层级组织、超长章节递归细切和差异化长度预算（普通1024、关键规则1536），Recall@5从74%提升至81%，提高7个百分点。这个增益对应结构感知整套改造，不能全部归因于增大块长。这件事说明 chunk_size 不是一个通用参数，它应该和文档类型挂钩。通用中文文档平均句子 20-30 字，512 token 大约够 2-3 段；但 CRM 审批和准入规则常把"客户类型 + 金额门槛 + 审批角色 + 例外条件"写在同一长段中，同样 512 token 经常只有一段话的开头和中间，上下文完全断掉了。

### 坑二：表格表头丢失导致 LLM 答错

这是需要重点检查的 badcase 类型之一：检索找到了表格，但表格 chunk 里没有表头，LLM 看不懂数字对应的是什么字段。

“每个 chunk 复制表头”用于保留字段含义。原文的“表格类答案正确率43%提升到78%”属于待核对的分桶结果，不能解释为整体Recall@5，也不能与81%到84%的整体提升相加。

### 坑三：列表项被孤立切分

"（1）未确认推广目标""（2）缺少有效触达证据"这类列表项单独成 chunk 之后，向量编码时完全不知道这两条的语义背景是"不得转商机"还是"转商机必备条件"，容易影响否定性查询（"哪些情况不能转商机"）的召回。

前导句合并用于补全禁止条件的语义背景。原文的“否定查询召回率0.58提升到0.83”属于待核对的分桶结果；当前时间线只记录表格保真与列表补全合计使整体Recall@5从81%提升到84%，未分别给出两项贡献。

## 七、进阶优化方向：切分技术的前沿

掌握了 V3 的方案之后，面试官有时候还会问："还有哪些改进空间？"这是考察技术视野的问题。以下三个方向值得了解。

### 语义切分（Semantic Chunking）

思路是用 Embedding 模型来判断切分点：计算相邻句子的向量相似度，相似度突变的地方（语义跳跃点）就是自然的切分边界。比如"客户归属"讲完了，开始讲"商务审批"，这两段的句子向量之间的相似度会显著下降。

理论上比规则方法更精准，但在实践中有两个问题：第一，计算成本高（每次切分都要跑 Embedding 推理）；第二，对短文本段落效果不稳定。目前项目采用 V3 的结构感知规则方案，尚未使用 Embedding 判断语义断点；Semantic Chunking 作为候选放在迭代计划里。

如果面试官追问"为什么不直接用 Semantic Chunking"，可以这样回答：对我们 126,400 篇百度搜索推广 CRM 制度、SOP 和操作手册来说，全量 Embedding 切分会显著延长重建窗口；而新文档上线需要在几分钟内完成建库——规则方案切分一份文档只需要 2-3 秒，Semantic Chunking 要 30-40 秒。工程上不是"哪个更好"，是"在当前的时延约束下，规则方案是目前唯一能用的方案"。

### Late Chunking

这是 2024 年底出现的一个新方向。基本思路是：先用长文本 Embedding 模型对整个文档（或章节）编码，获取每个 token 在完整上下文下的向量表示；再在向量层面做切分，而不是在文本层面切。

好处是每个 token 的向量里都带有全文的上下文信息，不存在"切断了就丢失了前文语义"的问题。缺点是对模型的上下文长度有要求（需要支持长文档输入），且目前支持这种编码方式的开源模型还不多。

从工程可行性角度来看，Late Chunking 目前处于研究向阶段。我们评估过 jina-embeddings-v3 的 Late Chunking 实现，在单文档上效果确实有提升，但多文档批量处理时的内存占用是传统方案的 8-10 倍，暂时没法用在生产环境里。值得追踪，等硬件成本下来或者出现更高效的实现，这个方向可能是下一代 RAG 切分的标准答案。

### 动态 Chunk Size

不同类型的内容应该有不同的 chunk_size。我们目前的实现是对商务审批、权限、底价和行业准入等关键规则用 1536、普通文本用 1024，还比较粗糙。更细粒度的做法是：根据章节的语义密度（信息量/token 数）动态调整，高密度章节用更大的 size，低密度的简介类内容用更小的 size。

这个方向属于后续候选优化。原文的“多跳推理类问题召回率提高3-5个百分点”未在当前时间线中给出对应实验，需独立核对，不叠加到切分阶段的84%。具体判断"语义密度"的方式是：先用 LLM 给章节内容打一个信息密度评分（0-10分），高于 7 分的章节用 1536，低于 4 分的用 512，中间区间用 1024。目前这个评分本身也需要推理时间，成本和收益还在权衡中。

## 八、面试怎么答 RAG Chunk 切分策略？

这个问题是面试官筛选候选人深度的常用手段。很多人卡在第一层就出不来。

**先讲演进路径（30 秒）。** "我们做了三版方案。V1固定长度切分，Recall@5为67%；V2句子级切分为74%；V3结构感知切分为81%；进一步完善表格和列表处理后达到84%。切分阶段合计提高17个百分点，后续混合检索和精排的收益另行统计。"

**讲 V3 的核心设计（60 秒）。** "V3 有四个核心改进：第一，结合标题标记、编号和父子关系等规则识别文档结构，优先按章节边界组织内容，超长时再根据 token 预算递归细切；第二，超长章节递归细切，普通章节 1024 token，审批、权限和准入等关键规则用 1536，保证语义完整；第三，表格专项处理，每个切分后的 chunk 都复制表头，大表格按行切分；第四，列表项合并前导句，避免'（1）未确认推广目标'这种孤立 chunk 丢失'不得转商机'的语义背景。"

**讲 Overlap（20 秒）。** "Overlap用于减少边界信息丢失，重叠区域也要尽量遵守句子边界。选择大小时，需要同时比较召回效果、重复内容和存储开销，不能只追求重叠越多越好。独立实验数据核实前，不将原文的参数收益计入项目结果。"

**讲元数据（20 秒）。** "每个 chunk 存了 section_path、is_key_section、前后 chunk ID 等元数据。section_path 用于定位'商务审批 > 预算调整'这样的证据路径，is_key_section 用于对审批、权限、底价和准入等关键规则加权，前后 chunk ID 用于检索到半截信息时自动扩展同章节上下文。"

**讲评估方法（20 秒）。** "在固定评测集、Embedding模型和检索配置下，对比新旧切分方案，分文本、表格、否定查询和多跳推理等类型检查效果。整体结果与分桶结果分别记录，避免把单项实验收益重复加到总体上。"
