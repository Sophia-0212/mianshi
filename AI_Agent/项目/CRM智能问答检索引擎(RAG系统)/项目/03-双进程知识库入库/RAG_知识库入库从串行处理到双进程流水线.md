# 为什么首版就选择双进程入库？

实现批量入库前，我们调研了单进程串行处理和双进程流水线两种方案。

双进程可以让“解析下一批文档”和“向量化并写入上一批文档”同时进行，相比同步串行处理，有机会缩短批量入库的总耗时。

因此，结合搜索推广 CRM 批量上传文档的场景，我们从首版就选择了解析、写入两个子进程，并通过有界队列传递批次、控制积压。

## 单进程：按批次串行处理

    同一台服务机器上的一个工作进程
        │
        ▼
    解析、切分第 1 批文档
        │
        ▼
    第 1 批 Embedding → 写入 Milvus
        │
        ▼
    解析、切分第 2 批文档
        │
        ▼
    第 2 批 Embedding → 写入 Milvus
        │
        ▼
    继续处理后续批次

前一批解析和写入全部完成后，才开始解析下一批。

## 双进程：解析与写入并行推进

    同一台服务机器
        │
        └─ 主进程：启动并等待两个子进程
               ├─ 解析子进程
               └─ 写入子进程

    解析子进程：解析、切分文档并组批
        │
        │ put（队列满时等待）
        ▼
    本机有界队列 multiprocessing.Queue
        │
        │ get（队列空时等待）
        ▼
    写入子进程：Embedding → 写入 Milvus

写入子进程处理第 1 批时，解析子进程可以同时准备第 2 批。这里是同机两个工作子进程，不是两个独立服务；Milvus 可以部署在其他机器上。
