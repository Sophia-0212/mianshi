# Markdown 文档解析与切块流水线

简历原文：
> 参与实现Markdown知识文档解析与切块流水线：按标题层级解析并合并父子内容块，超长文本块基于语义相似度做二次切分，保证切块内容完整性与检索粒度合理。

对应代码：`documents/markdown_parser.py` → `MarkdownParser` 类

## 一、整体流程（30秒话术）

知识文档是Markdown格式，先用Unstructured库解析成结构化元素——每个元素带category（标题/正文/列表项）和parent_id（属于哪个标题）。原始解析出来的是碎片化的元素，一个标题下面的多段正文是分开的多个document，直接存进向量库检索会丢上下文、也检索不准。所以做了两步处理：

1. **合并**：按标题层级把同一个父标题下的子内容合并成一个document，保证一个chunk里有完整的"标题+内容"语义单元
2. **二次切分**：合并后有些块因为内容多会变得很长（比如一个复杂故障排查步骤有几千字），太长的块检索时向量会被稀释，所以对超过5000字符的块用语义相似度做二次切分，在不破坏语义连贯性的前提下切成更细粒度的块

代码链路：`parse_markdown()`解析 → `merge_title_content()`合并父子块 → `text_chunker()`超长语义二次切分。

## 三、标准答案

### Q2a：为什么要按标题合并？

Unstructured解析markdown时是按元素粒度切的，一个标题和它下面的正文是分开的独立document。如果不合并直接存，检索命中一段正文时，这段正文自己没带标题信息，等于丢了"这段话是在讲什么功能/什么场景下"的上下文。比如故障排查文档里，同样一句"重启客户端"，在"登录异常"标题下和"同步失败"标题下含义完全不同，如果不带标题合并，检索出来的内容对生成阶段来说是没有语境的碎片。

### Q2b：父子块具体指什么？举个例子

举个例子，比如一份文档结构是：

```
## 客户资料同步失败
遇到同步失败，先检查网络连接...
重启客户端后仍未解决，联系管理员...
```

Unstructured解析后，"客户资料同步失败"是一个category=Title的document，下面两段正文是两个category=NarrativeText、parent_id指向这个标题element_id的document。合并逻辑就是把这两段正文依次拼接到标题这个document的page_content后面，最终变成一个完整块：标题+完整正文，同时把标题记录进metadata方便后续追溯。

### Q2c：标题多级嵌套时怎么处理？

标题拼接是用`父标题 -> 子标题`这种路径形式记录在metadata的title字段里，如果是三级标题，会拼成"一级 -> 二级 -> 三级"这样的路径，这样即使检索到的是三级标题下的内容，也能追溯到完整的层级上下文。不过这块目前对超过3层嵌套的情况没有专门测试过，文档本身层级不深（一般2-3级），是一个可以补充验证的边界。

### Q3a：语义相似度切分具体怎么算的？

用的是LangChain的SemanticChunker。原理是把长文本先按句子切开，对每两个相邻句子算embedding的余弦距离，如果某处的距离突然变大（说明这里语义跳变明显），就在这里断开成一个新的chunk。用的是percentile模式，也就是统计所有相邻句子距离的分布，取一个百分位数（比如95分位）作为断点阈值——距离超过这个百分位的地方才切，这样切出来的每个chunk内部语义是连贯的一段，不会在句子中间硬切。

### Q3b：为什么不直接固定长度切？

固定长度切分最大的问题是它不管语义边界，纯粹按字符数一刀切，很容易把一个完整的操作步骤或一句话切成两半——比如一段故障排查步骤"第一步检查网络，第二步重启客户端，第三步..."如果刚好在第二步中间被切断，前半句和后半句分到两个不同chunk，检索到任何一半都是不完整的信息，生成时容易答非所问。语义切分是找语义跳变点切，能保证每个chunk是一个相对完整的语义单元，检索命中率和生成质量都更稳。

### Q3c：阈值怎么定的？怎么判断好坏？

目前5000字符和percentile分位这两个阈值主要是基于实际文档抽样调整出来的经验值，还没有做严格的量化AB测试。评估方式是人工抽样看切出来的chunk：是否把一个完整的操作步骤/一段解释切断了、chunk长度分布是否合理（不会出现单个chunk依然过长或碎成几个字的情况）。这块可以补充：拿一批标注好的问答对，对比不同阈值下的检索命中率来定量选阈值。

### Q3d：语义判断用的模型，和最终存库检索的模型是同一个吗？

**不是同一个**。语义切块用的是接千帆网关的`bge-large-zh`（通过`OpenAIEmbeddings`接口协议调用，`base_url`指向qianfan，模型名叫`openai_embedding`但实际不是OpenAI模型）；存Milvus检索侧用的是本地跑的`bge-small-zh-v1.5`。两个是不同规格的模型（large vs small，云端API vs 本地）。

### Q3e：两个模型不一致，会不会有问题？

确实不完全一致，理论上如果切块时判断的语义边界和最终检索时的向量空间用同一个模型会更一致、误差更小。当时选择用bge-large-zh走网关API做切块阶段的原因是它精度更高、且切块是离线批处理不需要考虑推理延迟；存库检索侧用本地bge-small主要是考虑本地部署、免调用外部API的成本和延迟。这两个模型都是bge系列同源模型，语义空间相似度较高，实际影响有限，但如果要做得更严谨，应该统一用检索侧的模型来做切块判断，减少这种两次编码的不一致性——这是可以优化的点。

### Q4：效果怎么样？怎么验证的？

目前这块主要是人工验证阶段：拿几类典型问题（SOP流程类、故障排查类、话术类）去测试检索能不能命中正确的chunk，生成答案是否准确、完整。还没有做严格的量化AB对比（比如召回率、chunk平均长度分布的对比实验），这是接下来可以补充的评估工作。
