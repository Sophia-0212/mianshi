# 一、入库流程：markdown解析 → SemanticChunker

## 1. 流程总览

```
用户上传文档（单个或批量）
        ↓
md 先转 html
        ↓
按照 html 标签定类型（标题和内容等）
        ↓
按标题层级重挂 parent_id 和内容
重新组织成有语义完整性的检索单元
        ↓
超过5000 → 进行 SemanticChunker 语义划分
不超过5000 → 直接进入 milvus
        ↓
   （SemanticChunker 内部）
        ↓
按照 。？！ 拆分句子
        ↓
[i-1] + [i] + [i+1] 句组合
        ↓
调 openai_embedding 把组合句转成向量
        ↓
1 - cosine相似度，算出第i句和第i+1句之间的距离
        ↓
距离越大，说明这两个位置的组合句在语义空间里离得越远
越可能是话题切换点
        ↓
percentile 模式，默认阈值95
        ↓
开始切分
        ↓
切分成语义完整且小于5000字符的段落
        ↓
攒够20个放进队列（继续解析下一批，不等待）
        ↓
put 队列触发进程间通信（跨进程共享的管道）
        ↓
get 获取20个 Document
        ↓
批量写入 Milvus
```

# 二、使用流程：用户提问（Self-RAG 检索问答）

## 1. 流程总览

```
运营/销售同学进入CRM系统
        ↓
点击顶部栏"CRM智能助手"按钮
        ↓
唤起类似豆包的聊天页面
        ↓
输入问题（比如"客户说价格太贵怎么办"）
        ↓
问题路由判断（route_question / question_router_chain）
  ├─ 判断是CRM相关（销售SOP/产品功能/故障排查/异议话术）→ 走知识库检索
  └─ 判断不是CRM相关（比如问天气）→ 走网络搜索
        ↓
   【走知识库检索这条路】
        ↓
retrieve 节点：混合检索
  Milvus同时跑 dense（bge语义检索）+ sparse（BM25关键词检索）
  两路结果用 RRF 算法融合排序，取top4
        ↓
grade_documents 节点：逐篇打相关性分
  LLM判断每篇召回的文档是否真的跟用户问题相关
  相关的留下，不相关的过滤掉
        ↓
decide_to_generate 判断
  ├─ 过滤后还有相关文档 → 进入 generate 生成答案
  ├─ 过滤后没有相关文档 & 还没重试超2次 → transform_query 改写问题 → 回 retrieve 重新检索
  └─ 过滤后没有相关文档 & 已重试2次 → 升级到 web_search 兜底
        ↓
generate 节点：调用LLM，基于筛选后的文档生成答案
        ↓
双重质量校验
  1. hallucination检测：答案是否基于检索到的文档内容，没有瞎编
     ├─ 没通过 → 打回 generate 自己重新生成
     └─ 通过 → 进入下一道检测
  2. answer_grader检测：答案是否真的切题回答了用户的问题
     ├─ 不切题 → transform_query 改写问题 → 回 retrieve 重新检索
     └─ 切题 → 结束，返回答案给用户
        ↓
   【走网络搜索这条路（问题不属于CRM知识库范围，或知识库检索多次未果升级）】
        ↓
web_search 节点：调用Tavily搜索
        ↓
直接进入 generate 生成答案（跳过grading这一步）
        ↓
最终答案展示在聊天页面
        ↓
运营/销售同学看到答案，可能继续追问
  （比如接着问"那客户还是不接受怎么办"——这时候依赖对话历史管理，
   系统能结合上下文理解"客户"指的是刚才那个价格异议场景）
```

# 三、补充说明与问答摘录

- 上一部分（入库流程）是**离线的、一次性/批量的准备工作**；上一部分使用流程是**在线的、每次用户提问都要走一遍**的实时流程，两者通过Milvus这个知识库连接起来——入库流程把文档变成可检索的向量，使用流程才是真正把这些向量用起来回答问题。
- graph2这套Self-RAG设计比graph1（简单agentic RAG）多了"问题路由""文档相关性过滤""生成质量双重校验"三层机制。
- **潜在风险点**：`generate`→hallucination检测不过→退回`generate`自身这条边**没有重试次数上限**（[graph_2.py:138](../../workspace/RAG企业知识库项目/RAG_PROJECT/graph2/graph_2.py#L138) `"not supported": "generate"`），理论上如果模型持续判定自己"有幻觉"，会一直在这条边里打转，没有兜底跳出机制（跟`transform_query`那边有`transform_count>=2`的收敛计数器形成对比）。

## 附：问答摘录（问题路由与结构化输出相关知识点）

以下是之前几轮问答里摘录的知识点片段，保留作为速查笔记。

**Q：如何跟面试官描述用LangChain写的动态路由？**

> 我用LangChain的`with_structured_output`结合Pydantic的`Literal`枚举类型，实现了一个基于LLM语义理解的动态路由——让大模型根据用户问题的语义，在"查向量知识库"和"查网络搜索"之间做决策，替代了传统的关键词匹配或规则路由。

**Q：Pydantic是什么？**

> Pydantic是Python里专门做"数据校验+转换"的库——定义数据该长什么样，创建/接收数据时立刻检查，不符合就拦下来，能安全转换的类型会自动转换。

**Q：route_question和question_router_chain是什么关系？**

> `route_question`是一个LangGraph条件边（conditional edge）的判断函数，用来决定从当前节点走向哪个下一个node（`web_search`还是`retrieve`）；这个判断函数内部调用了`question_router_chain`——一条用LangChain实现的链，链内部用了`with_structured_output`（把Pydantic Schema转成LLM API的tool定义，约束输出格式）和`|`管道操作符（LCEL语法，把prompt模板和结构化LLM串起来）这些LangChain的经典用法。

**Q：`retrieval_grader_chain`和`question_router_chain`是不是同一套写法？**

```python
retrieval_grader_chain = grade_prompt | structured_llm_grader
```

> 跟`question_router_chain`是同一套模板——Pydantic约束（这里约束的是`binary_score`只能是文字上写"yes"或"no"，不是严格的`Literal`枚举）+ `with_structured_output` + system/human prompt + `|`管道。区别只是这次的system prompt换了个判断任务："判断这篇文档跟这个问题相关不相关"，而不是"判断这个问题该走哪个数据源"。

### retrieve 节点详解：混合检索怎么实现的

分5步讲，混合检索这块概念多，遇到RRF这种算法级的东西单独举数字例子。

#### retrieve节点整体在做什么（[retriever_node.py](../../workspace/RAG企业知识库项目/RAG_PROJECT/graph2/retriever_node.py)）

```python
def retrieve(state):
    question = state["question"]
    documents = retriever.invoke(question)
    return {"documents": documents, "question": question}
```

这个函数是LangGraph真正的Node（对照`workflow.add_node("retrieve", retrieve)`）——图执行到这一步，会更新state：从state里取出`question`，调用`retriever.invoke(question)`拿到检索结果，把结果塞回一个新字段`documents`里，返回。逻辑很薄，真正的检索细节藏在`retriever`这个对象内部（[retriever_tools.py](../../workspace/RAG企业知识库项目/RAG_PROJECT/tools/retriever_tools.py)）。

#### retriever是什么——Milvus + LangChain封装出来的一个"检索器"

```python
mv = MilvusVectorSave()
mv.create_connection()
retriever = mv.vector_store_saved.as_retriever(
    search_type='similarity',
    search_kwargs={
        "k": 4,
        "score_threshold": 0.1,
        "ranker_type": "rrf",
        "ranker_params": {"k": 100},
        'filter': {"category": "content"}
    }
)
```

`mv.vector_store_saved`是[milvus_db.py](../../workspace/RAG企业知识库项目/RAG_PROJECT/documents/milvus_db.py)里`create_connection()`创建的Milvus对象（对应之前入库部分聊过的`embedding_function=bge_embedding`+`builtin_function=BM25BuiltInFunction()`）。`.as_retriever(...)`是LangChain提供的方法，把一个"向量库对象"包装成一个统一接口的"检索器对象"——好处是不管底层是Milvus还是别的向量库，只要都封装成retriever，调用方式统一是`retriever.invoke(问题)`，不用关心底层具体怎么查的。

#### search_kwargs里每个参数是什么意思（逐个拆）

```python
search_kwargs={
    "k": 4,                              # 最终返回几条文档
    "score_threshold": 0.1,              # 相似度低于这个分数的文档直接丢弃
    "ranker_type": "rrf",                # 用RRF算法融合dense和sparse两路结果
    "ranker_params": {"k": 100},         # RRF算法自己的一个内部参数
    'filter': {"category": "content"}    # 只在category='content'的记录里检索（只有经过merge_title_content处理、打上category='content'标记的记录才会被检索到）
}
```

`k=4`就是流程图里写的"取top4"——最终不管dense和sparse各自查出多少条，融合排序完只留最靠前的4条。

#### dense + sparse 到底是"两路都跑"还是"跑一路"——混合检索具体怎么发生的

关键点：这不是Python代码手写了两次查询再手动合并，是Milvus这个数据库本身内置支持"混合检索"（Hybrid Search），只需要配置好dense和sparse两个向量字段，Milvus在底层查询引擎层面自动帮你并行查两路、再融合。

回顾入库时的[milvus_db.py:22-42](../../workspace/RAG企业知识库项目/RAG_PROJECT/documents/milvus_db.py#L22-L42)，schema里定义了两个向量字段：

```python
schema.add_field(field_name='sparse', datatype=DataType.SPARSE_FLOAT_VECTOR, is_function_output=True)
schema.add_field(field_name='dense', datatype=DataType.FLOAT_VECTOR, dim=512)
```

每条文档入库时，同一段`text`内容，会被同时算出两种向量：

- **dense**：用`bge_embedding`模型把这段文字变成一个512维的浮点数组，捕捉的是语义（比如"顾客觉得贵"和"客户对价格有异议"，字面完全不同，但语义相近，dense向量算出来的距离会很近）
- **sparse**：用Milvus内置的BM25 Function（对`text`字段jieba分词后统计词频）算出一个稀疏向量，捕捉的是关键词命中（比如用户问题里出现"分期付款"这个词，sparse检索会优先找那些文本里也出现"分期付款"这几个字的文档，哪怕语义上没那么接近）

检索时，`retriever.invoke(question)`发出的查询请求里，`vector_field=['dense', 'sparse']`（[milvus_db.py:84](../../workspace/RAG企业知识库项目/RAG_PROJECT/documents/milvus_db.py#L84)绑定过），Milvus拿到用户问题后：

1. 把问题也算一次dense向量，去dense字段的HNSW索引里查最相似的一批文档
2. 把问题也过一次BM25，去sparse字段的倒排索引里查关键词命中最高的一批文档
3. 这两路查询是同时/并行进行的，各自拿到一份候选文档+各自的打分

#### RRF——两路各自的打分怎么合并成一个最终排序（举数字例子）

**为什么不能直接把dense分数和sparse分数加起来比大小？** 因为两者不是同一个量纲——dense算出来的是cosine相似度或距离（比如0~1之间），sparse的BM25分数是词频统计出来的分数（可能是0~20甚至更大，没有固定上限）。直接相加，等于拿"温度"和"重量"加在一起比大小，没有意义。

**RRF（Reciprocal Rank Fusion，倒数排名融合）的思路**：不看"分数具体是多少"，只看"这篇文档在各自那一路里排第几名"。

举个具体例子，假设用户问"客户嫌价格贵怎么办"，dense和sparse各自独立查出一批文档，排名如下：

```
dense（语义检索）排名：
  第1名：文档A（"客户异议处理话术"）
  第2名：文档B（"分期付款方案说明"）
  第3名：文档C（"产品功能概览"）

sparse（关键词检索）排名：
  第1名：文档B（"分期付款方案说明"）——因为文本里直接命中"价格""分期"这些词
  第2名：文档D（"故障排查手册"）——碰巧命中了某个无关关键词，排名靠前但实际不相关
  第3名：文档A（"客户异议处理话术"）
```

RRF公式（简化版）：`RRF分数 = 1/(k + 排名)`，这里`k=100`（就是`ranker_params: {"k": 100}`这个配置项）：

```
文档A：
  dense排名第1 → 1/(100+1) = 0.0099
  sparse排名第3 → 1/(100+3) = 0.0097
  RRF总分 = 0.0099 + 0.0097 = 0.0196

文档B：
  dense排名第2 → 1/(100+2) = 0.0098
  sparse排名第1 → 1/(100+1) = 0.0099
  RRF总分 = 0.0098 + 0.0099 = 0.0197

文档C：
  dense排名第3 → 1/(100+3) = 0.0097
  sparse里没出现 → 记0
  RRF总分 = 0.0097

文档D：
  dense里没出现 → 记0
  sparse排名第2 → 1/(100+2) = 0.0098
  RRF总分 = 0.0098
```

最终按RRF总分排序：**文档B(0.0197) > 文档A(0.0196) > 文档D(0.0098) > 文档C(0.0097)**，取`k=4`（最终返回条数）全部保留。

**这个例子想说明的关键点**：文档B虽然dense排名不是第一（第2名），但因为sparse排名第1（关键词命中精准），综合RRF反而超过了dense排名第1的文档A——RRF的价值在于，某一路排名特别靠前，就能把它在另一路排名靠后的劣势拉回来一部分，起到"两路互相取长补短"的效果，而不是"谁的原始分数绝对值大就听谁的"。而文档D尽管sparse排名第2（关键词命中了，但实际内容跟"价格异议"这个语义可能没啥关系），因为dense那边完全没把它检索出来（说明语义上跟问题很不相关），RRF综合分数被拉得很低，排到了后面——这就是混合检索比单一检索方式更稳的地方：纯关键词匹配容易被"凑巧命中几个字但语义不对"的文档误导，纯语义检索遇到专业术语、错误码这种关键词场景又容易漏掉精确匹配的文档，两路一起跑、用RRF综合，能互相弥补对方的短板。

#### 完整链路串起来（retrieve）

```
LangGraph执行到retrieve节点
    ↓
retrieve函数：state["question"]取出用户问题
    ↓
retriever.invoke(question)
    ↓
Milvus内部并行执行两路查询：
  dense向量检索（bge_embedding算相似度，HNSW索引查最近邻）
  sparse向量检索（BM25算关键词命中分，倒排索引查）
    ↓
两路各自拿到一份候选文档+各自排名
    ↓
RRF算法（k=100这个内部参数）按"排名的倒数"融合成一个综合分数
    ↓
按综合分数排序，且score_threshold=0.1过滤掉分数太低的
    ↓
取前k=4条，作为最终documents
    ↓
retrieve函数返回 {"documents": documents, "question": question}
    ↓
state更新，流程进入下一个节点 grade_documents
```

### grade_documents 节点详解：逐篇打相关性分

分3步讲，代码本身不复杂，重点讲清楚"为什么retrieve已经排过序了，还要再单独打分过滤一遍"。

#### grade_documents节点整体做什么（[grade_documents_node.py](../../workspace/RAG企业知识库项目/RAG_PROJECT/graph2/grade_documents_node.py)）

```python
def grade_documents(state):
    question = state["question"]
    documents = state["documents"]

    filtered_docs = []
    for d in documents:
        score = retrieval_grader_chain.invoke(
            {"question": question, "document": d.page_content}
        )
        grade = score.binary_score
        if grade == "yes":
            filtered_docs.append(d)
        else:
            continue
    return {"documents": filtered_docs, "question": question}
```

逻辑很直白：拿到上一步retrieve节点检索出来的4篇文档，逐篇（一个for循环）单独喂给LLM，让LLM回答"这篇文档跟用户问题相关吗？yes还是no"，相关的留下，不相关的直接丢掉，最后返回过滤后的文档列表——这也是为什么这个节点叫"逐篇打相关性分"，"逐篇"就是这个`for d in documents`循环，一篇一篇单独判断，不是整体一次性判断。

#### retrieval_grader_chain是什么——4个`_chain.py`之一

回顾[grader_chain.py](../../workspace/RAG企业知识库项目/RAG_PROJECT/graph2/grader_chain.py)：

```python
class GradeDocuments(BaseModel):
    binary_score: str = Field(description="文档是否与问题相关，取值为'yes'或'no'")

structured_llm_grader = llm.with_structured_output(GradeDocuments)

system = """你是一个评估检索文档与用户问题相关性的评分器。
    如果文档包含与用户问题相关的关键词或语义含义，则评为相关。
    不需要非常严格的测试，目的是过滤掉错误的检索结果。
    给出'yes'或'no'的二元评分来表示文档是否与问题相关。"""
grade_prompt = ChatPromptTemplate.from_messages([
    ("system", system),
    ("human", "Retrieved document: \n\n {document} \n\n User question: {question}"),
])

retrieval_grader_chain = grade_prompt | structured_llm_grader
```

跟之前理解过的`question_router_chain`是同一套模板——Pydantic约束（这里约束的是`binary_score`只能是文字上写"yes"或"no"，不是严格的`Literal`枚举）+ `with_structured_output` + system/human prompt + `|`管道。区别只是这次的system prompt换了个判断任务："判断这篇文档跟这个问题相关不相关"，而不是"判断这个问题该走哪个数据源"。

#### 核心疑问——为什么retrieve那边已经用RRF排过序、按分数过滤过一次（score_threshold=0.1），这里还要再单独用LLM判断一遍

这是理解这个节点存在意义的关键点，用一个具体例子说明两种"相关性判断"的本质区别：

假设用户问"客户说价格太贵怎么办"，retriever（dense+sparse+RRF）检索出来的4篇文档可能是：

```
文档1："客户异议处理话术——价格异议应对策略"          （真的相关）
文档2："产品定价说明：企业版、专业版价格对比"        （沾边但答不上用户想问的"怎么办"）
文档3："销售提成计算规则，涉及价格折扣审批流程"       （命中了"价格"这个词，语义/统计分数不低，但实际内容跟"客户异议怎么处理"完全无关）
文档4："客户投诉处理SOP，包含价格投诉相关条款"        （真的相关）
```

RRF/向量检索的"相关性"是统计学意义上的相似——dense算的是语义向量距离，sparse算的是关键词命中频率，这两者衡量的是"这段文字和问题字面/语义上有多接近"，不是"这段文字是否真的能回答用户的问题"。文档3能被检索出来，可能是因为"价格"这个关键词命中，或者embedding模型觉得"价格折扣审批"和"价格太贵"语义上有点接近——但从人的角度看，这篇文档讲的是内部提成规则，根本没法用来回答"客户觉得贵该怎么应对"这个问题。

grade_documents这一步做的是"语义理解层面的二次把关"——不再是统计相似度，而是让LLM像人一样读一遍这篇文档的具体内容，结合用户问题，判断"这篇文档的内容，能不能真的帮上忙"。LLM读完文档3和文档2，可能会判断：

```
文档1 → LLM判断：yes（内容确实是价格异议应对策略）
文档2 → LLM判断：no（讲的是价格对比，不是应对方法）
文档3 → LLM判断：no（讲的是内部提成流程，跟客户异议处理毫无关系）
文档4 → LLM判断：yes（投诉处理流程里有价格相关内容，能用上）
```

过滤后`filtered_docs`只剩文档1和文档4，交给下一步generate节点生成答案——这样LLM在最终生成答案时，看到的都是真正相关的内容，不会被文档2、文档3这类"检索分数不低但实际不搭边"的内容干扰，降低生成答案时"看错资料乱说"的风险。

### 一句话总结两层过滤的分工

```
retrieve阶段的过滤（score_threshold=0.1）
  → 统计学意义的过滤，卡的是"分数够不够高"，防止把明显八竿子打不着的内容也召回进来
  → 是数据库/向量检索层面的粗筛

grade_documents阶段的过滤（LLM逐篇判断yes/no）
  → 语义理解层面的过滤，卡的是"内容能不能真正回答问题"
  → 是LLM读懂内容之后做的精筛，能识别"统计上沾边但实际不相关"这种粗筛卡不住的情况
```

两层过滤不是重复劳动，是先用便宜、快速的统计方法筛一遍范围，再用相对昂贵但更懂语义的LLM精筛一遍——这也是为什么之前CLAUDE.md笔记里提到"过滤越精细不代表生成答案就越好"这个观察背后的机制：这一层过滤越严格，`filtered_documents`可能会变得越少（比如4篇里过滤到只剩1篇甚至0篇），如果过滤过头把真正有用的内容也误判成"不相关"丢掉了，反而会导致下一步`decide_to_generate`判断"没有相关文档"，触发`transform_query`重新检索的循环，不一定是文档越少答案就越准。

### 三个"grader/grade"文件的区分

三个文件名字都带"grade/grader"容易混，按代码内容对号入座：

| 文件 | 类名 | 判断什么 | 属于哪个阶段 |
|---|---|---|---|
| `grader_chain.py` | `GradeDocuments` | "检索出的这篇文档跟用户问题相关吗" | `grade_documents`节点，在`retrieve`之后，`generate`之前 |
| `grade_hallucinations_chain.py` | `GradeHallucinations` | "生成的答案是否基于检索到的事实（有没有幻觉）" | `generate`之后，第1道校验 |
| `grade_answer_chain.py` | `GradeAnswer` | "生成的答案是否真的解决/回答了用户问题" | `generate`之后，第2道校验，即"准确性检测" |
