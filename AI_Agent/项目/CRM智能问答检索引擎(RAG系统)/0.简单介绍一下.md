我最近参与的是一个搜索推广 CRM 智能问答项目，主要服务销售、客服和广告运营人员，目前总用户1640多，日活890多。

项目主要解决知识分散、查找耗时和问答不准确的问题。销售 SOP、开户规范、客户归属规则和投放操作手册分散在多份文档中，我们通过 RAG 接入现有智能
助手，让员工能够统一查询并连续追问。我主要参与底层引擎的架构设计，以及知识入库、检索和问答工作流开发。

整个系统主要分为三部分：

知识侧，参与实现 Markdown 解析与结构感知切分，保留标题层级、表头和列表前导句，并采用 解析、写入 双进程流水线 完成批量入库。

检索侧，基于 Milvus 构建 BGE 向量与 BM25 混合检索，通过 RRF 融合，再用 CrossEncoder 精排，兼顾口语表达和政策名称、CRM业务术语等精确查询。

问答侧，基于 LangGraph 构建支持多轮对话的工具调用型 RAG 和 Self-RAG，通过相关性判断、答案校验和受控查询重写，提高复杂问题的回答质量。

评测时，我们分别关注 召回率、排序质量 和 答案忠实度，通过 新旧方案对照 定位问题，持续优化整个问答链路。

项目难点：

这个项目比较有挑战的是，Chunk的切分

起初立项的时候，要求迅速跑出一个demo演示给老板看，于是选择了最简单的切分策略 -- 固定长度切分
实现很简单：按 token 数量切，每个 chunk 不超过 512 token，相邻 chunk 重叠 50 token。

当时勉强用一些可以成功召回的案例给老板演示了，但是实际上召回率只有67%，完全不可用。

问题其实直观： 这种切法对结构化文档是灾难性的。一份三千字的"客户归属与撞单处理"章节被切成六个 chunk，每个 chunk 都在句子中间断开，用户问"区域交叉客户发生撞单时应该归属哪个团队"，当时，对应的答案在第三个 chunk 的中段，但那个 chunk 里既没有前文的章节标题，也没有后文的结论句，向量相似度算出来根本排不到前几名，导致召回率低。

后面就开始迭代Chunk切分策略，看了很多博客、搜了其他公司的RAG切分方案，看到有句子级切分、语义切分等方法。

经过对比发现，句子级切分更适合我们的项目，语义切分每次切分都要跑 Embedding 推理, 虽然语义切分最终效果会更好，但是开销太大了。

最终选择句子级切分策略作为第二版Chunk切分策略

相对于固定长度切分策略，句子级切分的改进是：不在句子中间切，只在句号、问号、分号等自然边界切。

关键判断：当前 Chunk 加上新句子后，是否超过512个Token。 overlap_sentences设置为 2

句子级切分解决了"在句子中间截断"的问题，召回率提升到 0.74。这一版本勉强能用了，基本雏形形成，部署之后，开通了测试账号给产品和研发同学试用

在试用的过程中又发现了一些新的问题：

一是不理解文档层级结构，把一级标题和二级标题下的正文混在一个 chunk 里；
二是没有处理表格和列表这种特殊结构——列表项"（1）未确认推广目标""（2）缺少有效触达证据"被拆开，每条都变成只有几十字的 chunk，信息密度极低。

为了解决这个问题，我们把问题描述，跟Claude code一起探索解决方案：

经过分析，可以采用结构感知切分策略，相邻 chunk 重叠 100 token。
核心思路是：先基于版本2的切分策略识别文档的层级结构，在此基础上，优先按章节和子标题边界切分，超长章节递归细切，每个chunk都携带标题，特殊元素单独处理。

这一版的测试结果：Recall@5 = 0.81，比 V2 提升了 7 个百分点。


整个过程持续了一两个月

取得阶段性成绩之后，正式开放给运营、销售同学开始使用。

在使用的过程中又暴露出许多问题：

1.百度搜索推广 CRM 文档的编号体系异常复杂——有的用数字（1. → 1.1 → 1.1.1），有的用中文（第一条 → （一） → 1.），有的混用（第3章 客户归属 → 3.1 区域交叉客户 → （1）撞单处理）。仅靠单一的 markdown语法 和 编号匹配规则，难以统一处理这些情况。

我们的方案是多策略融合：

Markdown 原生标题标记判断基础层级。
数字、中文序号等正则识别非标准标题。
结合缩进、上下文和父子关系，区分标题与普通列表项。
规则冲突时按照优先级裁决；无法确定时保留原文并记录结构告警，不让系统擅自猜测。
识别出层级之后，切分的基本原则是：同一个章节下的内容尽量放在同一个 chunk 里，跨章节绝不合并。


2.表格表头识别问题 和 前导句丢失问题

百度搜索推广 CRM 文档里的审批权限表、行业准入表等，表按照大小分两种：

小表格（≤300 token）： 整体作为一个 chunk，不切分。

大表格（跨页或超过 300 token）： 按行切分，但每个 chunk 都要复制表头。

表头必须复制到每个 chunk 的原因很简单：如果 LLM 收到的 chunk 只有"A 类：10 万元、区域负责人""S 类：50 万元、销售总监"这样没有表头的数据，它不知道金额是预算调整上限还是折扣审批门槛，也不知道人名列表示审批人，只能胡编。


关于前导句丢失问题，这是我们项目里遇到的高频 badcase 来源。

百度搜索推广 CRM 文档里大量的内容是列表结构：

以下情况不得转为商机：
 （1）未确认明确的推广目标
 （2）客户主体尚未完成确认
 （3）缺少可审计的有效触达证据
 ...
V1 和 V2 的切法会把"（1）未确认明确的推广目标"切成一个独立 chunk。用户问"还没确认推广目标，能先转商机吗"，这个 chunk 的向量里没有"不得转为商机"这个关键语义，会导致系统找到了这个 chunk 但 LLM 给出错误答案：看到"推广目标"出现了，却不知道这是一条禁止转化的条件。

我们的改进做法：识别列表结构，把前导句和所有列表项合并为一个 chunk。如果合并后超长，至少保留前导句到每个切分出来的 chunk 里。

如果正文以 ： 或 : 结尾，或者以“包括、如下、分别为、要求为、情形有”等表达结尾，就判定为前导句。

整体 Recall@5 从81%提升至84%
