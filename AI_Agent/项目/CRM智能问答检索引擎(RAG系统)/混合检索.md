# Milvus Dense+Sparse 混合检索方案

简历原文：
> 参与开发基于Milvus设计并实现Dense+Sparse混合检索方案：Dense向量使用本地BGE模型生成语义向量，Sparse侧基于BM25从文本生成关键词向量，两路并行检索后用RRF算法融合排序，提升专业术语、系统操作步骤等关键词场景的召回准确率。

对应代码：`documents/milvus_db.py` → `MilvusVectorSave` 类，`tools/retriever_tools.py`

## 一、整体流程（30秒话术）

纯语义向量检索（Dense）在专业术语、系统操作步骤这类关键词强的场景上召回不稳定——比如用户搜"CRM系统崩溃代码E1024"，语义向量检索容易被"崩溃"这类语义相似的内容干扰，反而漏掉包含精确错误码的文档。所以在 Milvus 里设计了双路检索：Dense 路用本地 BGE 模型（`bge-small-zh-v1.5`）生成语义向量做语义相似检索，Sparse 路用 Milvus 内置的 BM25 Function 直接从文本字段生成稀疏向量做关键词检索，两路并行查询后用 RRF（Reciprocal Rank Fusion）算法把两边的排名融合成一个最终排序，兼顾语义理解和关键词精确匹配。

代码链路：`create_collection()` 定义 dense+sparse 双字段 schema，BM25 Function 挂在 `text` 字段上自动生成 sparse 向量 → `create_connection()` 用 `langchain-milvus` 的 `Milvus` + `BM25BuiltInFunction` 建立双向量检索通道 → `retriever_tools.py` 里配置 `ranker_type: "rrf"` 做检索时融合。

## 三、标准答案

### Q2a/Q2b/Q2c：为什么要混合，各自的短板是什么

纯 Dense 向量检索基于语义相似度，遇到需要精确匹配专业术语、系统报错码、按钮名称这类"字面精确"的查询时容易漂——比如用户问"E1024 错误码怎么处理"，Dense 向量可能因为语义上"错误"、"异常"这类词权重高，检索出很多语义相关但不含精确错误码 E1024 的文档，把真正含有这个错误码的正确文档挤到后面。反过来纯关键词检索（BM25）虽然能精确匹配术语，但遇到用户用同义词或口语化提问（比如"客户不满意价格"对应文档里写的是"价格异议处理"）时，字面不匹配就检索不到，语义理解能力弱。两路结合刚好互补：Dense 兜底语义理解，Sparse 兜底关键词精确匹配。

### Q3a：Sparse 向量怎么生成的，跟传统 BM25 区别

用的是 Milvus 内置的 BM25 Function，直接挂在 schema 的 `text` 字段上（`function_type=FunctionType.BM25`），写入文档时 Milvus 会自动对 `text` 做分词、统计词频，生成一个稀疏向量存进 `sparse` 字段，不需要额外自己维护倒排索引或者手写 BM25 打分逻辑——这跟传统自己实现 BM25（比如用 whoosh/elasticsearch）的区别是，它是向量化存储的稀疏表示，可以和 dense 向量走同一套 Milvus 检索/索引框架，两路检索能在同一次查询里并行执行、结果统一走 ranker 融合，架构更简洁。

### Q3b：BM25 参数怎么配的

`bm25_k1=1.2`、`bm25_b=0.75` 用的是 BM25 的经典默认值（Elasticsearch/Lucene 也是这个默认配置）。k1 控制词频饱和度——词出现次数越多打分增长越平缓，避免高频词权重无限增大；b 控制文档长度归一化的强度，b 越大对长文档的惩罚越重，避免长文档因为词多而系统性得分虚高。目前用的是行业默认值，没有针对项目文档特点做过专门调参。

### Q3c：分词器

用的是 jieba 分词器（`analyzer_params={"tokenizer": "jieba", "filter": ["cnalphanumonly"]}`），`cnalphanumonly` 这个 filter 是过滤只保留中文/字母/数字，去掉其他符号噪音。jieba 是通用中文分词，遇到一些 CRM 系统里的专有名词（比如产品功能模块的简称、内部系统代号）分词可能不够精准，如果要优化可以考虑加自定义词典。

### Q3d：索引算法选择

`DAAT_MAXSCORE` 是文档级別逐个算分但用 MaxScore 提前剪枝跳过不可能进入 top-k 的文档，比 `TAAT_NAIVE`（逐词遍历，全量算分）效率高很多；跟 `DAAT_WAND`相比是另一种剪枝策略，两者性能接近，`DAAT_MAXSCORE`是 Milvus 官方对稀疏向量检索的推荐默认算法，所以直接采用，没有做过两者的专门 benchmark 对比。

### Q4a/Q4b/Q4c：Dense 侧细节

Dense 向量用的是本地部署的 `bge-small-zh-v1.5`，维度定义在 schema 里是 512（`FLOAT_VECTOR dim=512`）。索引用 HNSW 而不是 IVF，是因为 HNSW 在中小规模数据集上查询延迟更低、召回率更高，适合我们这种量级的企业知识库（不是十亿级别的海量数据，IVF 在这种规模下的优势不明显，HNSW 综合表现更好）。`M=16` 是每个节点的邻接边数，越大图越稠密、检索精度越高但内存占用和构建时间也上升；`efConstruction=64` 是建图时候的搜索范围，值越大建图质量越高但越慢——这两个也是采用 Milvus 官方推荐的常见配置，没有专门调优。度量方式用 IP（内积）是因为 bge 系列模型输出的向量通常会做归一化，归一化后的向量用内积等价于余弦相似度，且内积计算比余弦（要额外除模长）更快。

### Q5a：RRF 具体怎么算的

RRF（Reciprocal Rank Fusion）核心思路是不看每路检索的绝对分数（因为 Dense 的相似度分数和 Sparse 的 BM25 分数量纲完全不同，没法直接比大小），只看每个文档在各路结果里的**排名**。公式大致是：对某个文档，它在 Dense 结果里排第几就取 `1/(k+rank_dense)`，在 Sparse 结果里排第几就取 `1/(k+rank_sparse)`，两个值加起来就是这篇文档的最终融合分数，按这个分数重新排序。排名越靠前（rank 越小）贡献分越大，同时出现在两路结果里靠前位置的文档，融合分会明显更高。

### Q5b：为什么用 RRF 不用加权平均分数

因为 Dense 相似度分数和 BM25 分数完全不是一个量纲——Dense 通常是 0~1 之间的余弦/内积值，BM25 分数是没有固定上限的、和词频文档长度相关的打分，直接加权平均等于拿两个不可比的数字硬加，权重系数很难调、还会因文档集不同而漂移。RRF 只依赖排名这个相对顺序信息，天然规避了量纲不一致的问题，是目前混合检索最常用、最稳健的融合方式（业界很多混合检索系统包括 Elasticsearch 的 RRF 都是这个思路）。

### Q5c：k=100 是什么意思

RRF 公式里的 `k`（这里配置的 `ranker_params={"k": 100}`）是一个平滑常数，作用是防止排名靠前的文档分数差异过大、也防止排名靠后的文档分数趋近于 0 时波动过于剧烈——`k` 越大，排名先后对最终融合分的影响就越平缓（分数曲线更平滑），`k` 越小则排名靠前的优势被放大得更明显。100 是一个经验性的常用取值，业界惯用值多在 60~100 这个区间，目前没有针对我们数据集做过专门的敏感性测试来精调这个值。

### Q6a：效果验证

目前主要是人工抽样对比：拿几类典型问题（含精确术语/错误码的、纯语义描述的）分别测单独 Dense、单独 Sparse、混合 RRF 三种方式的检索结果，观察混合检索是否能把两路各自的短板互补上——比如精确术语查询下 Sparse 单独检索能命中但 Dense 单独检索排名靠后的情况，混合后有没有把正确答案排到前面。还没有做严格的量化 A/B 测试（比如构建标注好的 query-doc 相关性数据集去算 NDCG/MRR 提升幅度），这是可以补充的评估工作。

### Q6d：`create_collection()` drop 重建的风险

这个方法目前实现是"如果同名 collection 已存在，先释放、删索引、再 drop、再重建"，这是有损操作，如果对生产环境已有数据的 collection 误调用会导致全量数据丢失。目前这个方法主要是在开发/测试阶段用来重置 schema，生产环境调用前需要人工确认不是正在使用的 collection，这是当前实现里一个需要谨慎使用的地方，理想情况应该加一个环境判断或者二次确认机制。

## 四、核心提醒

RRF 这条问题链（Q5a→Q5b→Q5c）是这段简历里问得最密的地方，必须能讲清楚"为什么排名融合比分数融合稳健"这个核心逻辑。遇到"参数怎么调的/为啥选这个值"类问题，如果是用官方默认值，诚实说是默认值+说明默认值背后的设计考量，别硬编自己调过参。
