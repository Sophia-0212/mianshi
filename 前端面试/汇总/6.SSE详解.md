# 1.基本概念与场景:

## a.什么是SSE？

SSE（**Server-Sent Events**）是一种基于**HTTP协议**的**服务器单向推送**技术。浏览器通过 `EventSource` 对象向服务器发起一个**长连接请求**，服务器保持连接打开，并以**文本流**的形式持续向客户端推送数据，直到主动关闭。

核心特点：

1. **单向通信**：只能**服务器 → 客户端**推送数据，客户端不能通过同一条连接向服务器发消息。
2. **基于HTTP**：**复用现成的HTTP协议**，不需要像WebSocket一样单独升级协议，**兼容性好、易于调试**（浏览器网络面板可直接看到流式内容）。
3. **自动重连**：浏览器原生支持**断线后自动重连**，不需要手写重连逻辑。
4. **纯文本格式**：数据以 `text/event-stream` 的**约定文本格式**传输，天然适合**逐字/逐段推送文本**的场景。

## b.SSE和轮询、WebSocket的区别

| 维度 | 短轮询 | 长轮询 | SSE | WebSocket |
|------|--------|--------|-----|-----------|
| 通信方向 | 单向（客户端主动拉） | 单向（客户端主动拉） | **单向（服务端推）** | **双向** |
| 协议 | HTTP | HTTP | HTTP | 独立协议（ws/wss） |
| 连接数 | 每次请求新建连接 | 每次响应后重建连接 | 一条长连接复用 | 一条长连接复用 |
| 实时性 | 差，有延迟 | 较好 | 好 | 最好 |
| 自动重连 | 无需 | 需手写 | **浏览器原生支持** | 需手写 |
| 数据格式 | 任意 | 任意 | **纯文本，固定格式** | 文本/二进制 |
| 实现复杂度 | 低 | 中 | **低**（浏览器封装好） | 中高 |

## c.为什么AI时代SSE成了高频面试题？

因为**几乎所有大模型对话产品（ChatGPT、Claude、文心一言等）的"打字机效果"底层都是流式传输**，而**SSE是实现这种流式文本推送的最主流方案之一**：

1. 大模型**逐token生成**回复，天然适合**边生成边推送**，而不是等全部生成完再一次性返回（用户体验和首字节时间TTFB都会好很多）。
2. 相比WebSocket，SSE**更轻量**——大模型对话场景通常只需要"服务器推流"，不需要客户端持续双向通信，用WebSocket反而是过度设计。
3. **配合流式接口开发是AI应用工程师的基本功**，所以面试中会重点考察：流式解析、断线处理、性能优化、和WebSocket的选型判断等。

## d.EventSource基本用法

```javascript
// 客户端：建立SSE连接
const eventSource = new EventSource('/api/stream');

// 监听默认message事件（对应 data: 字段）
eventSource.onmessage = (event) => {
  console.log('收到数据:', event.data);
};

// 监听自定义事件（对应 event: 字段）
eventSource.addEventListener('customEvent', (event) => {
  console.log('自定义事件:', event.data);
});

// 连接建立成功
eventSource.onopen = () => {
  console.log('连接已建立');
};

// 错误处理（包括断线，浏览器会自动重连）
eventSource.onerror = (err) => {
  console.error('连接出错:', err);
};

// 主动关闭连接
eventSource.close();
```

# 2.协议与实现细节:

## a.SSE数据格式规范

SSE响应体是**纯文本流**，遵循固定的字段格式，**每条消息以空行 `\n\n` 分隔**：

```
event: message
data: 第一行数据
data: 第二行数据
id: 1
retry: 3000

event: message
data: {"content": "下一条消息"}
id: 2

```

字段说明：

1. **`data:`**：消息的实际内容。**同一条消息可以有多个 `data:` 行**，客户端会用 `\n` 拼接成一个字符串。
2. **`event:`**：自定义事件名，**默认为 `message`**。前端通过 `addEventListener(eventName, ...)` 监听对应事件。
3. **`id:`**：消息的唯一标识，浏览器会记录**最后收到的id**，断线重连时通过请求头 `Last-Event-ID` 带给服务器，方便**断点续传**。
4. **`retry:`**：告诉浏览器**断线重连的间隔时间**（毫秒），覆盖默认重连间隔。
5. **以 `:` 开头的行是注释**，常用作**心跳包**（服务端定期发 `: heartbeat\n\n` 保持连接活跃，客户端不会触发任何事件）。

## b.响应头要求

服务端必须正确设置响应头，否则浏览器不会按SSE协议解析：

```
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache
Connection: keep-alive
```

1. **`Content-Type: text/event-stream`**：**必须项**，告诉浏览器这是SSE流，触发流式解析逻辑。
2. **`Cache-Control: no-cache`**：**避免中间代理或浏览器缓存**流式响应，否则可能导致数据被缓存而不是实时推送。
3. **`Connection: keep-alive`**：保持连接不关闭（HTTP/1.1默认长连接，但显式声明更保险）。
4. 若接口部署在**Nginx等反向代理后面**，还需要关闭代理层的响应缓冲，否则Nginx会**攒够一定数据量或等响应结束才转发**，导致流式效果失效：

```nginx
location /api/stream {
    proxy_pass http://backend;
    proxy_buffering off;      # 关闭响应缓冲，实时转发
    proxy_cache off;
    proxy_set_header Connection '';
    proxy_http_version 1.1;
    chunked_transfer_encoding off;
}
```

## c.服务端如何实现SSE

以Node.js（Express）为例：

```javascript
app.get('/api/stream', (req, res) => {
  res.writeHead(200, {
    'Content-Type': 'text/event-stream',
    'Cache-Control': 'no-cache',
    'Connection': 'keep-alive',
  });

  let count = 0;
  const timer = setInterval(() => {
    count++;
    res.write(`id: ${count}\n`);
    res.write(`data: ${JSON.stringify({ text: `第${count}条消息` })}\n\n`);

    if (count >= 5) {
      clearInterval(timer);
      res.end();
    }
  }, 1000);

  // 客户端断开连接时清理资源，避免定时器泄漏
  req.on('close', () => {
    clearInterval(timer);
  });
});
```

核心要点：

1. **`res.write` 不能 `res.end`**，要持续写入直到主动结束。
2. **每条消息必须以 `\n\n` 结尾**，否则浏览器无法识别消息边界。
3. **必须监听客户端断开事件**（`req.on('close')`），及时清理定时器/流等资源，否则会造成**服务端资源泄漏**。

## d.断线重连机制

1. 浏览器的 `EventSource` **原生支持断线自动重连**，默认间隔约**3秒**（可通过服务端 `retry:` 字段调整）。
2. 重连时，浏览器会自动在请求头带上 **`Last-Event-ID`**，值为**最后一次成功接收的消息的 `id:`**。
3. **服务端应该利用 `Last-Event-ID` 实现断点续传**：判断该id之后的消息是否还需要补发，避免用户重连后丢失中间数据或重复收到已展示的数据。

```javascript
app.get('/api/stream', (req, res) => {
  const lastEventId = req.headers['last-event-id'];
  // 根据 lastEventId 判断从哪里继续推送
});
```

# 3.SSE与WebSocket对比（高频题）:

## a.通信方向的本质区别

- **SSE**：**单向**，只能服务器推送给客户端。如果客户端要发消息，只能**另外发起一个普通HTTP请求**（和SSE连接无关）。
- **WebSocket**：**全双工**，建立连接后客户端和服务器**可以随时互相发消息**。

## b.协议层面区别

- **SSE**：本质是**一个特殊的HTTP响应**（`Content-Type: text/event-stream`），走的还是HTTP协议，**没有单独的协议升级过程**。
- **WebSocket**：先通过HTTP发起 **`Upgrade` 请求完成协议升级握手**，之后**切换为独立的ws/wss协议**，不再是标准HTTP报文格式。

## c.HTTP/1.1连接数限制的坑

**HTTP/1.1下，浏览器对同一域名的并发连接数有限制（Chrome等主流浏览器通常是6个）**，而**SSE的长连接会一直占用一个连接名额**。如果一个页面同时打开多个SSE连接（比如多个标签页访问同一域名，或页面内多处使用SSE），**很容易触发连接数上限，导致后续请求被阻塞**。

解决方案：

1. **升级到HTTP/2**：HTTP/2**多路复用**，同一域名下的多个请求共享一条TCP连接，不再受6个连接数限制。
2. **合并连接**：业务层面**避免同时开多条SSE连接**，尽量共用一条连接分发不同类型的消息（用 `event:` 字段区分）。

## d.技术选型：什么时候用SSE，什么时候用WebSocket？

| 场景 | 推荐方案 | 理由 |
|------|----------|------|
| AI对话流式输出 | **SSE** | 只需服务端推送，天然基于HTTP，实现简单 |
| 消息通知/日志实时推送 | **SSE** | 单向推送场景，无需客户端主动发消息 |
| 在线协作文档、多人实时编辑 | **WebSocket** | 需要双向、低延迟的双向通信 |
| 实时聊天、游戏 | **WebSocket** | 双向、高频、低延迟要求高 |
| 需要传输二进制数据 | **WebSocket** | SSE只支持文本，WebSocket支持二进制帧 |

# 4.AI场景实战（重点）:

## a.ChatGPT/Claude打字机效果如何实现？

本质是：**大模型服务端每生成一小段文本（通常是一个或几个token），就立刻通过流式接口推送给前端；前端每收到一段，就追加渲染到界面上**，从而形成"逐字吐出"的视觉效果。

流程拆解：

1. 客户端发起对话请求（**通常是POST**，带上用户输入的prompt）。
2. 服务端调用大模型API，**以流式模式（stream: true）** 接收模型输出。
3. 服务端**每收到一小段模型输出，就立刻转发给客户端**（可以用SSE格式，也可以是其他自定义的分块文本格式）。
4. 客户端**边接收边拼接边渲染**，形成打字机效果。

## b.为什么大模型API不用原生EventSource，而用fetch+ReadableStream？

这是**面试中最容易被问到的坑**：原生 `EventSource` 有明显限制，**无法直接用于大多数大模型API**：

1. **`EventSource` 只支持GET请求**，而大模型对话接口通常需要**POST**（要传对话历史、参数等复杂请求体），`EventSource` 做不到。
2. **`EventSource` 不支持自定义请求头**（如 `Authorization: Bearer xxx`），而鉴权通常需要在header里带token。
3. **`EventSource` 不支持跨域时携带凭证的精细控制**，灵活性差。

因此实际工程中，**流式对话大多用 `fetch` + `ReadableStream` 手动实现类似SSE的效果**：用 `fetch` 发起POST请求（可自由设置header和body），响应体通过 `response.body.getReader()` 拿到一个可读流，**手动按SSE格式或自定义格式解析**。

## c.手动解析SSE流的核心代码

```javascript
async function streamChat(prompt) {
  const response = await fetch('/api/chat', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': 'Bearer ' + token, // EventSource做不到的自定义header
    },
    body: JSON.stringify({ prompt, stream: true }),
  });

  const reader = response.body.getReader();
  const decoder = new TextDecoder('utf-8');
  let buffer = '';

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;

    // 二进制chunk解码为文本，累加到buffer里
    buffer += decoder.decode(value, { stream: true });

    // 按SSE的消息分隔符 \n\n 切分完整消息
    const parts = buffer.split('\n\n');
    buffer = parts.pop(); // 最后一段可能不完整，留到下次拼接

    for (const part of parts) {
      const line = part.replace(/^data: /, '').trim();
      if (!line || line === '[DONE]') continue;

      try {
        const json = JSON.parse(line);
        appendToUI(json.content); // 追加渲染到界面
      } catch (e) {
        console.error('解析失败:', line, e);
      }
    }
  }
}
```

## d.如何处理JSON分片和不完整chunk？

**网络传输是按字节流分片的，不保证一个 `data:` 消息刚好落在一个chunk边界内**，可能出现：
- 一个chunk里包含**多条完整消息**
- 一个chunk**只包含半条消息**（比如JSON被从中间截断）

处理原则：

1. **维护一个字符串buffer**，每次收到新chunk就**累加到buffer**，而不是直接解析当前chunk。
2. **按分隔符（`\n\n`）切分buffer**，只处理**完整的消息段**，**最后一段不完整的内容留在buffer里，等待下一次chunk拼接**（如上面代码中的 `buffer = parts.pop()`）。
3. **对每条消息单独做 `JSON.parse`**，并**用try/catch兜底**，避免个别消息解析失败导致整个流处理中断。

## e.如何实现停止生成（AbortController）？

大模型对话产品通常都有"停止生成"按钮，本质是**用 `AbortController` 中断fetch请求**：

```javascript
const controller = new AbortController();

fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ prompt }),
  signal: controller.signal, // 绑定abort信号
});

// 用户点击"停止生成"
stopButton.onclick = () => controller.abort();
```

服务端也应监听**客户端断开连接**（如 `req.on('close')`），及时**终止对大模型的调用**，避免浪费算力和产生不必要的费用。

# 5.性能与工程问题:

## a.连接数过多怎么优化？

1. **升级HTTP/2**：解决同域名连接数上限问题（见第3节c）。
2. **合并/复用连接**：业务上避免为每种消息类型单独开一条SSE连接。
3. **限制并发**：如果页面内有多个组件都需要流式数据，考虑**用一个全局连接分发数据**，而不是每个组件各自建连接。

## b.常见内存泄漏场景

1. **忘记调用 `eventSource.close()`**：组件卸载、页面跳转时若不关闭连接，**连接会一直占用资源**，也会持续触发已卸载组件的回调（可能报错或造成内存泄漏）。
2. **服务端未监听客户端断开**：客户端关闭连接后，服务端若没有 `req.on('close')` 清理定时器/流，**服务端资源（定时器、数据库连接、模型调用）会持续泄漏**。
3. **React等框架中忘记在 `useEffect` 里做清理**：

```javascript
useEffect(() => {
  const es = new EventSource('/api/stream');
  es.onmessage = (e) => setData(e.data);

  return () => es.close(); // 组件卸载时必须关闭连接
}, []);
```

## c.移动端/后台标签页保活问题

1. **浏览器后台标签页策略**：Chrome等浏览器对**后台/不活跃标签页**会**限流甚至暂停部分网络活动和定时器**，可能导致SSE连接**推送延迟或被挂起**。
2. **移动端弱网/切后台**：App切到后台或网络切换（WiFi→4G）时，**长连接容易被系统或运营商网关中断**，依赖浏览器的**自动重连机制**加**心跳检测**（见第6节d）来快速恢复。
3. **对于强实时性要求场景**，可以结合 **Page Visibility API** 监听页面前后台切换，**后台时降低心跳频率或暂停非关键连接**，节省资源。

## d.负载均衡下如何保持SSE连接？

1. **粘性会话（Sticky Session）**：SSE是**长连接**，如果后端是多实例部署，**负载均衡器需要保证同一个客户端的请求（包括断线重连）始终路由到同一台服务器**，否则**重连后可能连到没有该会话上下文的实例**，导致数据丢失或状态不一致。
2. 常见方案：**基于Cookie或IP的一致性哈希**做粘性路由，或者将**会话状态外置**（如存到Redis），让任意实例都能处理该连接的重连请求。
3. **网关/代理层超时配置**：确保Nginx、云负载均衡器的**连接超时时间大于业务的正常推送间隔**，否则长时间无数据推送会被中间层**主动断开连接**。

# 6.安全与异常处理:

## a.跨域下SSE的CORS配置

`EventSource` 跨域请求**默认不带凭证（cookie）**，需要显式开启，且服务端要正确配置CORS：

```javascript
// 客户端：显式开启携带凭证
const es = new EventSource('https://api.example.com/stream', {
  withCredentials: true,
});
```

```javascript
// 服务端：CORS响应头配置
res.setHeader('Access-Control-Allow-Origin', 'https://your-frontend.com'); // 不能用 *，配合credentials必须指定具体域名
res.setHeader('Access-Control-Allow-Credentials', 'true');
```

## b.鉴权怎么做？

**核心痛点：原生 `EventSource` 不支持自定义请求头**，常见的 `Authorization: Bearer token` 鉴权方式用不了，实践中常用以下方案：

1. **走Cookie鉴权**：登录后由服务端设置 `HttpOnly` Cookie，`EventSource` 配合 `withCredentials: true` 自动带上cookie，**无需修改header**。
2. **Token放在URL query参数里**：如 `/api/stream?token=xxx`。**缺点是token会出现在日志、浏览器历史、Referer中，安全性较差**，建议**配合短时效token**使用。
3. **改用 `fetch` + `ReadableStream`（见第4节b）**：完全绕开 `EventSource` 的限制，可以自由设置任意header，这也是**大模型对话产品的主流做法**。

## c.错误处理与自动重连策略

1. **`EventSource` 原生自动重连**：出现网络错误时浏览器会**自动按 `retry:` 间隔重新连接**，无需手写重连逻辑，但**服务端返回4xx/5xx等HTTP错误状态码时，浏览器会停止自动重连**，需要业务代码在 `onerror` 里判断并决定是否手动重建连接。
2. **`fetch` 流式方案需要手写重连**：由于绕开了 `EventSource`，**断线检测、重连间隔、最大重试次数等逻辑都要自己实现**，通常结合**指数退避（exponential backoff）**策略，避免网络恢复瞬间大量客户端同时重连造成服务端压力骤增。
3. **区分可重试错误与不可重试错误**：网络中断、超时应重连；**鉴权失败（401）、参数错误（400）等不应无限重连**，应提示用户或终止请求。

## d.心跳检测机制

1. **为什么需要心跳**：长连接在**中间代理、NAT、防火墙**等环节可能因为**长时间无数据传输被判定为"死连接"而静默断开**，客户端却不一定能及时感知。
2. **实现方式**：服务端**定期发送注释行**（如 `: heartbeat\n\n`），这类以 `:` 开头的行**不会触发 `onmessage` 或任何自定义事件**，纯粹用于**保持连接活跃、让客户端能感知连接是否仍然存活**。
3. **客户端配合超时判断**：如果**超过预期心跳间隔仍未收到任何数据（包括心跳）**，可以主动判断连接已失效，**提前触发重连**，而不是被动等待浏览器的默认重连机制。
