# 推理过程可视化 与 工具调用结果渲染（面试口语版）

对应简历表述：
> 设计并实现推理过程（Chain-of-Thought）可视化组件与工具调用（Tool-Use）结果渲染引擎，提升 Agent 决策过程的可解释性

这份文档是拿来对着练的，不是给面试官看的。里面每句话都是可以直接照着说出口的口语，代码贴出来是让你知道自己说的每句话对应哪行代码，别瞎编。**先说清楚一个大前提**：接下来这两块东西，实现方式差别很大，回答的时候千万别混着讲，混了容易被一句话问穿。

## 一、推理过程可视化：其实是两套东西，一套真一套假

### 方案A：`ReasoningSteps`——这个是纯前端演的

文件：[src/components/ChatCards/ReasoningSteps/index.tsx](src/components/ChatCards/ReasoningSteps/index.tsx)

**怎么跟面试官说**：

"这个是给几个固定的任务类型用的，比如用户上传营销资料让AI帮忙搭建账户结构的时候。我们提前写好几条步骤文案，比如'阅读营销资料''分析落地页''理解优化目标'，然后用定时器一条一条往外蹦，每条之间随机等个100到300毫秒，看起来就跟真的在一步步分析一样。等文案播完了，就把内容换成后端真正返回的结果。"

**如果追问"这是真的模型思考过程吗"，直接说**：

"不是，这个跟模型有没有在思考完全没关系，是纯前端做的等待动画，图一个体验好看，用户不会干等着发呆。"

```ts
// src/components/ChatCards/ReasoningSteps/index.tsx
const advanceStep = useCallback(() => {
    if (currentStep < steps.length - 1) {
        setCurrentStep(prev => prev + 1);
    } else if (onComplete) {
        setTimeout(() => { onComplete(); }, completeDelay);
    }
}, [currentStep, steps.length, onComplete, setCurrentStep, completeDelay]);

useEffect(() => {
    if (autoMode && steps.length > 0) {
        const timer = setTimeout(
            () => advanceStep(),
            Math.random() * (maxDelay - minDelay) + minDelay // 100~300ms 随机间隔
        );
        return () => clearTimeout(timer);
    }
}, [autoMode, steps, currentStep, advanceStep, minDelay, maxDelay]);
```

### 方案B：`ThinkingCollapse`——这个是真的，才是简历里CoT可视化说的东西

文件：
- [src/components/AiAssistant/ThinkingPlaceholder.tsx](src/components/AiAssistant/ThinkingPlaceholder.tsx)（占位态，"正在思考…"）
- [src/components/AiAssistant/ThinkingCollapse.tsx](src/components/AiAssistant/ThinkingCollapse.tsx)（可展开收起的思考面板）
- 驱动逻辑：[src/components/AiAssistant/createAshOnMessage.ts](src/components/AiAssistant/createAshOnMessage.ts) 的 `handleAshMessage()`

**怎么跟面试官说**：

"我们用户提问之后，后端大模型不是直接把结果甩出来，中间有个推理过程，这个推理过程是通过SSE流式推给前端的，会推不同事件类型：一种是生命周期事件，告诉你现在系统在检索数据、在分析；还有一种是真正的流式文本事件，就是模型一边生成一边往外吐字。

前端拿到这些流式片段之后，实时拼起来渲染到一个可以展开收起的面板里，默认是展开的，用户能看着文字一点点往外冒，跟打字机效果差不多。等模型这一轮推理完了，给出最终答案了，这个面板会自动收起来，变成一行'思考已完成'，下面接上正式答案。"

**这里有个细节要提一下（面试加分项）**：

"流式片段拼接的时候我们做了个兼容，因为后端有时候返回的是完整全量文本，有时候是增量的片段，我们统一判断一下前缀关系，兼容这两种情况，不会拼重复或者拼丢。"

#### 三个事件各自到底在干什么（完整版，逐个讲清楚）

后端这一次问答，从开始到结束，SSE 通道上会陆陆续续推好几条消息，每条消息都带一个 `event_type` 字段，前端就是靠这个字段来分流处理。三个事件不是并列关系，是**按时间顺序、代表一次问答的三个阶段**：

```
用户提问
   │
   ▼
telos_lifecycle（会出现多次） ── 系统在准备阶段，比如"正在检索数据"
   │
   ▼
telos_sdk_message（会出现多次） ── 真正的模型输出，一个字一个字往外吐
   │
   ▼
telos_done（一次） ── 这轮问答结束，给出最终定稿文本
```

**这三个事件对应到 UI 上的完整体验，串起来是这样的**：

用户发一条消息 → 气泡先显示"正在思考…"（`ThinkingPlaceholder`）→ 期间如果收到 `telos_lifecycle`，把这些生命周期提示滚动展示出来 → 一旦 `telos_sdk_message` 开始推送，切换成 `ThinkingCollapse` 折叠面板，文字一点点往外冒（这期间 `telos_lifecycle` 即使再来也会被丢弃）→ 收到 `telos_done`，拿到最终定稿文本，折叠面板自动收起，下方展示正式答案。

**如果面试官问"这三个事件是你们自己定义的协议吗"**：

"不是，这是后端一个叫 telos 的 Agent 执行框架 / SDK 自带的事件命名，前端只是按这三个 `event_type` 分支处理，具体这三个阶段后端内部是怎么划分的、telos 这套框架的设计原理，不是我们前端负责的部分，我们只保证按这个约定的协议正确解析和渲染。"

三段事件分发逻辑（精简版，完整解释见上面）：

```ts
// src/components/AiAssistant/createAshOnMessage.ts
if (eventType === 'telos_lifecycle') {
    if (hasStreamReplyStarted) { return; }
    const texts = getOutputMessageTexts(data);
    const text = texts.join('\n').trim();
    if (text) { appendStreamThinkingStep(text, 'lifecycle', data?.stage); }
    return;
}

if (eventType === 'telos_sdk_message') {
    if (sdkMessageType !== 'stream_event') { return; }
    const texts = getOutputMessageTexts(data);
    const text = texts.join('');
    if (!replyFrom) { replyFrom = getReplyFrom(data); }
    if (text) { appendStreamReplyText(text); }
    return;
}

if (eventType === 'telos_done') {
    const doneText = getOutputMessageTexts(data).join('') || getOutputLlmText(data);
    if (doneText) { doneReplyText = doneText; }
    // ...
}
```

增量拼接兼容逻辑（就是上面说的"兼容全量和增量"那段）：

```ts
// src/components/AiAssistant/createAshOnMessage.ts
const appendStreamReplyText = (text: string) => {
    if (!text) { return; }
    if (text.startsWith(streamReplyText)) {
        streamReplyText = text; // 后端返回的是累积全量文本
    } else if (!streamReplyText.endsWith(text)) {
        streamReplyText += text; // 后端返回的是增量片段
    }
    thinkingText = streamReplyText;
    hasStreamReplyStarted = true;
    if (msg && !('error' in msg)) {
        if (canShowThinking()) {
            aiChatInstance.updateMessage(
                msg.id,
                replyFrom === 'keyue'
                    ? createMarkdownContent(streamReplyText, replyFrom, true)
                    : createThinkingCollapseContent(streamReplyText, undefined, replyFrom, true),
                {isUpdating: true}
            );
        } else {
            aiChatInstance.updateMessage(msg.id, createMarkdownContent(streamReplyText, replyFrom, true), {isUpdating: true});
        }
    }
};
```

折叠面板本身，流结束自动收起：

```tsx
// src/components/AiAssistant/ThinkingCollapse.tsx
function ThinkingCollapse({thinkingText, answerText, replyFrom, isStreaming}: ThinkingCollapseProps) {
    const [expanded, setExpanded] = useState(!!isStreaming);

    useEffect(() => {
        if (!isStreaming) { setExpanded(false); } // 流结束自动收起
    }, [isStreaming]);

    return (
        <div className={`thinking-collapse${isStreaming ? ' thinking-collapse-streaming' : ''}`}>
            <div className="thinking-collapse-header" onClick={() => setExpanded(v => !v)}>
                <span className="thinking-collapse-label">{isStreaming ? '思考中…' : '思考已完成'}</span>
                {expanded ? <IconChevronUp /> : <IconChevronDown />}
            </div>
            <div className="thinking-collapse-body" style={expanded ? undefined : {display: 'none'}}>
                <MarkdownRenderer content={thinkingText} isStreaming={isStreaming} />
            </div>
            {!isStreaming && answerText && (
                <div className="thinking-collapse-answer">
                    <MarkdownRenderer content={answerText} replyFrom={replyFrom} />
                </div>
            )}
        </div>
    );
}
```

**还有个小分支要知道**：客服工单那种场景（`replyFrom === 'keyue'`），不走这个折叠面板，直接用普通Markdown展示，因为那种场景不需要看"思考过程"。这个如果被问到就说一下，显得你对细节场景也清楚。

**最后必须自己心里明白的一点**：

"我们这个思考过程展示，说白了就是把模型中间吐出来的一段文字，原样用Markdown渲染出来，并没有对这段话做结构化拆解，比如说识别出'第一步做了什么、第二步做了什么'这种边界。所以严格来讲，这是'流式中间文本的展示'，比一些产品里做的那种结构化、带步骤编号的CoT展示要浅一层。这个我是清楚的，所以不会往简历里加太多不实的细节。"

## 二、工具调用结果渲染：`ToolTaskRenderer`

文件：[src/components/AiAssistant/ToolTaskRenderer.tsx](src/components/AiAssistant/ToolTaskRenderer.tsx)

**怎么跟面试官说**：

"这个场景是用户遇到问题来问诊断助手，比如说账户消费突然下降了，后端AI分析完之后，判断这个问题应该交给一个叫'排查兔'的内部工具平台去处理，会返回一个结构化的数据，告诉前端识别到了什么问题、需要传什么参数。前端拿到这个数据之后，去判断能不能定位到具体问题类型：能定位到，就把这个第三方诊断工具用iframe嵌到对话气泡里面，用户不用跳出对话就能看到诊断工具；定位不到，就引导用户自己去那个平台手动查。底部还会根据用户角色，展示不同的引导文案，比如内部员工能看到'发起工单'的入口，普通用户看到的是'找顾问咨询'。"

**如果追问"这跟OpenAI说的function calling是一个东西吗"，直接说**：

"不完全一样。OpenAI那套function calling是有个通用的schema定义，模型自己决定调哪个函数、传什么参数，是个比较通用的协议。我们这个是百度内部一个具体工具平台的私有数据格式，前端拿到这个数据只是判断走iframe还是走引导文案，没有做那种'多个工具里选一个、或者同时调多个工具'的调度逻辑，就是针对这一个诊断场景做的定制渲染。所以严格讲，'渲染引擎'这个词说大了，应该说是'渲染组件'更准确。"

判断走不走这条链路的解析逻辑：

```ts
// src/components/AiAssistant/createAshOnMessage.ts
export function parseToolQuestionPayload(text?: string): ToolQuestionPayload | null {
    if (!text) { return null; }
    try {
        const payload = JSON.parse(text);
        if (!Array.isArray(payload?.categories)) { return null; }
        const cat = payload.categories.find((c: any) => c.categoryId === 'tool_question');
        if (!cat || resolveDiagnosisTabByQuestionName(cat.questionName)) { return null; }
        return {
            questionId: Number(cat.questionId),
            questionName: String(cat.questionName || cat.categoryName || ''),
            params: typeof payload.params === 'object' && payload.params !== null ? payload.params : undefined,
        };
    } catch {
        return null;
    }
}
```

```tsx
// src/components/AiAssistant/ToolTaskRenderer.tsx
function ToolTaskRenderer({messageId, categories, params}: ToolTaskRendererProps) {
    const questionName = useMemo(() => categories?.[0]?.questionName || '', [categories]);
    const {path, ticketPath} = useMemo(
        () => getPageConfig(categories) || {path: '', ticketPath: 'ticket/submit'},
        [categories]
    );
    const iframeSrc = useMemo(() => getToolUrl(path || '', {'chat_id': messageId}), [path, messageId]);

    const enrichedParams = useMemo(() => {
        const uid = getUserId();
        return uid ? {...params, userId: String(uid)} : params;
    }, [params]);

    // questionName 为空 → 引导去"排查兔"平台手动排查
    // questionName 有值 → 展示已识别到的问题，并把第三方诊断工具用 iframe 嵌进气泡
    return (
        <div className="ai-assistant-ticket-submit">
            <p>{questionName ? `识别到『${questionName}』问题` : '暂不支持该类型问题的排查'}</p>
            <ToolIframe id={messageId} src={iframeSrc} params={enrichedParams} />
            <p>{getIsManageUser() ? /* 发起工单+查看工单 */ null : /* 咨询顾问 */ null}</p>
        </div>
    );
}
```

配套还有个提交工单的表单组件`TicketSubmitRenderer`（对应`createAshOnMessage.ts`里的`createTicketSubmitContent`），可以当作这条链路的下一步动作，问到了就补一句："识别到问题之后，用户如果还想深入排查，可以走到提交工单这一步，这个是另一个组件做的表单化渲染。"

## 三、几个大概率会被问到的问题，答案先想好

**问："你说的CoT可视化，到底是模型真吐的还是你们前端演的？"**

"两种都有，我们项目里是分开设计的。针对几个固定的任务类型，比如搭建账户结构，我们是前端预置文案配合定时器模拟一个循序播放的效果，纯粹是等待体验的动画；针对通用对话场景，我们是真的解析后端SSE推的流式事件，把模型实时吐的中间文本渲染出来。这两个我不会混着说，简历上如果要写得更准确一点，我会拆成'预置任务分解动效'和'流式中间推理文本展示'两点分开讲。"

**问："工具调用结果渲染引擎，具体解析的是什么协议？"**

"是我们百度内部一个诊断工具平台自己定义的数据格式，不是行业通用的tool schema，没有做通用的多工具调度，就是针对这一个场景做的定制化渲染，'引擎'这个词严格讲是我说大了，准确讲是个'渲染组件'。"

**问："这些是你独立设计的吗？"**

"如果不是很确定自己当时是不是主导了这块的设计，就老实说清楚自己具体负责的部分，比如'我负责的是折叠面板的交互和流式增量渲染这部分的前端实现'，别把后端事件协议设计这种自己没参与的部分也揽到自己身上，被问设计动机的时候答不上来更麻烦。"

## 简历表述，建议改成这样

原句"可解释性"这个词有点大，用在"折叠展示中间推理文本"这一点上问题不大，别覆盖到工具渲染那部分（工具渲染更多是"告诉用户下一步该干什么"，跟"可解释性"关系不大）。可以考虑改成：

> 基于 SSE 流式事件解析实现大模型中间推理文本的折叠展示（思考中/思考完成态切换、流式增量更新），并支持特定任务卡片的分步骤加载动效，提升等待过程的可感知性；同时实现外部诊断工具结果的对话内嵌渲染（iframe 化 + 工单提交表单联动），支撑智能助手工具调用场景的闭环体验。

这版更长，但每个词都对得上代码，深挖不会露怯。
