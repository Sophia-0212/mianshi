# K8s 高频面试题 Top 10

## 1. Pod、Deployment、Service 区别与关系？

- **Pod**：k8s最小调度单元，一个或多个容器共享网络namespace和存储卷
- **Deployment**：管理Pod的副本数、滚动更新、回滚，保证指定数量的Pod副本持续运行
- **Service**：为一组Pod提供稳定的访问入口（虚拟IP+DNS名），屏蔽Pod的动态变化

关系：Deployment 创建并维护多个 Pod 副本 → Service 通过 label selector 关联这些 Pod，对外提供统一入口。Pod会随调度、重启变化IP，Service地址不变。

## 2. K8s 架构组件有哪些，各自作用？

| 组件 | 位置 | 作用 |
|---|---|---|
| kube-apiserver | Master | 集群唯一入口，处理REST请求，写入etcd |
| etcd | Master | 分布式KV存储，保存集群所有状态数据 |
| kube-scheduler | Master | 根据资源、亲和性等策略为Pod选择合适节点 |
| kube-controller-manager | Master | 运行各类控制器（Deployment/Node/Job等），驱动实际状态趋近期望状态 |
| kubelet | Node | 与apiserver通信，管理本节点Pod生命周期 |
| kube-proxy | Node | 维护节点网络规则，实现Service的负载均衡转发 |
| container runtime | Node | 实际运行容器（containerd/CRI-O等） |

## 3. Service 类型有哪些，区别是什么？

| 类型 | 说明 | 使用场景 |
|---|---|---|
| ClusterIP | 默认类型，仅集群内部可访问的虚拟IP | 内部服务间调用 |
| NodePort | 在每个Node上开放固定端口，外部通过`NodeIP:Port`访问 | 测试环境/无云LB时对外暴露 |
| LoadBalancer | 依赖云厂商LB，自动分配外部IP | 生产环境对外暴露 |
| ExternalName | 通过DNS CNAME映射到外部地址，不分配ClusterIP | 访问集群外部服务（如外部数据库） |

## 4. Pod 调度策略有哪些？

- **nodeSelector**：简单的节点标签匹配
- **节点亲和性 nodeAffinity**：更灵活的节点选择（required硬限制/preferred软偏好）
- **Pod亲和性/反亲和性 podAffinity/podAntiAffinity**：控制Pod与其他Pod的共置或分散
- **污点与容忍 Taints & Tolerations**：Node打污点拒绝Pod调度，Pod声明容忍度才能调度上去（如master节点默认污点）
- **资源请求与限制 requests/limits**：调度器依据requests判断节点是否有足够资源容纳

## 5. ConfigMap 与 Secret 区别及使用场景？

| 对比项 | ConfigMap | Secret |
|---|---|---|
| 存储内容 | 明文配置（环境变量、配置文件） | 敏感信息（密码、Token、证书） |
| 编码方式 | 明文 | Base64编码（非加密，需配合RBAC/加密插件） |
| etcd存储 | 明文存储 | 默认明文存储，可开启etcd静态加密 |
| 使用场景 | 应用配置、启动参数 | 数据库密码、API密钥、TLS证书 |

两者都可通过环境变量或Volume方式挂载进Pod。

## 6. PV、PVC、StorageClass 关系？

- **PV（PersistentVolume）**：集群级别的存储资源，由管理员创建或动态供给，与具体存储介质（NFS/云盘等）对应
- **PVC（PersistentVolumeClaim）**：用户对存储的申请（声明需要多大、什么访问模式），类似"申请书"
- **StorageClass**：定义存储的"类别"（如SSD/HDD、云厂商存储类型），支持**动态供给**——PVC提交后自动创建匹配的PV，无需管理员手动预先创建PV

流程：用户创建PVC → 指定StorageClass → 触发动态供给自动创建PV → PVC与PV绑定 → Pod通过PVC挂载存储。

## 7. 滚动更新与回滚机制？

Deployment 默认使用 **RollingUpdate** 策略：

```yaml
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%       # 更新过程中最多可超出期望副本数的比例/数量
    maxUnavailable: 25% # 更新过程中最多允许不可用的比例/数量
```

逐步用新版本Pod替换旧版本Pod，保证服务不中断。回滚使用：

```bash
kubectl rollout undo deployment/xxx           # 回滚到上一版本
kubectl rollout undo deployment/xxx --to-revision=2  # 回滚到指定版本
kubectl rollout history deployment/xxx         # 查看历史版本
```

k8s通过ReplicaSet记录每次修订版本（revision），回滚本质是切换到旧的ReplicaSet。

## 8. 健康检查机制有哪几种？

| Probe | 作用 | 失败后行为 |
|---|---|---|
| livenessProbe | 判断容器是否存活 | 失败则kubelet重启容器 |
| readinessProbe | 判断容器是否准备好接收流量 | 失败则从Service Endpoints中移除，不重启 |
| startupProbe | 判断慢启动应用是否启动完成 | 失败则杀掉容器重启；成功前其他probe不生效，避免慢启动应用被误杀 |

检测方式支持：`httpGet`、`tcpSocket`、`exec`命令。

## 9. K8s 网络模型是怎样的？

三大网络问题：

- **容器间通信**：同Pod内容器共享network namespace，通过`localhost`直接通信
- **Pod间通信**：依赖CNI插件（Calico/Flannel/Cilium等）实现，要求所有Pod IP在集群内**扁平可达**，无需NAT
- **Service负载均衡**：kube-proxy监听apiserver的Service/Endpoints变化，在节点上维护iptables/IPVS规则，将访问Service的流量按规则转发到后端Pod（也可用Endpoints实现基础的负载均衡）

对外访问还可用 **Ingress**：七层路由规则，统一入口按域名/路径转发到不同Service，比NodePort/LoadBalancer更省资源、更灵活。

## 10. HPA 自动扩缩容原理？

**HPA（Horizontal Pod Autoscaler）** 根据指标自动调整Deployment/StatefulSet的Pod副本数：

```bash
kubectl autoscale deployment xxx --cpu-percent=50 --min=2 --max=10
```

原理：

1. metrics-server（或自定义/外部指标源）定期采集Pod的CPU/内存/自定义指标
2. HPA Controller 按周期（默认15s）从metrics API拉取数据，与目标值对比
3. 计算期望副本数：`期望副本数 = 当前副本数 × (当前指标值 / 目标指标值)`
4. 更新Deployment的replicas字段，触发扩缩容

支持基于CPU/内存的资源指标，也支持QPS等自定义指标（需配合Prometheus Adapter等）。
