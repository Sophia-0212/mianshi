# Redis 面试速记

## 1. Redis 是什么？为什么快？

Redis（Remote Dictionary Server）是基于内存的开源 Key-Value 数据库，也常用于缓存、计数器、排行榜、分布式锁、Session 和消息队列。

高性能原因：

- 内存读写，避免磁盘 I/O。
- 核心命令单线程执行，减少锁竞争和线程切换。
- I/O 多路复用，一个线程管理大量连接。
- 数据结构和底层编码经过优化。
- C 语言实现，运行开销低。

“单线程”只指命令执行主流程；持久化、网络 I/O 等可能使用其他线程。慢命令、大 Key、复杂 Lua 仍会阻塞主线程。

## 2. 数据类型与应用

| 类型 | 特点 | 常见场景 |
|---|---|---|
| String | 字符串、数字、二进制；最大 512 MB | 缓存、计数器、Token、锁 |
| Hash | field-value；小数据通常用 listpack，大数据转 hashtable | 用户、商品等对象 |
| List | 两端操作；底层通常是 quicklist | 队列、栈、简单消息 |
| Set | 无序、不重复；支持交并差集 | 标签、好友关系、黑白名单 |
| ZSet | member + score；dict 快速定位，skiplist 排序 | 排行榜、延迟队列 |
| Bitmap | String 的 bit 操作 | 签到、活跃状态 |
| HyperLogLog | 近似统计基数，标准误差约 0.81% | UV 统计 |
| Geo | 基于 geohash 和 ZSet | 附近门店、附近的人 |
| Stream | 消息 ID、消费组、ACK、Pending List | 轻量消息队列 |

ZSet 使用 `dict + skiplist`：dict 按 member 快速查找，skiplist 按 score 排序并支持范围查询。跳表实现简单、范围查询友好，因此没有采用红黑树。

### Bitmap 与 HyperLogLog

- Bitmap：精确记录和统计，但 offset 设计不当会浪费空间。
- HyperLogLog：只统计数量，内存固定且很小，有误差，不能反查元素。

### 布隆过滤器

由位数组和多个哈希函数组成。查询结果是“可能存在”或“一定不存在”，存在误判，不适合直接删除。常用于缓存穿透防护、黑名单和去重。

## 3. Redis 与 MySQL

| 维度 | Redis | MySQL（InnoDB） |
|---|---|---|
| 存储 | 内存为主，可持久化 | 磁盘为主，内存做缓存 |
| 模型 | Key-Value、多种结构 | 关系表、SQL |
| 事务 | 命令批量执行，不支持回滚 | ACID，支持回滚 |
| 场景 | 缓存、计数、排行榜、锁 | 权威业务数据、复杂查询 |

常见方案：MySQL 保存权威数据，Redis 保存缓存副本；缓存丢失后从 MySQL 重建。

## 4. 持久化：RDB 与 AOF

| 对比 | RDB | AOF |
|---|---|---|
| 内容 | 某一时刻的快照 | 写命令日志 |
| 文件 | 小 | 大 |
| 恢复 | 快 | 相对慢 |
| 丢失风险 | 可能丢最近一次快照后的数据 | 取决于刷盘策略 |
| 性能 | `bgsave` 对主线程影响较小 | 写日志有额外 I/O |

RDB 适合备份，AOF 更利于减少数据丢失。两者同时开启时，Redis 通常优先加载 AOF；混合持久化用快照加增量日志恢复。

## 5. 缓存三大问题

### 缓存穿透

查询的数据缓存没有、数据库也没有，请求持续打到数据库。

解决：

- 校验参数，拒绝非法请求。
- 缓存空值，并设置短 TTL。
- 使用布隆过滤器提前拦截不存在的 Key。

### 缓存击穿

热点 Key 过期瞬间，大量并发请求同时查询数据库。

解决：

- 热点数据不过期或提前预热。
- 缓存未命中时加互斥锁，只允许一个请求重建缓存。
- 设置逻辑过期，后台异步刷新。

### 缓存雪崩

大量 Key 同时过期，或 Redis 整体故障，导致请求集中访问数据库。

解决：

- TTL 加随机值，错开过期时间。
- 主从、哨兵或 Cluster 提高可用性。
- 限流、熔断、降级，避免请求全部穿透。
- 核心热点数据预热或不过期。

记忆：**穿透是查不存在，击穿是热点失效，雪崩是大量失效或整体故障。**

## 6. Redis 分布式锁

### 基础实现

```text
获取：SET lock:key UUID NX EX 30
释放：Lua 判断 value == UUID 后 DEL
```

要求：互斥、只能由持有者释放、避免死锁、具备可用性；是否可重入取决于实现。

不能拆成 `SETNX + EXPIRE`，否则两条命令之间宕机，会产生永不过期的锁。释放必须使用 Lua 保证“校验并删除”原子执行，防止误删其他线程的新锁。

### 常见问题

- 锁过期但任务未完成：使用看门狗续期，例如 Redisson。
- Redis 单点故障：使用高可用部署；但主从切换存在锁状态丢失风险，需结合业务容忍度评估。
- 可重入、续期、等待和公平性：生产环境优先使用 Redisson 等成熟实现，避免手写漏洞。

## 7. 集群与高可用

### 主从复制

Master 负责写，Replica 负责读。首次同步通常传输 RDB，之后同步复制期间积累的写命令。可读写分离，但不分片，主节点故障通常需要额外故障转移机制。

### 哨兵（Sentinel）

监控主从、发现故障、选举新主并通知客户端。解决自动故障转移，但仍不负责数据分片。

### Redis Cluster

把 Key 映射到 **16384 个哈希槽**，槽分配到多个主节点；主节点配副本，支持分片和故障转移，突破单机内存与并发限制。

## 8. 过期键与内存淘汰

过期键采用三种机制配合：

- 惰性删除：访问时发现过期再删。
- 定期删除：周期性抽样删除。
- 内存淘汰：达到 `maxmemory` 后按策略淘汰。

常见淘汰策略：

- `allkeys-lru`：所有 Key 中淘汰最近最少使用者，缓存场景常用。
- `volatile-lru`：只在设置 TTL 的 Key 中执行 LRU。
- `volatile-ttl`：优先淘汰剩余 TTL 较短的 Key。
- `noeviction`：不淘汰，写入失败。

## 9. Redis 事务与 Lua

事务命令：

- `MULTI`：开始排队。
- `EXEC`：执行队列。
- `DISCARD`：取消队列。

Redis 事务是弱事务：命令按顺序执行，但不支持回滚；执行中某条命令失败，其他命令仍可能执行。单条命令本身通常具有原子性。

Lua 脚本在 Redis 内部连续执行，可将多个操作组合成原子操作，适合锁释放、库存校验等场景，但脚本不能长时间运行。

## 10. 常见追问

### 缓存一致性怎么保证？

常见做法是“先更新数据库，再删除缓存”；删除失败时通过重试、消息队列或定时补偿。对强一致要求高的场景，不能只依赖缓存。

### BigKey 和 HotKey 怎么处理？

- BigKey：拆分数据、限制 Value 大小，避免一次性读取或删除；删除大 Key 可使用渐进式删除。
- HotKey：本地缓存、热点副本、请求合并、限流或拆分 Key，避免单节点被打满。

### Redis 为什么不适合复杂查询？

Redis 以 Key 和内置数据结构为中心，缺少 MySQL 的多表关联、复杂聚合和完整事务能力；复杂查询应交给关系数据库或搜索引擎。

## 11. 一分钟面试回答

Redis 是基于内存的高性能 Key-Value 数据库，常用于缓存、分布式锁、计数、排行榜和消息处理。它快的原因是内存操作、单线程命令执行、I/O 多路复用和高效数据结构。项目中重点关注缓存穿透、击穿、雪崩，使用空值缓存、布隆过滤器、互斥锁、随机 TTL、限流降级等方案；分布式锁使用 `SET NX EX` 加 Lua 原子释放，生产环境优先使用成熟客户端。Redis 通过 RDB/AOF 持久化，通过主从、哨兵或 Cluster 实现高可用和扩展。
