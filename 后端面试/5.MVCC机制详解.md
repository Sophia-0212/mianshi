### **数据库中的 MVCC 机制详解**

**MVCC（Multi-Version Concurrency Control，多版本并发控制）** 是一种通过维护数据的多个版本来实现高并发访问的机制，核心目标是 **解决读写冲突**，减少锁竞争，提升数据库的并发性能。以下是 MVCC 的深度解析：

---

### **1. MVCC 的核心思想**

- **数据多版本**：每个数据行维护多个历史版本，不同事务根据其 **可见性规则** 读取合适的版本。

- **无锁读**：读操作不阻塞写操作，写操作不阻塞读操作（写操作仍需加锁）。

- **快照隔离**：事务看到的是一个一致性的数据快照，而非实时数据。

---

### **2. MVCC 的实现原理（以 MySQL InnoDB 为例）**

#### **(1) 数据版本管理**

- **隐藏字段**：
每行数据包含两个隐藏字段：

  - `DB_TRX_ID（6字节）`：表示最后一次插入或更新该行的事务 id。此外，`delete` 操作在内部被视为更新，只不过会在记录头 `Record header` 中的 `deleted_flag` 字段将其标记为已删除

  - `DB_ROLL_PTR（7字节）` 回滚指针，指向该行的 `undo log` 。如果该行未被更新，则为空

  - `DB_ROW_ID（6字节）`：如果没有设置主键且该表没有唯一非空索引时，`InnoDB` 会使用该 id 来生成聚簇索引

#### **(2) Read View（读视图）**

- **作用**：决定事务能看到哪些版本的数据。

- **关键属性**：

|字段名|作用|可见性规则中的逻辑||
|-|-|-|-|
|m_low_limit_id|当前系统最大事务 ID +1（即下一个将被分配的事务 ID）|高水位线：DB_TRX_ID ≥ m_low_limit_id 的数据版本对当前事务不可见。|DB_TRX_ID 处于 m_low_limit_id 和 m_up_limit_id 间|
|m_up_limit_id|活跃事务列表中的最小事务 ID（若列表为空，则等于 m_low_limit_id）|低水位线：DB_TRX_ID < m_up_limit_id 的数据版本对当前事务可见。||
|m_ids|Read View 创建时活跃的未提交事务 ID 列表（不包括已提交和自身事务）|事务 ID 在 m_ids 中且未提交的数据版本对当前事务不可见。||
|m_creator_trx_id|创建该 Read View 的事务自身的事务 ID|允许事务看到自己修改的数据版本（即使未提交）。||

---

### **3. MVCC 如何支持不同隔离级别？**

|隔离级别|MVCC 行为|
|-|-|
|**读未提交**|不使用 MVCC，直接读取最新数据（可能脏读）。|
|**读已提交**|每次查询生成新的 Read View，读取已提交的最新版本（解决脏读）。|
|**可重复读**|事务首次查询生成 Read View，后续沿用同一视图（解决不可重复读）。|
|**串行化**|不使用 MVCC，退化为基于锁的并发控制。|

---

### **4. MVCC 的完整工作流程**

#### **场景示例**

- **事务A（事务ID=100）**：

  ```SQL
BEGIN;
UPDATE users SET balance = 200 WHERE id = 1;  -- 生成新版本，DB_TRX_ID=100
COMMIT;
```


- **事务B（事务ID=101）**：

  ```SQL
BEGIN;
SELECT balance FROM users WHERE id = 1;  -- 生成 Read View
-- 事务A提交后
SELECT balance FROM users WHERE id = 1;  -- 结果取决于隔离级别
COMMIT;
```


#### **可重复读（RR）隔离级别下的流程**

1. 事务B首次查询时生成 Read View：

  - `trx_ids` = [活跃事务列表]

  - `low_limit_id` = 102（假设当前最大事务ID为101）

  - `up_limit_id` = 活跃事务最小ID（如100）

2. 遍历版本链，找到 `DB_TRX_ID=100` 的版本（已提交），返回 `balance=200`。

3. 事务A提交后，事务B再次查询仍使用同一 Read View，结果不变。

---

### **5. MVCC 的优缺点**

|**优点**|**缺点**|
|-|-|
|高并发：读写互不阻塞|存储开销：需维护多版本数据和 undo 日志|
|避免脏读、不可重复读|历史版本清理需额外机制（如 purge 线程）|
|支持快照隔离|写操作仍需加锁（如行锁、间隙锁）|

---

### **6. MVCC 与锁的协作**

- **写操作加锁**：

  - INSERT/UPDATE/DELETE 操作需加排他锁（X锁），确保写操作的原子性。

- **读操作无锁**：

  - 通过 MVCC 读取历史版本，无需加共享锁（S锁）。

- **间隙锁防幻读**：

  - 在可重复读级别，MVCC 结合间隙锁避免幻读。

---

### **7. 关键实现细节**

#### **(1) Undo 日志的作用**

- 存储旧版本数据，用于构建版本链和事务回滚。

- 事务提交后，undo 日志不会立即删除，需等待无活跃事务依赖时由 purge 线程清理。

#### **(2) Read View 的生成时机**

- **读已提交（RC）**：每次查询生成新 Read View。

- **可重复读（RR）**：事务首次查询生成 Read View，后续复用。

#### **(3) 版本清理（Purge 机制）**

- 后台线程定期清理不再需要的 undo 日志和旧数据版本。

- 清理条件：无活跃事务依赖该版本。

---

### **8. 总结**

- **MVCC 是数据库高并发的基石**：通过多版本和快照隔离，实现读写非阻塞。

- **核心组件**：版本链、Read View、undo 日志。

- **隔离级别适配**：不同级别通过调整 Read View 生成策略和锁机制实现数据一致性。

- **权衡**：在存储开销、并发性能和数据一致性之间取得平衡。

理解 MVCC 的机制，有助于优化事务设计、合理选择隔离级别，并诊断并发问题。
