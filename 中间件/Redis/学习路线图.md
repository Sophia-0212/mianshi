# Redis 学习路线图

## 总目标

从“会用 Redis”到能够解释：

```text
数据结构
→ 底层实现
→ 持久化
→ 过期与淘汰
→ 高可用与集群
→ 缓存问题
→ 分布式锁
→ 高并发优化
```

## 第 1 阶段：建立直觉，1 天

### 学习内容

- Redis 解决什么问题
- Redis 与 MySQL 的区别
- Redis 请求的基本流程
- 内存访问为什么快
- 单线程模型的含义

### 必须理解

```text
应用 → Redis → 返回结果
       ↓ 未命中
      MySQL → 回写 Redis
```

### 输出

能够回答：

- 为什么使用 Redis？
- Redis 为什么比 MySQL 快？
- Redis 适合存什么，不适合存什么？

## 第 2 阶段：数据结构，2 天

### 学习顺序

1. String
2. Hash
3. List
4. Set
5. ZSet
6. Bitmap
7. Stream

### 学习方法

每种结构回答四个问题：

1. 存储模型是什么？
2. 常用命令是什么？
3. 时间复杂度是多少？
4. 业务中如何使用？

### 典型场景

| 结构 | 典型场景 |
|---|---|
| String | 缓存、计数器、分布式锁 |
| Hash | 用户信息、商品信息 |
| List | 简单队列、消息列表 |
| Set | 标签、共同关注、去重 |
| ZSet | 排行榜、延迟队列 |
| Bitmap | 签到、活跃统计 |
| Stream | 消息流、消费组 |

### 实践

- 访问量计数器
- 用户签到
- 商品排行榜
- 简单消息队列

## 第 3 阶段：底层结构，3 天

### 学习内容

- SDS：Redis 字符串实现
- 哈希表：Hash 的底层基础
- 双向链表：List 的基础结构
- 跳表：ZSet 的有序索引
- 压缩列表 / listpack：节省内存的紧凑结构
- Intset：小整数集合
- 编码转换条件

### 重点理解

Redis 的一个逻辑结构，底层可能根据数据规模和类型选择不同实现。

例如：

```text
ZSet
├── dict：快速查成员分值
└── skiplist：按分值排序和范围查询
```

### 必须能回答

- 跳表是什么？为什么不用红黑树？
- SDS 比 C 字符串好在哪里？
- Redis 为什么需要多种底层编码？
- listpack 什么时候会导致性能问题？

## 第 4 阶段：持久化，2 天

### RDB

定期生成某一时刻的内存快照：

```text
内存数据 → RDB 文件
```

优点：文件紧凑、恢复快。  
缺点：两次快照之间的数据可能丢失。

### AOF

记录写命令：

```text
SET k v → AOF 文件
```

优点：数据更完整。  
缺点：文件更大，恢复更慢。

### 混合持久化

使用 RDB 保存快照，再用 AOF 保存增量命令，兼顾恢复速度和数据完整性。

### 必须能回答

- RDB 和 AOF 如何选择？
- Redis 宕机最多可能丢多少数据？
- AOF 重写解决什么问题？
- `fsync always`、`everysec`、`no` 有什么区别？

### 实践

- 配置 RDB 和 AOF
- 模拟宕机恢复
- 对比恢复速度和数据丢失量

## 第 5 阶段：过期删除与淘汰，1 天

### 过期删除

Redis 不会在 Key 到期的瞬间立即删除，主要采用：

- 惰性删除：访问 Key 时检查并删除。
- 定期删除：周期性抽样检查过期 Key。

### 内存淘汰

内存达到上限后，根据策略删除 Key：

- `noeviction`
- `allkeys-lru`
- `allkeys-lfu`
- `volatile-lru`
- `volatile-ttl`
- `allkeys-random`

### 必须区分

```text
过期删除：Key 到期后的清理机制
内存淘汰：内存不足时的清理机制
```

### 实践

- 配置 `maxmemory`
- 对比 LRU 和 LFU
- 观察淘汰 Key 和命中率变化

## 第 6 阶段：主从、哨兵、集群，3 天

### 主从复制

```text
Master
  ↓ 复制
Replica
```

解决读扩展和数据备份问题，但主节点故障时不会自动完成高可用切换。

### 哨兵

负责：

- 监控节点
- 判断主节点故障
- 自动选举新主节点
- 通知客户端

### Cluster

通过哈希槽分片：

```text
16384 个槽位 → 多个主节点
```

同一个 Key 根据哈希槽定位到对应节点。

### 必须能回答

- 主从复制是同步还是异步？
- 哨兵和 Cluster 有什么区别？
- Redis Cluster 为什么是 16384 个槽？
- 跨槽操作为什么失败？
- 如何保证故障转移期间业务可用？

### 实践

- 搭建主从集群
- 模拟主节点宕机
- 观察哨兵故障转移
- 测试 Cluster 的分片和跨槽限制

## 第 7 阶段：缓存问题，3 天

### 缓存穿透

查询不存在的数据，请求直接打到数据库。

解决：

- 布隆过滤器
- 空值缓存
- 参数校验

### 缓存击穿

某个热点 Key 过期，大量请求同时访问数据库。

解决：

- 互斥锁
- 逻辑过期
- 热点 Key 永不过期

### 缓存雪崩

大量 Key 同时过期，或 Redis 整体不可用。

解决：

- 过期时间加随机值
- 多级缓存
- 限流和熔断
- Redis 高可用

### 热 Key

单个 Key 请求量过大，导致节点或线程压力集中。

解决：

- 本地缓存
- Key 拆分
- 读副本
- 热点监控

### 大 Key

单个 Key 数据量过大，导致网络、内存和删除操作变慢。

解决：

- 拆分 Key
- 控制集合大小
- 分批删除
- 使用 `UNLINK`

### 实践

- 模拟缓存穿透
- 模拟热点 Key 失效
- 给过期时间加随机值
- 监控热 Key 和大 Key

## 第 8 阶段：分布式锁，2 天

### 基础实现

```redis
SET lock:order:1001 request-id NX EX 30
```

含义：

- `NX`：只有 Key 不存在时才能加锁。
- `EX 30`：30 秒后自动释放。
- `request-id`：标识锁的持有者。

### 解锁必须校验持有者

不能直接：

```redis
DEL lock:order:1001
```

否则锁过期后，旧请求可能删除新请求持有的锁。

应使用 Lua 保证判断和删除原子化：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

### 必须解决

- 锁误删
- 锁过期
- 业务执行时间超过租期
- 服务宕机
- 主从切换导致锁丢失
- 多节点加锁一致性

### 实践

- 实现订单防重复提交
- 实现库存扣减锁
- 模拟持锁服务宕机
- 模拟锁过期和续期

## 第 9 阶段：高并发与性能优化，3 天

### 学习内容

- Pipeline
- 批量命令
- Lua 脚本
- 连接池
- 慢查询
- 大 Key 检测
- 热 Key 检测
- 网络与序列化开销
- 读写分离
- 本地缓存 + Redis 二级缓存

### 关键原则

```text
减少网络往返
减少单次数据量
避免阻塞命令
控制 Key 和 Value 大小
```

### 高风险命令

- `KEYS *`
- `SMEMBERS` 超大集合
- `LRANGE` 大范围读取
- `HGETALL` 超大 Hash
- `DEL` 删除大 Key

可考虑：

- `SCAN`
- `SSCAN`
- `HSCAN`
- `ZSCAN`
- `UNLINK`

### 实践

- 用 Pipeline 对比逐条命令耗时
- 用 Lua 实现库存扣减
- 使用慢查询日志定位问题
- 测量不同 Value 大小的性能

## 第 10 阶段：综合项目，5～7 天

实现一个商品与秒杀系统：

```text
请求
  ↓
本地缓存
  ↓ 未命中
Redis 商品缓存
  ↓ 未命中
MySQL
  ↓
回写 Redis
```

秒杀链路：

```text
用户请求
  ↓
限流
  ↓
Redis 原子扣库存
  ↓
生成订单消息
  ↓
MQ 异步创建订单
  ↓
MySQL 持久化
```

必须加入：

- 缓存穿透防护
- 热点 Key 防护
- 分布式锁或 Lua
- 库存超卖防护
- 消费幂等
- 缓存更新策略
- Redis 宕机降级
- 监控与告警
