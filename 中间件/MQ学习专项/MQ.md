### 1. 生产者到 Broker

  不能只调用发送接口后就认为成功。

  应使用xxx 保证发生成功，消费成功：

  - 同步发送确认
  - 发送失败重试
  - 失败记录
  - 本地消息表
  - 事务消息

  本地消息表示例：

  本地事务：
  1. 写入订单
  2. 写入消息表，状态为待发送

  后台任务：
  1. 扫描待发送消息
  2. 发送 MQ
  3. 收到确认后标记为已发送
  4. 失败则继续重试

  订单和消息记录在同一个数据库事务中，因此不会出现：

  订单已创建，但消息没有记录

  ### 2. Broker 存储

  需要开启：

  - 消息持久化
  - 多副本
  - 主从复制
  - 刷盘确认
  - 集群高可用

  消息只有在 Broker 确认可靠保存后，生产者才认为发送成功。

  ### 3. Broker 到消费者

  消费者必须：

  拉取消息
  → 执行业务
  → 业务成功
  → ACK

  不能：

  拉取消息
  → 先 ACK
  → 再执行业务

  否则业务执行失败后，消息已经被确认，无法重试。

  ## 二、如何处理重复消费

  重复消费通常无法完全避免，例如：

  消费者处理成功
  → ACK 丢失
  → MQ 认为消费失败
  → 再次投递

  因此消费者必须幂等。

  ### 方法一：业务唯一 ID + 消费记录

  消息 ID：msg_1001

  查询消费记录：
  ├── 已处理：直接返回成功
  └── 未处理：执行业务并记录

  消费记录表可以设置唯一索引：

  UNIQUE(message_id)

  ### 方法二：数据库唯一约束

  例如支付回调只能生成一笔支付记录：

  UNIQUE(order_id)

  第二次插入失败时，判断为已处理。

  ### 方法三：状态机

  订单状态只能按合法方向流转：

  待支付 → 已支付 → 已发货 → 已完成

  重复收到“支付成功”消息时：

  订单已经是“已支付”
  → 不再重复执行

  ### 方法四：Redis 原子去重

  SET message_id 1 NX EX 86400

  返回成功表示第一次处理，返回失败表示已经处理过。

  但 Redis 去重不能代替数据库最终一致性，关键业务通常仍需要数据库约束。

  ## 三、如何避免“业务无法接受重复消费”

  先把业务操作分为两类。

  ### 1. 天然幂等

  重复执行结果相同：

  设置订单状态为“已支付”
  更新用户等级为 VIP

  适合使用：

  UPDATE order
  SET status = 'PAID'
  WHERE id = ? AND status = 'UNPAID';

  ### 2. 非幂等

  重复执行会产生错误：

  账户扣款
  库存扣减
  发放优惠券
  增加积分

  需要增加业务唯一约束或操作流水。

  例如库存扣减：

  扣库存流水：
  order_id + sku_id

  同一个订单只能存在一条扣库存流水。

  流程：

  检查扣库存流水
  → 不存在：扣库存并写流水
  → 已存在：直接返回成功

  ## 四、消费失败如何处理

  不要无限重试。

  推荐流程：

  第一次失败 → 延迟重试
  第二次失败 → 延迟重试
  多次失败 → 死信队列
  人工排查 → 修复后重新投递

  重试必须区分异常：

  - 网络临时故障：可以重试。
  - 数据格式错误：重试没有意义，应进入死信队列。
  - 业务状态冲突：等待状态变化后重试或人工处理。

  ## 五、数据库与 MQ 如何保持一致

  典型问题：

  数据库事务提交成功
  → MQ 发送失败

  解决方案：

  ### 方案一：本地消息表

  数据库事务：
  订单表 + 消息表一起提交

  后台任务负责补发消息。

  ### 方案二：事务消息

  消息先进入半消息状态：

  执行本地事务
  ├── 成功：提交消息
  └── 失败：回滚消息

  适合订单、支付等重要场景。

  ### 方案三：CDC / Outbox

  先可靠写数据库，再通过 Debezium、Canal 等工具捕获变更并投递 MQ。

  ## 六、典型支付场景

  支付平台回调
  → 生成业务幂等键 transaction_id
  → 查询支付记录
  ├── 已成功：直接返回成功
  └── 未成功：
      1. 更新订单状态
      2. 写入支付流水
      3. 记录 transaction_id
      4. 返回成功

  数据库约束：

  transaction_id 唯一
  order_id 唯一

  即使支付平台重复回调，也不会重复记账。

  ## 七、最终可靠消费模型

  消息持久化
  → 消费者处理业务
  → 数据库唯一约束 / 状态机保证幂等
  → 业务成功后 ACK
  → 失败自动重试
  → 多次失败进入死信队列
  → 监控、告警、人工补偿
