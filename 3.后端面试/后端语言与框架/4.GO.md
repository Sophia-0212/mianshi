# Go 面试题：精简纠错版

> 基于《代码随想录知识星球精华》第五版 Go 篇，合并第四版重复题。先掌握语义，再理解实现，最后联系业务。
> 版本约定：循环变量采用 Go 1.22+ 语义；map 区分旧实现与 Go 1.24 Swiss Table；调度、GC 以 Go 1.24–1.25 为例。运行时细节不是语言保证。

## 学习路线

| 顺序 | 学什么 | 学到什么程度 |
| --- | --- | --- |
| 1 | 值传递、string、slice、map、interface | 能判断复制后是否共享数据 |
| 2 | error、defer、panic/recover | 能推导执行顺序和返回值 |
| 3 | goroutine、channel、锁、context | 能写出可取消、可等待的并发任务 |
| 4 | GMP、阻塞、抢占 | 能解释任务为何等待、线程是否被占住 |
| 5 | 逃逸、GC、内存对齐 | 能定位分配、泄漏和 GC 开销 |
| 6 | Gin、请求生命周期、CAP | 能把机制用于超时、鉴权和一致性设计 |

**回答顺序：结论 → 原理 → 边界 → 场景。** 首轮重点：slice、map、defer、channel、context、GMP、GC。

## 一、语言基础

### 1. Go 有什么特点？

**静态类型、编译执行、语法简洁、并发支持、自动内存管理。**

- goroutine 降低并发任务的创建和调度成本。
- channel、锁、原子操作提供不同的同步方式。
- 接口隐式实现，组合优先；支持泛型。
- 标准库和工具链统一，适合后端服务、网关、云基础设施。

优势是工程效率与运行成本的平衡；高并发能力仍受 CPU、内存、连接池和下游容量约束。

### 2. Go 和 Java 怎么选？

| 维度 | Go | Java |
| --- | --- | --- |
| 类型组织 | struct、方法、接口、组合 | class、接口、继承 |
| 并发 | goroutine、channel、sync | 平台线程、虚拟线程、并发库 |
| 错误处理 | 显式返回 error | throw、try/catch |
| 内存管理 | GC | GC，多种收集器可选 |
| 工程侧重 | 简洁服务、网络组件、云原生 | 企业框架、成熟业务生态 |

两者都支持泛型，都能做高并发，也都可能发生 GC 暂停。Java 21 已正式支持虚拟线程，不能再用“Java 一个任务只能对应一个 OS 线程”比较。[JEP 444](https://openjdk.org/jeps/444)

业务选型优先看团队经验、现有系统、依赖生态，再通过压测比较成本。

### 3. string、[]byte、[]rune 有什么区别？
string 是不可变的字节序列；[]byte 是可变的字节切片，常用于文件、网络 I/O；[]rune 是可变的 Unicode 码点切片，适合按码点处理中文等文本。
| 类型 | 元素含义 | 可修改 | 常见用途 |
| --- | --- | --- | --- |
| string | 字节序列 | 内容不可修改 | 文本、键、协议字段 |
| []byte | 字节切片，byte 是 uint8 别名 | 可以 | I/O、二进制、缓冲区 |
| []rune | Unicode 码点切片，rune 是 int32 别名 | 可以 | 按码点处理文本 |

### 4. make 和 new 有什么区别？
new 为任意类型分配零值内存，返回 *T；make 只用于 slice、map、chan，完成初始化，返回类型本身。

               new             make
  ━━━━━━━━━━  ━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━
   适用类型    任意类型        slice、map、chan
  ──────────  ──────────────  ──────────────────
   返回值      指针 *T         类型本身
  ──────────  ──────────────  ──────────────────
   作用        分配零值对象    初始化可用结构


### 5. Go 是值传递还是引用传递？

**只有值传递：传参、赋值都会复制值。**

- 数组、struct：复制各元素或字段；其中的指针仍可能共享目标。
- 指针：复制地址，能修改地址指向的对象。
- slice：复制描述符，仍共享底层数组。
- map、channel：复制的值仍关联同一个运行时对象。

直觉：**复制钥匙不会复制房子；换掉自己的钥匙也不会换掉别人的钥匙。**

### 6. Go 怎么实现面向对象？

**struct 保存状态，方法定义行为，interface 实现多态，组合实现复用。**

- 首字母大写表示导出；小写标识符限包内访问。
- 嵌入字段可提升字段和方法，但不等于传统继承。
- 方法绑定在类型上，不是 struct 内的普通字段。
- 修改接收者状态通常使用指针接收者。

### 7. interface 如何实现？T 和 *T 有什么区别？

**类型满足接口的方法集合，即隐式实现接口，无需 implements。**

```go
type Speaker interface { Speak() string }
type Person struct { Name string }
func (p *Person) Speak() string { return p.Name }

var _ Speaker = (*Person)(nil) // 编译期检查：*Person 实现 Speaker
```

- `T` 的方法集包含接收者为 `T` 的方法。
- `*T` 的方法集包含接收者为 `T`、`*T` 的方法。
- 可寻址变量调用指针方法时可能自动取址；接口赋值不会因此让 `T` 自动满足接口。

隐式实现降低接口与实现的耦合，不代表“不依赖框架”，也不妨碍复用框架功能。

### 8. 为什么 interface 里的 nil 不一定等于 nil？

接口值可理解为 **动态类型 + 动态值**；两者都为空才等于 nil。

```go
var p *int = nil
var x any = p
fmt.Println(p == nil) // true
fmt.Println(x == nil) // false：动态类型是 *int
```

常见事故：返回一个值为 nil 的 `*MyError`，装入 error 接口后，`err != nil`。没有错误时应直接 `return nil`。

## 二、slice 与 map

### 9. 数组和 slice 有什么区别？

| 维度 | 数组 | slice |
| --- | --- | --- |
| 类型 | `[3]int`，长度属于类型 | `[]int`，长度不属于类型 |
| 长度 | 固定 | 可通过重新切片、append 改变 |
| 赋值 | 复制整个数组 | 复制描述符，共享底层数组 |
| 零值 | 各元素的零值 | nil，len/cap 均为 0 |

nil slice 可以直接 `append`、`range`，不需要先 make。

### 10. slice 底层是什么？

**指向底层数组的指针 + len + cap。**

```text
slice = { data, len, cap }
          │
          └──> 底层数组
```

- `len`：当前可索引的元素数，索引必须 `< len`。
- `cap`：从切片起点到可扩展边界的容量。
- `s[a:b]` 通常与 s 共享数组，不复制元素。
- `s[a:b:c]` 将容量限制为 `c-a`，不复制数组。

切片描述符可以修改；“slice 是只读对象”是错误的。

### 11. slice 如何扩容？

**append 所需长度超过 cap 时，分配更大的底层数组，复制原元素，再追加新元素。**

以 Go 1.24 的容量计算为例：

1. 新长度大于旧容量的两倍：候选容量取新长度。
2. 否则，旧容量小于 256：候选容量翻倍。
3. 否则，循环执行 `newcap += (newcap + 3*256) >> 2`，直到够用；增长比例逐渐接近 1.25。
4. 最终分配还受元素大小、内存分配规格和溢出检查影响。

**1024 阈值是旧实现，精确扩容比例不是语言约定。** 已知规模时可预分配，减少复制和分配。[slice 源码](https://go.dev/src/runtime/slice.go)

### 12. append 前后是否共享底层数组？

**容量足够时复用；容量不足时分配新数组。容量够时追加不叫扩容。**

```go
s := make([]int, 2, 4)
s[0], s[1] = 1, 2
t := append(s, 3)
t[0] = 9
fmt.Println(s) // [9 2]：共享数组，但 s 的长度仍为 2

u := append(s[:len(s):len(s)], 4) // 限制容量，强制本次追加换数组
u[0] = 7
fmt.Println(s) // [9 2]
```

要立即获得独立元素存储，用 `make + copy` 或 `slices.Clone`；如果元素包含指针，它们指向的对象仍共享。

### 13. map 为什么无序？如何有序遍历？

**语言不保证 map 的迭代顺序，不能依赖插入顺序，也不能依赖两次遍历一致。** 哈希存储、随机化和扩容都不提供稳定顺序。

```go
keys := make([]string, 0, len(m))
for k := range m { keys = append(keys, k) }
sort.Strings(keys)
for _, k := range keys { fmt.Println(k, m[k]) }
```

并发环境需要保护“取键 + 读值”的整个过程，或先在锁内复制快照再排序。

### 14. map 底层怎么实现？

**核心是哈希表，但必须区分版本。**

| 实现 | 存储与冲突处理 |
| --- | --- |
| Go 1.23 及更早的常见实现 | bucket 存最多 8 个键值对，使用 tophash 筛选；冲突多时挂溢出桶 |
| Go 1.24 默认实现 | Swiss Table：每组 8 个槽位，控制字节记录状态和哈希指纹，冲突通过探测处理 |

Swiss Table 先利用哈希指纹筛选候选槽位，再比较完整键；大 map 通过目录管理多个 table。

**Go map 不使用 Java HashMap 的“链表转红黑树”。** [官方 Swiss Table 说明](https://go.dev/blog/swisstable)

### 15. map 如何扩容？

- **旧实现**：负载过高时翻倍扩容；溢出桶过多时可能等量扩容，整理稀疏桶；写入、删除等操作逐步迁移旧桶。
- **Go 1.24 Swiss Table**：table 达到增长条件后重建并重新散列；超过 table 大小上限则分裂，必要时扩展目录。

扩容是为了控制查找成本，和维持迭代顺序无关，也不提供并发安全保证。

来源：[旧 map 实现](https://github.com/golang/go/blob/go1.24.0/src/runtime/map_noswiss.go)、[新 map 实现](https://go.dev/blog/swisstable)。

### 16. map 并发安全吗？

**安全发布后，只有并发读可以；只要并发访问包含写操作，就要同步。** 不同 key 的并发写也不安全。

| 方案 | 适用场景 |
| --- | --- |
| map + Mutex/RWMutex | 默认选择，类型明确，便于保护复合操作 |
| sync.Map | 写入一次、读取多次，或不同 goroutine 操作不同键集 |
| 分片 map + 锁 | 锁竞争已成为瓶颈时 |
| 单 goroutine 持有 map | 通过 channel 串行处理状态变更 |

`sync.Map` 的单次方法安全，不代表 `Load → 修改 → Store` 整体原子；按需使用 CAS、`LoadOrStore` 或外部锁。`Range` 也不是一致性快照。[sync.Map 文档](https://pkg.go.dev/sync#Map)

### 17. map 常见边界有哪些？

- nil map：可读、可遍历、可 delete；写入 panic。
- key 必须可比较；slice、map、func 不能直接作为 key。
- 读取不存在的 key 返回零值；用 `v, ok := m[k]` 区分“缺失”和“存在但为零值”。
- map 元素不可取址；struct 值可先取出修改再写回，或存指针并管理同步。
- `len(m)` 表示元素数，map 没有 `cap`；删除元素不保证底层存储立即缩小。

## 三、错误处理与 defer

### 18. Go 如何处理错误？与 Java 异常有什么区别？

**error 是普通接口值，可预期失败用返回值表达，由调用方明确处理。**

```go
v, err := load()
if err != nil {
    return fmt.Errorf("load config: %w", err)
}
```

- `fmt.Errorf("...: %w", err)`：保留错误链并添加上下文。
- `errors.Is`：判断错误链中是否匹配目标错误。
- `errors.As`：提取错误链中的指定类型。

Java 异常通过栈展开寻找 catch；Go 通常用 `if err != nil`。性能取决于具体路径，不能概括为“Go 错误处理一定更快”。

### 19. panic 和 recover 是什么？

**二者都是内建函数。panic 中断正常执行并展开当前 goroutine 调用栈；recover 可以终止该展开过程。**

```go
func f() {
    defer func() {
        if r := recover(); r != nil {
            fmt.Println("recovered:", r)
        }
    }()
    panic("bad state")
    // 不会恢复执行到这里
}
// 调用 f() 的上层可以继续执行。
```

业务失败如“库存不足”返回 error；panic 适合无法继续维持正常状态的程序错误。

### 20. recover 有哪些限制？

- 必须由**同一 goroutine 中正在执行的 deferred 函数直接调用**。
- 普通调用、defer 内再调用的辅助函数，不能据此捕获当前 panic。
- 捕获后，发生 panic 的函数不会从出错行继续执行；完成相应 defer 后返回。
- 任一 goroutine 的 panic 未被恢复，通常导致整个程序退出。
- 运行时 fatal 错误，如某些并发 map 错误，不属于可 recover 的普通 panic。

HTTP 中间件无法捕获另起 goroutine 中的 panic；恢复边界应记录堆栈并给出明确失败结果。

### 21. defer 的执行规则是什么？

**登记时求值，退出前执行，后登记先执行。**

1. 执行到 defer 时，保存函数值及参数；闭包引用的变量在执行时读取。
2. 正常返回或 panic 展开时，按 LIFO 执行。
3. `return` 先给返回值赋值，再执行 defer，最后返回调用方。

```go
func f() (n int) {
    defer func() { n++ }()
    return 1
} // 返回 2

x := 1
defer fmt.Println(x)                   // 登记时保存 1
defer func() { fmt.Println(x) }()      // 执行时读取 2
x = 2
// 所在函数退出时：先打印 2，再打印 1
```

`os.Exit` 不执行 defer；main 返回时也不会等待其他 goroutine 执行完 defer。

### 22. defer 底层原理和使用陷阱？

**现代编译器可能使用开放编码、栈上记录或运行时记录，不能一概说“每次都在堆上压栈”。**

- 常见固定数量 defer 可被编译为退出路径中的直接调用。
- 循环内的 defer 到整个函数退出才执行，可能积压文件句柄、锁和内存。
- 资源获取成功后再登记释放；defer 一个 nil 函数值，会在真正调用时 panic。

循环处理文件时，将单次处理封装成函数，在该函数内 `defer f.Close()`，每次处理完即释放资源。

### 23. 循环变量捕获还会打印“5 个 5”吗？

**取决于语言版本和变量声明位置。** Go 1.22+ 中，循环自身通过 `:=` 声明的变量，每轮具有独立实例。

```go
for i := 0; i < 5; i++ {
    defer func() { fmt.Println(i) }()
}
// Go 1.22+ 语义：4 3 2 1 0，defer 倒序执行
```

如果循环复用外部变量，仍然共享：

```go
i := 0
for ; i < 5; i++ {
    defer func() { fmt.Println(i) }()
}
// 5 5 5 5 5
```

语言版本通常由 `go.mod` 的 `go` 指令决定。启动 goroutine 时，显式参数 `go func(v int) { ... }(i)` 也能清楚表达值捕获；输出顺序仍无保证。[Go 1.22 说明](https://go.dev/doc/go1.22#language)

## 四、并发与同步

### 24. 进程、线程、goroutine 有什么区别？

| 概念 | 资源与调度 | 成本特点 |
| --- | --- | --- |
| 进程 | 隔离地址空间，通过 IPC 或共享内存通信 | 隔离强，创建和切换通常更重 |
| OS 线程 | 共享进程资源，由操作系统调度 | 有独立栈和寄存器状态 |
| goroutine | 共享进程地址空间，由 Go runtime 调度到线程 | 栈较小且可增长，调度通常更轻 |

goroutine 支持多核并行和抢占，不等于“单线程、纯协作式协程”。线程栈大小依平台配置；goroutine 栈也有成本，不能无限创建。

### 25. 并发和并行有什么区别？

- **并发**：多个任务在时间段内交错推进，描述任务组织方式。
- **并行**：多个任务在同一时刻执行，描述实际执行状态。

单核可通过切换实现并发；多核可并行执行 CPU 任务。并发并不意味着“任一时刻只能执行一个任务”。

### 26. Go 的并发模型是什么？

**goroutine 执行任务，channel 传递数据和同步，sync/atomic 保护共享状态。**

- channel 适合任务流转、结果汇聚、背压和通知。
- 锁适合保护共享数据及其不变量。
- atomic 适合独立计数器、标志位等简单状态。

发送 slice、map 或指针不会深拷贝对象。发送后双方继续修改共享对象，仍会产生数据竞争。

### 27. 如何管理 goroutine 生命周期？

**启动前明确三件事：谁取消、怎么退出、谁等待。**

```go
func run(ctx context.Context, jobs <-chan int) {
    var wg sync.WaitGroup
    wg.Add(1)
    go func() {
        defer wg.Done()
        for {
            select {
            case <-ctx.Done():
                return
            case v, ok := <-jobs:
                if !ok { return }
                _ = v // 实际处理也应支持 ctx 取消
            }
        }
    }()
    wg.Wait()
}
```

`context` 发出取消信号，任务协作退出，`WaitGroup` 等待完成。任务不检查取消、阻塞操作不支持取消时，cancel 无法强杀它。

### 28. 主 goroutine 有什么特殊之处？

**main 函数返回，程序退出；不会自动等待其他 goroutine。**

`go f()` 只启动任务，不等待完成，也不保证按启动顺序执行。使用 WaitGroup 或完成通道等待，不能用 `time.Sleep` 保证正确性。

### 29. channel 是什么？底层如何工作？

**channel 是带类型的通信与同步机制，发送传递元素值的副本。**

常见 runtime 实现包含：缓冲环形队列、发送/接收等待队列、锁、关闭状态。

- 有等待对端时，可直接交接数据并唤醒对端。
- 有缓冲空间或数据时，操作环形队列。
- 条件不满足时，挂起 goroutine，等待条件变化。

并发安全针对 channel 操作本身；接收一个消息也不代表消费端已经完成业务处理。单通道多个消费者是分摊消息，不是每人收到一份的广播。

### 30. 无缓冲和有缓冲 channel 有什么区别？

| 通道 | 发送完成条件 | 接收完成条件 | 典型用途 |
| --- | --- | --- | --- |
| 无缓冲 | 接收方参与交接 | 发送方参与交接 | 同步交接 |
| 有缓冲 | 有空位，或可直接交接 | 有数据，或可直接交接 | 有界队列、削峰 |

缓冲区满时发送阻塞，空时接收阻塞。**缓冲只能吸收短时波动，不能解决生产持续快于消费。** 满时的阻塞就是背压。

### 31. nil、关闭后的 channel 怎么表现？

| 状态 | 发送 | 接收 | close |
| --- | --- | --- | --- |
| nil | 永久阻塞 | 永久阻塞 | panic |
| 已关闭但有缓存 | panic | 先读缓存，`ok=true` | panic |
| 已关闭且已排空 | panic | 立即返回零值，`ok=false` | panic |

普通打开通道的发送、接收按缓冲与对端状态决定是否阻塞。`for v := range ch` 在通道关闭且排空后退出。

关闭通常由能确定“不会再发送”的一方负责。多个发送者应先统一等待全部发送结束，再由协调者关闭；不需要为 GC 专门 close。

### 32. select 如何工作？

**从能立即进行的通信操作中伪随机选择一个；都不可进行时，有 default 就执行，否则阻塞。**

- 不按代码顺序赋予优先级；同时就绪时，取消分支也不保证先执行。
- nil channel 的 case 永远不可进行，可用来禁用分支。
- 已关闭 channel 的接收持续就绪，循环中应退出或将该通道变量置 nil。
- `select {}` 永久阻塞；循环加 default 容易空转占满 CPU。

通用实现会以随机探测顺序检查 case，按固定锁顺序锁定涉及的 channel；需要等待时注册等待节点并挂起，选中后清理其他节点。编译器可优化简单 select。

### 33. 如何给 channel 操作加超时或取消？

```go
select {
case out <- value:
    // 发送完成
case <-ctx.Done():
    return ctx.Err()
}
```

`ctx` 可由 `context.WithTimeout` 创建；单次等待也可使用 `time.NewTimer`。default 表达“立即放弃或降级”，不是超时；需要明确丢弃、重试还是返回忙碌错误。

### 34. Mutex、RWMutex、atomic 怎么选？

| 工具 | 保护对象 | 关键边界 |
| --- | --- | --- |
| Mutex | 临界区及多字段一致性 | 同一时刻一个持锁者 |
| RWMutex | 读多写少的共享状态 | 读锁可并行；写锁排斥其他读写锁 |
| atomic | 单个简单状态 | 多次原子操作不会自动组成事务 |

规则：共享数据的相关读写都必须遵循同一同步协议；锁使用后不能复制；Mutex 不可重入；持锁期间避免慢 I/O。

RWMutex 不保证一定快于 Mutex；读临界区很短时，维护读锁也可能增加开销。

### 35. Mutex 有几种模式、哪些状态位？

**正常模式追求吞吐，饥饿模式减少长时间等待。**

- 正常模式：被唤醒的等待者与新到来的 goroutine 竞争，后者可能先拿锁。
- 饥饿模式：等待者等待超过约 1ms 且未获得锁时可能触发；锁交给队首等待者，新来者排队。
- 接手者发现自己是最后等待者，或本次等待不足约 1ms，会退出饥饿模式。

状态字包含 `mutexLocked`、`mutexWoken`、`mutexStarving` 三个位及等待者计数；它们不是四种互斥状态，`mutexWoken` 用来协调唤醒、避免重复唤醒。

阈值和策略属于实现，不是公平性 API 保证。[Mutex 源码](https://go.dev/src/internal/sync/mutex.go)

### 36. WaitGroup、Cond、Once、Pool 分别解决什么问题？

| 工具 | 用途 | 易错点 |
| --- | --- | --- |
| WaitGroup | 等待一组任务结束 | 先 Add 再启动；Done 与 Add 配对，不承担取消 |
| Cond | 等待共享条件变化 | 持锁循环判断条件；Wait 会解锁等待，返回前重新加锁 |
| Once | 一次性初始化 | 初始化函数 panic 后也视为已执行，不能依赖它自动重试 |
| Pool | 复用临时对象 | 对象可随时被移除，不能作为可靠缓存或连接池 |

`Pool.Put` 后应放弃该对象的使用权，避免被其他 goroutine 取出后并发修改。[sync 文档](https://pkg.go.dev/sync)

### 37. context 的作用和原理是什么？

**沿调用链传播取消、截止时间和请求级元数据。**

- `Background/TODO`：根上下文，无截止时间，其 Done 为 nil。
- `WithCancel`：创建可取消子上下文。
- `WithTimeout/WithDeadline`：增加时间限制；不会延长父级更早的截止时间。
- `WithValue`：派生携带元数据的上下文，不修改父上下文。

取消沿父到子传播；子取消不影响父。取消通过关闭 Done 通道通知监听者，`Err()` 返回取消或超时原因；多个 goroutine 可以安全使用同一个 context。[context 文档](https://pkg.go.dev/context)

### 38. context 使用有哪些规范？

```go
ctx, cancel := context.WithTimeout(parent, 200*time.Millisecond)
defer cancel()
return callDownstream(ctx) // 下游也必须使用 ctx
```

- 通常作为函数第一个参数，命名 ctx，不传 nil。
- 派生出 cancel 后确保调用，及时释放关联资源。
- 请求链传递原 ctx；随意替换成 Background 会切断取消与追踪。
- Value 用于 trace ID 等请求元数据；用自定义 key 类型避免冲突，不代替显式业务参数。
- context 并发安全，不代表 Value 存放的 map、指针对象自动安全。

### 39. goroutine 泄漏如何发现和避免？

**任务已经没有业务价值，却一直不退出，就是 goroutine 泄漏。**

常见原因：发送无人接收、等待未关闭通道、死锁、无退出条件循环、下游调用无超时。

防范：取消可传播、阻塞有出口、队列有上限、结束有人等待。通过 goroutine 数量趋势及 pprof 堆栈，定位重复积累的阻塞位置。

泄漏的 goroutine 不会因为“没人引用它”就被 GC 自动回收；它的栈及引用对象还可能持续占用内存。

## 五、GMP 与调度

### 40. GMP 分别是什么？

| 组件 | 含义 | 核心职责 |
| --- | --- | --- |
| G | goroutine | 保存栈、执行状态和调度信息 |
| M | OS 线程 | 实际执行代码 |
| P | 调度上下文 | 持有运行队列、分配缓存等执行资源 |

**M 执行普通 Go 代码需要持有 P；G 被调度到 M 上执行。**

```text
可运行 G ──> P 的本地队列 / 全局队列
                      │
                 持有 P 的 M ──> 执行 G
                      │
                 无任务时尝试窃取
```

直觉：G 是任务，M 是工人，P 是执行 Go 任务所需的工作台。工作台数量限制同时执行 Go 代码的线程数。

### 41. GOMAXPROCS 控制什么？

**控制 P 数量，即同时执行用户 Go 代码的最大线程数，不是 goroutine 或 OS 线程总数。**

- M 可能多于 P：某些线程可能正在系统调用、cgo 或休眠。
- 实际 CPU 并行度还受可用 CPU 和容器配额限制。
- 可运行时调整，不是“启动后固定”“最大 256”；单核也允许设置大于 1，只是不增加物理并行能力。
- Go 1.25 引入容器感知默认值，并可按资源变化自动更新；手动配置及兼容性设置会影响此行为。[Go 1.25 说明](https://go.dev/doc/go1.25#runtime)

### 42. 调度流程与优势是什么？

1. 新建 G 通常优先进入当前 P 的调度位置或本地队列。
2. M 寻找可运行 G，来源包括本地队列、全局队列、网络轮询和其他 P。
3. 本地工作不足时，通过 work stealing 从其他 P 获取任务。
4. 周期性检查全局任务，降低局部任务长期独占的风险。
5. 没有工作时，线程可休眠；新任务到来时按需唤醒或创建线程。

优势：复用线程、减少调度竞争、平衡负载、利用多核。**不保证 FIFO，也不是每条 go 语句创建一个线程。** [调度器源码](https://go.dev/src/runtime/proc.go)

### 43. 阻塞时调度器做什么？

| 原因 | G、M、P 的典型变化 |
| --- | --- |
| channel、锁等待、Sleep | G 挂起，M/P 可继续运行其他 G |
| 可轮询的网络 I/O | G 等 netpoll，就绪后重新进入可运行状态 |
| 阻塞系统调用 | M 随调用阻塞，P 可交给其他 M；返回后重新获取执行资源 |
| Gosched | G 主动让出执行机会，仍可运行 |
| 抢占 | 保存执行现场，将执行机会交给其他任务 |

**G 阻塞不等于 M 阻塞。** 普通文件 I/O 不一定走 netpoll；atomic 操作也不是“必然挂起 G”的操作。

### 44. goroutine 最多执行 10ms 吗？

**不是硬上限。约 10ms 是运行时请求抢占的一个判断阈值，实际切换受安全点、平台和当前代码影响。**

Go 1.14 引入基于信号的异步抢占，减少纯计算循环长期霸占线程的问题。协作式检查仍存在；`sysmon` 还参与系统调用 P 回收等监控工作。

抢占改善公平性，不提供实时调度保证。业务仍要控制并发数量和单任务工作量。

## 六、内存管理与 GC

### 45. 什么是逃逸分析？

**编译器分析对象生命周期和使用方式，决定能否放在栈上；不能证明安全或不适合栈分配时，可能分配到堆。**

常见诱因：指针流向函数外、被长期存活对象引用、跨 goroutine 传递、对象过大、大小或调用关系难以静态确定。

```go
func makeInt() *int {
    n := 42
    return &n
}
```

n 必须存活到引用结束；但调用被内联且指针未外泄时，分配还可能被优化。**返回指针、new、make、接口转换都不能脱离上下文断言一定堆分配。**

```bash
go build -gcflags='-m=2' ./...
```

### 46. 有 GC，为什么还会内存泄漏？

**GC 回收不可达对象；业务不再需要但仍被引用的数据不会回收。**

- 子 slice、子 string 保留大块底层数据：需要独立存储时复制，string 可用 `strings.Clone`。
- slice 缩短后，底层数组中的旧指针仍保留对象：移除时按需清空槽位。
- 全局 map、缓存只增不减：设置容量、TTL 或淘汰策略。
- goroutine 泄漏：栈及其引用对象持续存活。

这类问题本质是无效引用保留，不应把所有子切片都称为“必然的内存泄漏”。

### 47. Go GC 的核心原理是什么？

**以 Go 1.24 常规实现为例：并发、非分代、非移动的标记清扫，配合写屏障和 GC assist。**

- 从根出发：栈、全局变量等持有的指针。
- 沿引用关系标记可达的堆对象。
- 清扫未标记对象，使内存可再次分配。
- 并发阶段与业务同时推进，但仍有短暂 STW，且会消耗 CPU。

三色标记是描述标记过程的模型，不是取代“标记清扫”的另一套算法。Go 1.5 是并发 GC 的重要节点，Go 1.8 引入混合写屏障。

### 48. 三色标记是什么？

| 颜色 | 含义 |
| --- | --- |
| 白 | 尚未发现；标记完成后剩余白对象才可回收 |
| 灰 | 已发现，自身引用尚未扫描完 |
| 黑 | 已扫描完自身引用 |

流程：根发现对象 → 加入灰集合 → 扫描引用，将新发现对象变灰 → 当前对象变黑 → 处理到没有待扫描对象。

并发难点：业务同时修改引用，可能让尚未标记的可达对象被漏掉。写屏障用来防止漏标。

### 49. 混合写屏障为什么有效？

**修改指针时保护旧引用和新引用相关的对象，避免业务把对象从 GC 尚未扫描到的位置“藏走”。**

理论模型：

```text
写入 slot = newPointer 前：
  标记 slot 原来指向的对象
  若当前栈尚未扫描，标记 newPointer 指向的对象
  完成指针写入
```

Go 实现可保守地对新旧目标都着色，减少条件判断；标记期间新分配的堆对象直接视为黑色。结合栈扫描规则，可避免标记结束时重新扫描所有栈。

不是“GC 开始把所有栈对象直接变黑”，也不能承诺固定的微秒级暂停时间。[写屏障源码](https://go.dev/src/runtime/mbarrier.go)

### 50. 一轮 GC 有哪些阶段？

```text
短暂 STW：完成标记准备、开启写屏障
    ↓
并发标记：扫描根和堆对象，必要时业务分配触发 assist
    ↓
短暂 STW：完成标记终止，关闭写屏障
    ↓
并发清扫：回收未标记对象，供后续分配复用
```

GC assist 主要让分配内存的 goroutine 分担标记工作，防止分配速度持续超过回收进度。

**清扫后可复用，不代表立即归还操作系统。** 空闲页归还由 scavenger 等机制处理，RSS 不一定立即下降。

### 51. GC 何时触发？GOGC、GOMEMLIMIT 有什么作用？

- **分配触发**：pacer 根据堆目标等信息决定何时开始，给标记预留时间。
- **时间触发**：长期未 GC 时，runtime 可能强制发起；常见实现约 2 分钟，不是精确定时承诺。
- **手动触发**：`runtime.GC()`；通常不用它替代正常调优。

| 参数 | 作用 | 代价 |
| --- | --- | --- |
| GOGC | 调节相对存活堆与根集合的增长目标，默认 100 | 增大通常减少 GC 频率、增加内存占用 |
| GOMEMLIMIT | 为 runtime 管理的内存设置软限制 | 太低可能频繁 GC；不等于进程 RSS 硬上限 |

忽略内存限制等影响时，堆目标近似：`存活堆 + (存活堆 + 根集合) × GOGC/100`。开始 GC 的触发点一般早于该目标。[官方 GC 指南](https://go.dev/doc/gc-guide)

### 52. 如何调优 GC？

**先测量，再减少分配和存活数据，最后调整参数。**

| 观察结果 | 优先动作 |
| --- | --- |
| 分配速率高 | 预分配、减少转换与临时对象、按需使用 sync.Pool |
| 存活堆持续增长 | 检查缓存、引用保留、goroutine 泄漏 |
| GC CPU 或 assist 高 | 减少分配；评估用更多内存换更少 GC |
| 容器内存吃紧 | 设置留有余量的 GOMEMLIMIT，控制并发和队列 |

`pprof` 看分配热点与存活对象，`trace` 看调度和阻塞，`GODEBUG=gctrace=1` 看 GC 概况。优化前后比较延迟、吞吐、CPU、内存，不能只看 GC 次数。

### 53. Go 内存对齐是什么？

**字段按其对齐要求放置，编译器插入 padding；结构体大小还需满足整体对齐要求。**

```go
type A struct { a byte; b int64; c byte }
type B struct { b int64; a byte; c byte }
// 常见 64 位平台：unsafe.Sizeof(A{}) == 24，B{} == 16
```

合理字段顺序可减少大量对象的内存占用；通过 `unsafe.Sizeof/Alignof/Offsetof` 验证，不能跨平台写死。

**对齐不等于并发安全。** CPU 并非永远按一个固定字长访问；需要原子性和可见性时，使用 atomic 或锁。

## 七、Go Web 与业务场景

### 54. Gin 提供什么能力？路由怎么实现？

**Gin 基于 net/http，提供路由、中间件、参数绑定、响应渲染等能力。**

- `gin.Engine` 实现 `http.Handler`，入口是 `ServeHTTP`。
- 按 HTTP 方法组织路由树；使用压缩前缀树匹配路径。
- `:id` 匹配参数段，`*path` 匹配剩余路径；路由组组合前缀和中间件。
- 匹配成功后，把对应 handler 链交给 Context 执行。

中间件常用于鉴权、限流、追踪、日志和 panic 恢复。项目简单时 net/http 也可满足需求，框架不能替代业务边界设计。[Gin 路由源码](https://github.com/gin-gonic/gin/blob/v1.10.0/tree.go)

### 55. Gin 中间件的 Next、Abort、return 有什么区别？

**核心是 handler 列表 + 当前索引；Next 在当前位置继续执行后续 handler。**

```go
func Auth(c *gin.Context) {
    if c.GetHeader("Authorization") == "" { // 仅演示，真实鉴权还需校验凭证
        c.AbortWithStatusJSON(401, gin.H{"error": "unauthorized"})
        return
    }
    c.Next()
    // 后续 handler 完成后执行，例如记录耗时
}
```

| 操作 | 语义 |
| --- | --- |
| Next | 在当前中间件内执行后续链，返回后继续当前中间件 |
| Abort | 阻止后续未执行 handler，不会退出当前函数 |
| return | 退出当前函数，不负责阻断整个链 |

若 A、B 都调用 Next：`A前 → B前 → handler → B后 → A后`。

**不调用 Next 不等于拦截。** 外层驱动循环仍可能执行后续 handler；拒绝请求通常需要 `Abort + return`。Abort 也不会阻止已经进入的外层中间件继续收尾。[Context 源码](https://github.com/gin-gonic/gin/blob/v1.10.0/context.go)、[外层驱动](https://github.com/gin-gonic/gin/blob/v1.10.0/gin.go)

### 56. 一个请求并发调用多个下游，如何设计？

**共享取消链，限制并发，明确结果策略，等待任务收尾。**

1. 从请求 ctx 派生总超时，下游调用使用该 ctx 或更短的子超时。
2. 使用有界 worker pool 或信号量，防止请求扇出压垮连接池和下游。
3. 用 channel 汇总结果，或同步保护共享状态。
4. 明确“任一失败全部取消”还是“允许部分成功”；取消后仍要等待任务退出。
5. 重试受剩余时间和次数限制；有副作用的写操作需要幂等保障。

例：聚合接口总预算 200ms，某个推荐服务超时可降级；扣库存失败则必须按业务规则返回失败或补偿。

### 57. CAP 是什么？为什么不能同时满足？

**发生网络分区时，无法同时保证线性一致性 C 和可用性 A。**

| 属性 | 准确定义 |
| --- | --- |
| C：Consistency | 操作表现得像作用于单个副本，并遵守真实时间顺序，即线性一致性 |
| A：Availability | 发给非故障节点的请求最终完成，不依赖分区何时修复 |
| P：Partition tolerance | 即使节点间消息丢失、网络分区，仍需讨论系统保证 |

例：A、B 断网；写入 A 成功后，再读 B。

- B 等待同步或拒绝请求：可维护 C，但牺牲 A。
- B 返回尚未更新的旧值：可保持响应，但牺牲 C。

P 不表示“分区时仍同时保证 C 和 A”；CAP 也不是平时任意三选二。业务通常按操作取舍：库存扣减偏向一致性，推荐数据可容忍陈旧。[Gilbert、Lynch 关于 CAP 的论文](https://dspace.mit.edu/entities/publication/dfcb6512-af44-4fc9-8e8b-1a8f28f1b53a)

## 八、面试前自测

2. 接口装入 nil 指针后，为什么不等于 nil？
3. map 不同 key 并发写，为什么仍要加锁？
4. channel 传指针后，为什么还可能发生数据竞争？
5. cancel 后任务为什么可能仍不退出？
6. G 被挂起时，M 是否一定被阻塞？
7. GC 后 RSS 为什么可能不下降？
8. Gin 鉴权失败为什么需要 Abort 和 return？

```bash
go test -race ./...             # 检查实际执行路径中的数据竞争
go test -bench=. -benchmem ./... # 比较性能与分配
go build -gcflags='-m=2' ./...   # 查看逃逸与内联分析
```

race 检测通过不代表所有执行路径都无竞争。涉及语义争议时查 [Go 规范](https://go.dev/ref/spec)，涉及并发可见性时查 [Go 内存模型](https://go.dev/ref/mem)。
