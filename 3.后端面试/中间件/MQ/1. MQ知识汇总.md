# MQ 基础与核心直觉

是什么：MQ 是消息队列，是服务之间通过 消息 异步通信 的中间件，它的本质，就是个转发器，包含发消息、存消息、消费消息的过程。常见实现有 Kafka、RocketMQ、RabbitMQ。

工作流程：生产者发送消息 → Broker 存储消息 → 消费者处理业务 → 成功后确认消费或提交消费位点。

解决的问题：**异步、解耦、削峰**。

- 异步：调用方发送消息后立即返回，消费者稍后处理，减少等待。
- 解耦：生产者只发布消息，不依赖具体消费者；新增、修改消费者不会影响生产者。
- 削峰：高峰请求先进入 MQ 排队，消费者按处理能力消费，避免下游瞬时过载。

带来的问题：引入消息丢失、重复、乱序、积压，以及跨服务的数据一致性问题。消息发送成功，不代表业务处理成功。选择消息队列的有点 就必须配套解决丢失、重复、乱序和积压问题。


其中：

消息丢了怎么办？→ 可靠投递：生产端确认与重试，Broker 持久化与副本复制，消费端业务提交后再确认；可靠性取决于配置和故障范围。

重复消费怎么办？→ 业务幂等：用业务唯一键、条件更新，或把消费记录与业务更新放在同一数据库事务中，避免重复生效。

消息乱序怎么办？→ 顺序消费：同一业务键固定路由，生产端有序发送，消费端按键串行处理，再用状态机或版本校验兜底。

处理失败怎么办？→ 重试与死信：临时故障有限退避重试；持续失败则隔离、告警，修复后受控重放。

数据库成功、消息没发出去怎么办？→ Outbox 或事务消息：协调本地事务与消息发送，配合消费幂等、补偿和对账实现最终一致性。

消息积压怎么办？→ 积压治理：先定位消费慢、下游瓶颈或热点，再优化处理、扩容和限流；不能只加消费者。

机器坏了、容量不够怎么办？→ 高可用与扩展：副本复制与故障切换提高可用性，分区或队列分片扩展容量和并行度。
