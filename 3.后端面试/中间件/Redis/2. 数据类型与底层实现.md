# Redis 数据类型与底层实现

## 核心直觉
以 Redis 7.2 为基线：

| 类型或功能 | 业务需求 | Redis 7.2 底层实现 |
|---|---|---|
| [String](#string) | 整值读写、计数 | [int](#string) / [embstr](#string) / [raw](#string)；后两者使用 [SDS](#sds) |
| [Hash](#hash) | 对象字段读写 | [listpack](#listpack) / [哈希表](#哈希表) |
| [List](#list) | 有序、可重复、两端操作 | [listpack](#listpack) / [quicklist](#quicklist) |
| [Set](#set) | 去重、成员判断、集合运算 | [intset](#intset) / [listpack](#listpack) / [哈希表](#哈希表) |
| [ZSet](#zset) | 成员去重、按分数排序 | [listpack](#listpack) / [哈希表](#哈希表) + [跳表](#跳表) |
| [Bitmap](#bitmap) | 布尔标记、位统计 | 基于 [String](#string) 的位操作 |
| [Stream](#stream) | 消息追加、消费追踪 | [基数树（rax）](#基数树) + [listpack](#listpack) |

## 数据类型与业务选择

### String

- **定义**：一个 Key 保存一个值，支持字符串、二进制数据及数值操作。
- **常用命令**：
  - **`SET name Alice`**：写入值；默认覆盖已有值。
  - **`GET name`**：读取 `Alice`；Key 不存在返回 `nil`。
  - **`INCR views`**：整数原子加 1，返回新值；原值 10 则返回 11，Key 不存在则从 0 加到 1。
- **业务场景**：缓存 JSON、计数器、分布式锁。
- **底层实现**：
  - **int**：符合条件的整数直接编码存储，节省空间。
  - **embstr**：短字符串的对象头与 SDS 一次分配，减少分配次数。
  - **raw**：对象头与 SDS 分开分配，适合较长或修改后的字符串；[SDS 原理](#sds)。
- **面试重点**：
  - **原子计数**：`INCR` 不会丢失并发增量；`GET → 加 1 → SET` 可能相互覆盖。
  - **数值边界**：值非整数或结果超出有符号 64 位范围，`INCR` 报错。
  - **锁的入口**：`SET lock:order:1001 A NX EX 30`；`NX` 要求 Key 不存在，`EX 30` 设置租期，成功返回 `OK`，竞争失败返回 `nil`；详见[分布式锁](<6. 分布式锁.md>)。

### Hash

- **定义**：一个 Key 保存多个字段及对应值，适合表示对象。
- **常用命令**：`HSET user:1001 name Alice` 写字段；`HGET user:1001 name` 读字段。
- **业务场景**：用户资料、商品属性、购物车；单独修改字段，无需反序列化并重写整段 JSON。
- **底层实现**：小 Hash 使用 [listpack](#listpack)；字段数量或字段/值长度超限后转为[哈希表](#哈希表)。
- **面试重点**：listpack 少指针、省内存，但查字段需要遍历；哈希表平均 O(1) 定位字段，但内存开销更大。`HGETALL` 遍历全部字段，大 Hash 应避免一次取全量。

### List

- **定义**：按插入位置排列，元素可重复，支持两端插入、弹出。
- **常用命令**：`LPUSH jobs task1` 从左端入队；`RPOP jobs` 从右端出队，组合实现先进先出。
- **业务场景**：简单队列、最新消息列表。
- **底层实现**：小 List 可直接使用 listpack；变大后转为 [quicklist](#quicklist)，用链表串联多个紧凑数据块。
- **面试重点**：
  - **访问代价**：单元素两端操作通常按 O(1) 分析；中间位置访问需要遍历，最坏 O(N)，不适合当随机访问数组。
  - **消费可靠性**：直接 `RPOP` 后消费者宕机，消息已移除；List 无内置消费确认，可靠消费需另建处理中队列，或使用 Stream / MQ。

### Set

- **定义**：无序、成员唯一的集合，支持成员判断、交集、并集、差集。
- **常用命令**：`SADD tags redis` 添加成员；`SISMEMBER tags redis` 判断存在；`SINTER` / `SUNION` / `SDIFF` 做集合运算。
- **业务场景**：标签、共同关注、独立访客去重。
- **底层实现**：小型纯整数集合可用 [intset](#intset)；符合条件的小集合可用 listpack；超出紧凑编码条件后使用哈希表。
- **面试重点**：哈希表成员判断平均 O(1)，intset 查找 O(log N)，listpack 通常遍历；Set“无序”指不承诺对外顺序，底层 intset 仍可有序。集合运算不能一概视为 O(1)。

### ZSet

- **定义**：成员唯一，每个成员关联一个分数，按分数排序；分数可重复。
- **常用命令**：
  - **`ZADD rank 100 Alice`**：添加成员，已存在则更新分数。
  - **`ZRANGE rank 0 9 REV WITHSCORES`**：按分数降序取前 10 名及分数。
  - **`ZSCORE` / `ZREVRANK`**：查询成员分数 / 降序排名，排名从 0 开始。
- **业务场景**：排行榜；延迟队列可把执行时间作为分数。
- **底层实现**：小 ZSet 使用 listpack；超限后使用“哈希表 + [跳表](#跳表)”。哈希表按成员查分数，跳表按分数维护顺序。
- **面试重点**：
  - **为什么需要两种索引**：哈希表便于成员定位，跳表便于排名与范围查询；两者互补。
  - **访问代价**：采用哈希表 + 跳表时，查分数平均 O(1)，增删和查排名平均 O(log N)，分数范围查询平均 O(log N + M)，M 为返回数量。
  - **Set 与 ZSet**：两者都按成员去重；需要排序、排名或分数范围时选 ZSet。
  - **延迟队列边界**：查到期任务与移除任务需原子执行；取出后宕机、重试和幂等仍需业务处理。
  - **命令演进**：旧写法 `ZREVRANGE` 仍常见；Redis 6.2 起推荐用 `ZRANGE ... REV`。[官方说明](https://redis.io/docs/latest/commands/zrevrange/)

### Bitmap

- **定义**：用一个二进制位保存一个布尔标记，是 String 的使用方式，不是独立的 Redis 数据类型。
- **常用命令**：`SETBIT sign:1001 0 1` 标记第 0 位；`GETBIT` 读位，`BITCOUNT` 统计值为 1 的位数。
- **业务场景**：签到、活跃用户、在线状态。
- **底层实现**：操作 String 字节数组中的指定位；空间取决于最大位偏移，而非值为 1 的位数。
- **面试重点**：适合密集编号；只标记编号十亿的用户，也要扩展到对应位置。稀疏编号需映射或分桶，不能只按活跃人数估算空间。

### Stream

- **定义**：消息带 ID 的日志结构，支持追加、消费组、确认及待处理消息追踪。
- **常用命令**：`XADD` 追加，`XREADGROUP` 消费组读取，`XACK` 确认，`XPENDING` 查看待确认消息，`XAUTOCLAIM` 接管超时消息。
- **业务场景**：任务分发、事件流、需要追踪消费状态的消息处理。
- **底层实现**：消息主体由[基数树](#基数树)索引多个 listpack；树按 ID 定位数据块，块内紧凑保存多条消息。
- **面试重点**：普通消费组读取会登记待确认消息；处理成功后再 `XACK`。宕机后可接管重试，但可能重复处理，需幂等；确认不等于删除消息，容量需单独裁剪，复杂需求评估专业 MQ。

## 底层结构原理

### SDS

- **定义**：Simple Dynamic String，简单动态字符串；保存内容及长度等元信息，常用头部还记录容量。
- **解决问题**：取长度 O(1)，无需像 C 字符串那样扫描到结束符。
- **设计优势**：二进制安全，内容可含 `\0`；扩容时可预留空间，减少后续追加的分配次数。
- **面试重点**：String 是对外类型，SDS 是底层字符串结构；String 的 int 编码不靠 SDS 保存整数值。

### listpack

- **定义**：将多个元素紧凑存入连续内存，元素之间不必逐个保存链表指针。
- **解决问题**：减少指针和内存分配开销，提高小集合的空间利用率。
- **性能代价**：查找通常需遍历；插入、删除可能搬移后续数据，不宜无限放大。
- **面试重点**：相比旧 ziplist，每项记录自身长度信息，避免因前一项长度变化引发连锁更新；但仍有内存搬移成本。

### intset

- **定义**：有序、无重复的整数数组，按成员范围选择统一的整数宽度。
- **解决问题**：小型纯整数 Set 无需为每个成员分配字符串和哈希节点。
- **性能代价**：二分查找 O(log N)，插入可能搬移 O(N) 个元素；更大整数可能触发整个数组宽度升级。
- **面试重点**：加入非整数或超过规模条件时需转换编码；Redis 7.2 还可能转为 listpack，不能笼统说“一定转哈希表”。

### 哈希表

- **定义**：根据哈希值定位桶；发生冲突时通过链式结构保存多个条目。
- **解决问题**：平均 O(1) 查找、插入、删除，用于 Hash、Set，也用于 ZSet 的成员索引。
- **渐进式 rehash**：扩缩容时暂存新旧两张表，分批迁移条目；迁移期间查询需兼顾两表，新增条目写入新表。
- **面试重点**：渐进迁移降低一次搬完的阻塞风险，不代表完全没有延迟；O(1) 是平均情况，严重冲突会降低性能。

### quicklist

- **定义**：用双向链表连接多个数据块，常规数据块内部使用 listpack；超大元素可单独存放。
- **解决问题**：块内紧凑存储省内存，块间链表支持扩展和两端操作。
- **性能代价**：块过大，块内搬移成本增加；块过小，指针和分配开销增加。
- **面试重点**：List 不是简单的“一个元素一个链表节点”；Redis 7.2 小 List 还可直接采用单个 listpack。

### 跳表

- **定义**：底层有序链表上增加多层稀疏索引，查找时先跨大步，再逐层缩小范围。
- **解决问题**：查找、插入、删除平均 O(log N)；定位范围起点后顺序遍历，适合排行榜和范围查询。
- **排名原理**：Redis 跳表索引记录跨越的元素数（span），沿查找路径累加可计算排名。
- **面试重点**：平衡树也能实现类似复杂度；跳表在实现复杂度、范围遍历和维护成本上较合适，并非性能永远优于平衡树。

### 基数树

- **定义**：按键的组成部分逐层索引，并压缩公共前缀，Redis 实现称为 rax。
- **解决问题**：Stream 将消息 ID 编码为有序键，定位对应 listpack，再遍历块内消息。
- **面试重点**：树负责索引，listpack 负责紧凑存储；这种组合兼顾有序访问与内存效率。
