# Redis 分布式锁

Redis分布式锁可以分为三部分来说：

1.加锁
2.解锁
3.续期

## 加锁

- **定义**：多个服务实例竞争同一个锁 Key，拿到锁后才能操作对应资源。
- **实现方式**：用SET NX EX完成“抢锁 + 设置过期时间”。
- **关键参数**：
  - **`NX`**：座位空着才能坐；已有锁时加锁失败。
  - **`EX 30`**：成功坐下后，锁最多保留 30 秒，到期自动释放。
- **需要注意：**：

不能拆成 `SETNX` 和 `EXPIRE`，否则两条命令之间宕机会留下无过期时间的锁；（要用一条命令 保证“加锁”和“设置过期时间”一起成功。）

抢锁失败应限时退避重试（让等待时间越来越长，直到超时），避免无限自旋。

## 解锁

- **定义**：只允许持有者释放自己的锁，校验和删除必须原子执行。
- **实现方式**：Lua 脚本比较 锁的值 ，匹配才删除。（校验锁持有者和删除锁必须作为一个不可分割的原子操作完成。）
- **危险场景**：A 的锁过期 → B 获得同名锁 → A 执行 `DEL`，误删 B 的锁。（用lua脚本执行原子性操作可以避免）

## 续期

- **定义**：业务执行时间可能超过租期，由看门狗定期延长锁的有效期。
- **实现方式**：客户端或锁框架启动后台任务；业务仍在执行时，用 Lua 原子完成“校验持有者 + 重设 TTL”。（不是Redis 主动为业务续期。）
- **计时示例**：租期 30 秒，每 10 秒续期一次；剩余 20 秒时续期，TTL 重新变为 30 秒，不是累加到 50 秒。
- **生命周期x**：持锁期间定期续期，业务结束后停止续期并解锁；实例宕机后续期停止，锁最终过期。
- **面试重点x**：
  - **为什么校验归属**：A 的锁可能已过期并被 B 获取；直接执行 `EXPIRE` 会给 B 的锁续期。校验和续期必须原子执行。
  - **为什么提前续期**：续期间隔应小于租期，为调度延迟、网络抖动留出余量；不能等到即将过期才续期。
  - **GC 为什么影响续期**：某些 GC 阶段会暂停业务线程和看门狗线程，但 Redis 的 TTL 继续倒计时；暂停过久，锁仍会过期。
  - **锁过期不等于业务停止**：A 暂停 → 锁过期 → B 获锁 → A 恢复，A、B 可能同时执行；锁过期不会中断 A，也不会撤销已提交的数据。
  - **续期失败怎么办**：锁不存在或归属不匹配，说明已失去锁；网络超时则结果不确定。不能继续假定独占资源，应尝试停止后续业务，并由下游校验写入资格。
  - **能否通过续期重新获锁**：不能。归属校验失败后不可直接重建锁；如需重试，应重新竞争锁，并读取、校验最新业务状态。
  - **先检查锁再写库是否安全**：不安全。检查时锁有效，写库前仍可能过期；两步不原子，仍需版本号、条件更新或隔离令牌兜底。

## 风险与兜底x

- **核心风险**：锁的有效期与业务执行并不绑定，拿到锁不代表整个业务期间始终独占资源。
- **失效场景**：
  - **租期失效**：A 执行超时，锁过期后 B 拿锁，A、B 同时操作业务。
  - **主从切换**：加锁成功但尚未复制，主节点宕机；新主节点没有锁，B 可再次加锁。
  - **网络故障**：请求超时不代表加锁失败；持有者断网后也可能继续执行，而锁已过期并被他人获取。
- **兜底方案**：
  - **幂等与唯一约束**：按业务唯一标识去重，防止同一请求重复产生结果。
  - **条件更新**：用状态或版本号限制写入，如 `UPDATE ... WHERE version = old_version`，检查受影响行数判断是否成功。
  - **隔离令牌（fencing token）**：每次获锁分配严格递增的令牌，下游原子拒绝小于已接受令牌的写入，防止旧持有者覆盖新持有者的结果。
- **面试重点**：
  - **唯一锁值与隔离令牌**：唯一锁值判断“锁是不是我的”；隔离令牌标记获锁先后，必须可靠生成且由下游原子校验。
  - **版本号与隔离令牌**：数据版本号随更新变化，提交时要求旧版本与当前版本相等；隔离令牌随获锁变化，下游接受新令牌后拒绝旧令牌。B 仅拿到新令牌时，A 的旧令牌未必立即被拒绝。
  - **写入被拒绝是否代表数据丢失**：拒绝的是本次过时结果，不会撤销之前已提交的数据；若 A 只是暂停，内存中的计算结果也不一定丢失，但不能盲目提交。
  - **被拒绝后如何处理**：可重新读取、校验并计算后有限重试；需要用户决策时返回冲突；同一请求已完成时，通过幂等记录返回已有结果，不能直接重放扣款等副作用。
  - **重试示例**：余额 100，A 想扣 10，算出 90 后暂停；B 扣 20 后余额变为 80。A 的旧写入 90 被拒绝，应确认本次扣款尚未执行且余额足够，再基于 80 计算并尝试写入 70。
  - **正确性边界**：锁减少并发冲突，业务正确性仍需存储层约束与并发控制。
