# 项目实战：RAG 中的 Redis

## 面试官：你的项目使用过 Redis 吗？

> 用过。在我的企业知识库 RAG 项目中，Redis 主要承担三个职责：租户级限流、同一会话的分布式锁，以及过期状态清理任务的互斥。
>
> 多个服务实例共享 Redis 令牌桶，控制每个租户的请求速率；同一会话执行前，通过 `SET NX PX` 获取锁，后台续租，结束后用 Lua 校验持有者并释放，减少并发修改对话上下文的冲突。清理任务也复用这套锁，避免多个任务同时执行。
>
> 实例内部另外使用信号量控制并发；会话历史和工作流 checkpoint 等持久状态由 PostgreSQL 保存。Redis 协调失败时返回错误，不回退成本地锁。

## 三个用途

- **[租户限流](#租户限流)**：控制同一租户跨实例的请求速率，避免资源被单个租户占满。
- **[会话锁](#会话锁)**：协调同一租户、同一会话的执行顺序，保护上下文更新。
- **[清理任务互斥](#清理任务互斥)**：过期状态清理前先抢锁，拿到锁的任务才执行。（不说）

### 租户限流

- **为什么用 Redis**：请求可能落到不同实例；各自在内存计数，会把同一租户的额度放大。Redis 保存共享配额。
- **数据结构**：Hash，Key 为 `rag:quota:<租户ID哈希>`，字段为 `tokens`、`updated_at`。
- **执行流程**：请求到达 → 按经过时间补充令牌 → 判断是否足够 → 扣一个 → 放行；补充和扣减由 Lua 原子完成。
- **时间来源**：使用 Redis `TIME`，避免各实例时钟不一致影响补充计算；不需要后台每秒补令牌。
- **配置示例**：桶容量 20，每分钟补充 60 个，即每秒补充 1 个、最多攒到 20 个；允许突发，不是“每分钟固定窗口最多 60 次”。
- **超限处理**：没有令牌则返回 `429 TENANT_QUOTA_EXCEEDED`，不进入工作流。
- **TTL 用途**：回收不活跃租户的配额记录；当前参数下每次访问重设为 40 秒，不是令牌的业务有效期。
- **面试重点**：这里的 token 是“请求许可”，不是大模型 token；一次请求扣一个，处理结束不归还，按时间补充。

### 会话锁

- **业务场景**：同一会话的两个请求分别落到实例 A、B；若同时读取旧历史并追加回答，可能产生上下文冲突。
- **锁粒度**：`tenant_id + conversation_id`；同一会话竞争同一把锁，不同会话可以并行。
- **数据结构**：String，Key 为 `rag:conversation-lock:<会话标识哈希>`，Value 为每次获取锁生成的 UUID。
- **加锁方式**：`SET key uuid NX PX 45000`；不存在才写入，设置 45 秒租期。
- **续租方式**：后台线程约每 15 秒执行 Lua；锁值仍是自己的 UUID，才重设 45 秒 TTL。
- **释放方式**：结束时执行 Lua，原子完成“校验 UUID + 删除”，防止误删别人重新获得的锁。
- **竞争失败**：短暂重试，获取锁的等待预算约 0.25 秒；未成功则返回 `409 CONVERSATION_BUSY`。
- **面试重点**：这是带租期的互斥协调；续租可能失败，不能承诺业务全过程绝对独占。原理详见[分布式锁](<6. 分布式锁.md>)。

### 清理任务互斥

- **业务场景**：多个调度任务可能同时清理过期会话和相关 checkpoint。
- **实现方式**：复用会话锁组件，传入固定标识 `__rag_expired_state_maintenance__`；获取锁后调用 `prune_expired`。
- **职责区分**：Redis 决定谁来清理；应用执行 PostgreSQL 状态清理，不是 Redis 自动删除数据库记录。

## 面试追问

### Redis 限流和实例限流有什么区别？

- **Redis 令牌桶**：同一租户跨实例共享配额，控制进入系统的请求速率。
- **实例信号量**：使用 `threading.BoundedSemaphore`，控制本进程同时处理的请求数；结束后归还名额。
- **配置示例**：部署模板为 3 个 API Pod、每 Pod 12 个名额，合计最多约 36 个受保护的 API 请求同时处理。
- **关键区别**：令牌桶控制“进来多快”，信号量控制“同时处理多少”；12 是工作流并发名额，不是数据库连接数。

### 请求经过哪些步骤？

- **主链路**：租户令牌桶 → 本实例并发名额 → 会话锁 → RAG 工作流 → 保存结果 → 释放锁和并发名额。
- **开启自动恢复时**：还会在 PostgreSQL 中记录请求、领取请求租约，并在提交结果时校验当前所有权。
- **实际边界**：配额检查在前；后面即使因实例繁忙或会话竞争被拒绝，已经消耗的请求令牌也不会退回。

### Redis 故障怎么办？

- **处理方式**：协调调用失败，返回 `503 COORDINATION_UNAVAILABLE`，提示调用方稍后重试。
- **为什么不退回本地锁**：本地锁只能保护一个进程，无法阻止其他实例同时操作同一会话；故障时降级会破坏原有协调规则。
- **面试重点**：这里优先保住协调约束，暂时牺牲可用性；不能照搬“缓存故障就直接查数据库”的处理方式。

### 锁续租失败，旧请求会立即停止吗？

- **当前实现**：续租线程设置锁丢失标记，退出锁上下文时检查并报错；不会立即中断正在执行的工作流。
- **提交保护**：开启自动恢复时，PostgreSQL 在事务中检查请求状态和 `lease_token`，拒绝已被其他执行者接管的旧请求提交。
- **边界**：数据库校验的是“请求租约”，Redis 协调的是“会话锁”，两者作用范围不同；不能声称数据库校验自动解决了所有会话锁失效风险。

### 熔断也在 Redis 里吗？

- **当前实现**：熔断器保存在各实例内存中，针对检索、联网搜索、LLM 等依赖分别记录状态。
- **状态变化**：关闭时正常调用；达到失败阈值后打开；等待恢复时间后只放一个试探请求。
- **配置默认值**：失败阈值 3，恢复等待 30 秒；不是多个实例共享的 Redis 熔断状态。

### Redis 缓存了答案或向量吗？

- **按现有业务代码回答**：核心用途是协调，未实现 Redis 问答结果缓存、检索结果缓存或 embedding 缓存。
- **持久状态**：PostgreSQL 保存 checkpoint、请求账本、对话记录等；Redis 保存短期配额和锁状态。
- **开发模式**：默认 SQLite 后端使用本地锁与本地令牌桶；PostgreSQL 后端使用 Redis，生产配置要求 PostgreSQL + Redis。
