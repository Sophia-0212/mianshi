# 持久化：RDB 与 AOF

目的：将内存数据写入磁盘，重启后恢复；持久化不等于高可用，核心数据仍需数据库主存储。

## 持久化方式

RDB：某时刻的全量内存快照 → `dump.rdb`；文件小、恢复快，适合备份；两次快照之间的数据可能丢失。

AOF：按顺序记录写命令 → `appendonly.aof`；重启时重放命令；数据丢失窗口小，但文件较大、恢复较慢。

混合持久化：AOF 重写文件 = RDB 全量数据 + 增量 AOF 命令。RDB 用于备份，AOF 用于更完整恢复；重启时通常优先加载 AOF；

无持久化：关闭 RDB 和 AOF；适合纯缓存，重启后数据全部丢失。

## RDB 生成

自动：`save <秒数> <修改数>`：达到条件自动触发；

手动：
- `BGSAVE`：`fork` 子进程后台生成，主线程继续服务；
- `SAVE`：主线程同步生成，会阻塞请求，生产环境慎用。后台生成有 `fork` 延迟和写时复制（COW）内存开销。

判断标准：需要继续服务 → BGSAVE；允许全程阻塞 → SAVE。

## AOF 刷盘

写入路径：执行写命令 → Redis 的 AOF 缓冲区 → 操作系统页缓存 → 磁盘。

写入不等于落盘：调用 write 通常只是写进操作系统页缓存，仍在内存里；调用fsync 才要求把数据同步到磁盘。机器断电时，尚未落盘的日志可能丢失。

- `appendfsync always`：每次写都刷盘，最可靠、性能最低；
- `everysec`：每秒刷盘，常用，故障通常最多丢约 1 秒；
- `no`：由操作系统决定，性能高、风险最大。
