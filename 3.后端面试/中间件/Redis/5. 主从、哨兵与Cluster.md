# 主从、哨兵与 Cluster

## 一、先分清：


主从是复制；哨兵是故障转移；Cluster 是数据分片。

## 二、主从复制

定义：一个 Master 配合一个或多个 Replica；Master 主要处理写入，Replica 复制 Master 的数据并分担读请求。

作用：Replica 分担读流量，实现读扩展；保存数据副本，在故障时恢复；为哨兵或 Cluster 的故障转移提供基础。

限制：复制存在延迟；Replica 仍保存全量数据，不能扩展写入能力；主从复制不解决数据分片。

### 复制过程

需要分3个不同的场景：

首次连接或无法增量同步时：执行全量复制。- Master 生成 RDB，Replica 加载 RDB，再接收复制期间产生的增量命令。RDB 是紧凑的全量数据，适合快速传输；AOF 主要用于 Redis 重启时的本地持久化恢复。

短暂断线并成功重连时：Replica 携带自己的复制 ID 和 offset，执行部分复制。- 只要 Master 的复制积压缓冲区仍保留缺失命令，就执行部分复制，只补发缺失数据；缺失命令已被覆盖时，只能重新全量复制。

异步复制：Master 执行写命令后通常立即向客户端返回，不等待 Replica 确认。- 因此性能和延迟较好，但 Master 故障时可能丢失尚未复制的数据，Replica 也可能读到旧数据。

降低 异步复制 里 丢失风险：可用 `WAIT` 等待指定数量的 Replica 确认后再返回，但会增加延迟。

## 三、哨兵

### 1. 哨兵是什么？

哨兵（Sentinel）是监控与故障转移组件，不存储业务数据。它管理一组主从节点：Master 处理写请求，Replica 复制 Master，哨兵 监控节点并执行故障转移。
解决：Master 故障后需要人工判断、提升 Replica、修改客户端配置、处理慢且容易误判。
不解决：哨兵不负责数据分片、总容量扩展、写请求水平扩展、严格强一致和业务数据持久化；单个 Master 放不下全部数据或写入能力不足时，应使用 Cluster。

### 2. 哨兵解决问题：

自动监控：检查 Master、Replica 和其他 Sentinel。  
自动判断故障：通过主观下线和客观下线减少误判。  
自动故障转移：选择 Replica 提升为新 Master。  
重新配置复制：让其他 Replica 复制新 Master。  
通知客户端：提供新的 Master 地址。

### 3. 哨兵判断故障：

主观下线（SDOWN）：某个 Sentinel 在规定时间内联系不上 Master，只代表自己的判断。  
客观下线（ODOWN）：多个 Sentinel 投票并达到大多数，确认 Master 确实故障。

1. Sentinel 发现 Master 疑似故障；
2. 多个 Sentinel 达成客观下线判断；
3. Sentinel 之间选举负责本次故障转移的 Leader；
4. Leader 从 Replica 中选择合适节点；
5. 将该 Replica 提升为新 Master；
6. 让其他 Replica 改为复制新 Master；
7. 通知客户端更新 Master 地址。

通常部署奇数个，便于形成多数。

### 4. 扩容：

增加 Replica从：重点高可用，扩展读能力；每个 Replica 仍保存全量数据，不增加总容量和写能力。  
增加 Sentinel哨兵：重点高可用，提高故障判断可靠性；Sentinel 不存储业务数据，不增加容量和读写吞吐。  
增加 Cluster集群：重点高并发


## 四、为什么需要 Cluster

1. 为什么需要 Cluster？单个 Master 的内存和写入能力有限，增加 Replica 只能增加副本、分担读流量。Cluster 将数据分散到多个 Master，扩展总
容量和读写吞吐，同时提供自动故障转移。

2. 数据怎么分？Cluster 将数据划分到 16384 个哈希槽，每个 Master 负责一部分槽。Key 默认通过 CRC16(key) mod 16384 确定槽位，再由槽位确定节
点。分片分的是不同数据，副本复制的是同一份数据。

3. 请求怎么找到节点？客户端缓存“槽位与节点的对应关系”，计算 Key 的槽位后直接访问目标节点。映射过期时，节点返回 MOVED，客户端更新映射并重
试；迁移期间可能返回 ASK，客户端临时去目标节点执行本次请求。节点负责指路，客户端重新请求。

4. 节点故障怎么处理？每个 Master 可配置 Replica，复制这个分片的数据。Master 故障且满足选举条件时，对应 Replica 升主，接管原来的槽位。
Cluster 自带故障转移，无须哨兵；复制仍是异步，可能丢失最近写入。

5. 如何扩缩容？增加 Master 后，将部分槽位及数据迁给它，分担存储和请求；缩容先迁走数据，再移除节点。槽位总数不变，变化的是槽位归属。
例如原来由 A 负责的部分槽迁给 D，对应 Key 也随之迁移；仅增加节点不会自动分担负载。

6. 有什么限制？MGET、MSET、事务、Lua 等涉及多个 Key 时，需要满足同槽要求。可以用 Hash Tag，让 user:{1001}:name 和 user:{1001}:orders 都按
1001 计算槽位。同一 Key 不会拆到多个分片，单个热 Key 或大 Key 的瓶颈也不能靠增加 Master 直接解决。

## 七、三种架构对比

| 架构 | 解决问题 | 分片 | 自动故障转移 |
|---|---|---:|---:|
| 主从 | 复制、读扩展 | 否 | 否 |
| 哨兵 | 高可用、自动选主 | 否 | 是 |
| Cluster | 分片、水平扩展 | 是 | 是 |
