## 缓存生命周期 - Redis 内部机制

有 过期删除 和 内存淘汰 两种方式：

### 过期删除

- **定义**：清理已超过有效期的 Key。
- **实现方式**：
  - **惰性删除**：访问 Key 时检查，到期则删除并视为不存在。
  - **定期删除**：Redis 周期性抽样检查，清理已过期数据。
- **为什么两者配合**：只靠惰性删除，长期无人访问的过期数据会占用内存；定期清理补足这一点。

### 内存淘汰

- **定义**：内存使用 超过 `maxmemory` 限制时，根据策略尝试淘汰 Key；
- **候选范围**：`allkeys-*` 面向所有 Key；`volatile-*` 仅面向设置了过期时间的 Key。
- **常见策略**：
  - **`noeviction`**：不主动淘汰；超限时拒绝需要新增内存的写入，读取仍可继续。
  - **`allkeys-lru`**：在所有 Key 中优先淘汰最近较少使用的 Key。
  - **`allkeys-lfu`**：在所有 Key 中优先淘汰访问频率较低的 Key。
  - **`volatile-lru` / `volatile-lfu`**：仅在带过期时间的 Key 中按 LRU / LFU 选择。
  - **`volatile-ttl`**：在带过期时间的 Key 中优先淘汰剩余 TTL 较短者。
  - **`allkeys-random` / `volatile-random`**：分别在所有 Key / 带过期时间的 Key 中随机淘汰。

### 过期删除与内存淘汰的区别

| 对比项 | 过期删除 | 内存淘汰 |
|---|---|---|
| 触发条件 | Key 到期 | 内存压力超过限制 |
| 处理对象 | 已过期的 Key | 策略范围内的 Key，可能尚未过期 |
| 主要目的 | 清理失效数据 | 控制内存使用 |

## 缓存三大问题

### 缓存击穿

- **定义**：单个热点 Key 过期或失效，大量并发请求同时访问数据库。
- **影响**：数据库瞬时压力增大，可能引发超时。
- **解决方案**：
  - **互斥锁**：仅一个请求重建缓存；
  - **逻辑过期**：保留旧值，用时间字段判断过期；先返回旧值，再由一个任务后台刷新。
  - **延长 TTL**：降低过期频率；只能缓解，不能消除击穿。

### 缓存雪崩

- **定义**：大量 Key 同时失效，或 Redis 整体不可用，导致请求集中访问数据库。
- **影响**：数据库过载，故障可能扩散到上游服务。
- **解决方案**：
  - **过期时间打散**：TTL 加随机值，避免批量缓存同时过期。
  - **多级缓存**：本地缓存承接部分热点请求，减少对 Redis 的依赖。
  - **限流、熔断、降级**：限制回源并发，必要时返回兜底结果，保护数据库。
  - **高可用部署**：主从复制配合哨兵或 Redis Cluster，降低单点故障影响；详见[主从、哨兵与 Cluster](<5. 主从、哨兵与Cluster.md>)。

### 缓存穿透

- **定义**：查询不存在的数据，缓存和数据库都没有，请求反复访问数据库。
- **影响**：无效请求占用数据库资源，可能拖慢正常查询。
- **解决方案**：
  - **参数校验**：拦截格式、范围不合法的请求；无法识别合法但不存在的 ID。
  - **缓存空值**：不存在也写入缓存，设置较短 TTL；新数据写入后需清理对应空值缓存。
  - **布隆过滤器**：查询前判断数据是否可能存在；判定不存在则拦截，可能存在则继续查。
- **需要注意**：布隆过滤器可能把不存在的数据判为“可能存在”，不能完全阻止穿透；新数据需及时加入过滤器，避免被误拦截。



## 性能优化

从 **6 个点**展开：**定位瓶颈 → 减少通信 → 避免阻塞 → 优化数据 → 控制流量 → 扩展容量**。

```text
Redis 高并发与性能优化
│
├─ 1. 定位瓶颈：先确定慢在哪里
│  ├─ 业务侧：QPS、P99 延迟、缓存命中率
│  ├─ Redis 侧：CPU、内存、带宽、连接数、慢日志
│  └─ 区分：网络慢、命令慢，还是热点导致单节点过载
│
├─ 2. 减少通信：降低网络与连接开销
│  ├─ 连接复用：连接池或客户端多路复用，避免频繁建连
│  ├─ 批量请求：MGET、Pipeline，减少网络往返
│  └─ Lua：合并“判断＋更新”，例如校验库存后扣减
│     注意：Pipeline 不保证原子性；Lua 原子执行，但长脚本会阻塞
│
├─ 3. 避免阻塞：控制单次执行时间
│  ├─ KEYS → SCAN，分批遍历
│  ├─ HGETALL、SMEMBERS、大范围 LRANGE → 分批读取
│  └─ 删除大 Key：优先 UNLINK，后台回收内存
│
├─ 4. 优化数据：减少内存、传输和处理成本
│  ├─ 控制 Value 大小：只缓存必要字段
│  ├─ 拆分大 Key：限制单 Key 的体积和元素数量
│  └─ 设置合理 TTL、内存上限与淘汰策略，避免内存耗尽
│
├─ 5. 控制流量：减少无效请求与突发冲击
│  ├─ 热 Key：本地缓存、请求合并，降低重复访问
│  ├─ 缓存失效：TTL 加随机偏移；热点重建加互斥，保护数据库
│  └─ 过载保护：限流、超时、有限重试，防止请求堆积
│
└─ 6. 扩展容量：分散节点负载
   ├─ 读多：读副本分担读压力，但需接受复制延迟
   ├─ 数据量或总吞吐超限：Cluster 分片
   └─ 单个热 Key：不会自动分散到多个分片，仍需缓存或业务拆分
```

### 热 Key

- **定义**：单个 Key 访问量过高，请求集中到少数节点。
- **影响**：节点 CPU 或网络带宽成为瓶颈，拖慢同节点其他请求。
- **解决方案**：
  - **热点监控**：通过业务埋点识别热点和它的请求量。（发现问题）
  - **本地缓存**：热点读请求在应用内完成；需控制容量、过期与更新一致性。
  - **读流量分散**：使用读副本，或将热点数据复制为多个 Key 并分散到不同分片；需处理复制延迟或多副本更新。
  - **限流**：限制热点请求，保护节点。

### 大 Key

- **定义**：单个 Value 字节数过大，或集合元素过多。
- **影响**：占用内存和带宽；全量读写、遍历或同步删除可能阻塞其他请求，还会加剧内存压力。
- **解决方案**：
  - **拆分 Key**：按业务维度分桶，限制单个 Value 大小及集合元素数量。
  - **分批处理**：分页读取、增量遍历，避免一次获取或处理整个集合。
  - **异步删除**：使用 `UNLINK` 将内存回收交给后台线程，降低删除阻塞。
- **面试重点**：大 Key 是“体积大”，热 Key 是“访问频繁”；`UNLINK` 只缓解删除成本，不解决读写开销，也不代表调用后内存立即全部释放。

### 缓存一致性

- **定义**：数据库与缓存保存同一份业务数据，更新和并发访问可能导致两者不一致。
- **影响**：读到旧值，影响展示或业务判断。
- **解决方案**：
  - **旁路缓存**：读时先查缓存，未命中再查数据库并回填；写时先提交数据库事务，再删除缓存。
  - **失败补偿**：删除失败后重试；通过可靠消息或订阅数据库变更日志补偿，避免进程崩溃导致任务丢失。
  - **TTL 兜底**：限制某次脏缓存写入后的存活时间；配合校验和修复机制，不能只靠淘汰策略碰运气。
- **需要注意**：
  - **为什么删除而非更新**：并发写入时，直接更新缓存可能因执行顺序交错而被旧值覆盖。
  - **仍有竞争窗口**：读请求未命中并读到旧值 → 写请求提交并删除缓存 → 读请求回填旧值。
  - **延迟双删的边界**：延后再删一次可降低旧值回填风险；延迟难以精确确定，不能替代可靠重试或保证强一致性。
  - **一致性取舍**：上述策略通常实现最终一致；强一致读应访问数据库权威数据，并配合满足要求的事务隔离或并发控制。
