## 第 2 阶段：数据类型与底层实现，5 天

- **对应文档**：[2. 数据类型与底层实现](<2. 数据类型与底层实现.md>)。
- **学习顺序**：String → Hash → List → Set → ZSet → Bitmap → Stream；每学一种类型，就衔接其底层编码。
- **每种类型回答**：存什么、怎么操作、用于什么业务、底层怎么实现、性能与代价是什么。
- **底层主线**：SDS → listpack → intset → 哈希表 → quicklist → 跳表 → 基数树。
- **核心直觉**：同一种逻辑类型可有不同编码；小数据节省内存，数据增大后兼顾访问效率。

### 类型与场景

| 类型或功能 | 典型场景 |
|---|---|
| String | 缓存、计数器、分布式锁 |
| Hash | 用户信息、商品信息 |
| List | 简单队列、消息列表 |
| Set | 标签、共同关注、去重 |
| ZSet | 排行榜、延迟队列 |
| Bitmap | 签到、活跃统计 |
| Stream | 消息流、消费组 |

### 必须能回答

- String 与 SDS 有什么区别？SDS 比 C 字符串好在哪里？
- 为什么同一个 Hash 会从 listpack 转为哈希表？
- List 为什么使用 listpack / quicklist，而不是简单链表？
- ZSet 为什么需要哈希表与跳表配合？为什么选择跳表？
- listpack 什么时候会导致性能问题？
- Bitmap 与 String 是什么关系？
- Stream 如何追踪未确认消息？为什么仍需幂等？

### 实践

- 实现访问量计数器、用户签到、商品排行榜、简单消息队列。
- 用 `TYPE`、`OBJECT ENCODING`、`MEMORY USAGE` 观察类型、编码和内存。
- 改变测试数据规模，观察编码转换，解释内存与访问效率的取舍。

## 第 3 阶段：持久化，2 天

### RDB

定期生成某一时刻的内存快照：

```text
内存数据 → RDB 文件
```

优点：文件紧凑、恢复快。  
缺点：两次快照之间的数据可能丢失。

### AOF

记录写命令：

```text
SET k v → AOF 文件
```

优点：数据更完整。  
缺点：文件更大，恢复更慢。

### 混合持久化

使用 RDB 保存快照，再用 AOF 保存增量命令，兼顾恢复速度和数据完整性。

### 必须能回答

- RDB 和 AOF 如何选择？
- Redis 宕机最多可能丢多少数据？
- AOF 重写解决什么问题？
- `fsync always`、`everysec`、`no` 有什么区别？

### 实践

- 配置 RDB 和 AOF
- 模拟宕机恢复
- 对比恢复速度和数据丢失量

## 第 4 阶段：缓存生命周期与常见问题，4 天

- **对应文档**：[4. 缓存生命周期与常见问题](<4. 缓存生命周期与常见问题.md>)。
- **学习主线**：TTL 与清理 → 内存淘汰 → 缓存未命中与回源 → 击穿、雪崩及其他缓存问题。
- **内部机制**：惰性删除、定期删除、`maxmemory`、`noeviction`、LRU / LFU、`allkeys-*` 与 `volatile-*`。
- **关键区分**：过期删除清理到期数据；内存淘汰可能删除未到期数据；TTL 不承诺内存立即释放，也不承诺缓存一直保留。

### 业务问题与应对

- **击穿**：单个热点失效；用互斥重建、逻辑过期保护回源，不能只依赖长 TTL。
- **雪崩**：大量缓存失效或 Redis 不可用；打散 TTL、多级缓存、限流熔断降级，并结合高可用部署。
- **穿透**：查询不存在的数据；参数校验、布隆过滤器、缓存空值。
- **热 Key**：请求集中；本地缓存、读流量分散、限流与热点监控。
- **大 Key**：数据体积过大；限制大小、拆分、分批处理、`UNLINK`。
- **一致性**：先提交数据库再删除缓存，配合可靠重试、TTL 兜底与修复；并发回填旧值仍需考虑。

### 必须能回答

- 到期但尚未清理的 Key，能否正常读到旧值？
- 没有设置 TTL 的 Key，会不会被淘汰？
- `noeviction` 与 `volatile-*` 下没有候选 Key，各会怎样？
- 为什么热点 Key 没到过期时间也可能击穿？
- TTL 随机化为什么不能解决所有雪崩？
- 为什么先更新数据库再删除缓存仍可能读到旧值？

### 实践

- 设置 TTL 和 `maxmemory`，对比过期与淘汰，观察命中率和回源量。
- 对比 LRU / LFU；模拟热点失效与大量失效，验证回源保护。
- 模拟穿透、缓存删除失败和旧值回填，验证补偿与兜底。
- 监控热 Key、大 Key，验证拆分、限流与异步删除。

## 第 5 阶段：主从、哨兵、集群，3 天

### 主从复制

```text
Master
  ↓ 复制
Replica
```

解决读扩展和数据备份问题，但主节点故障时不会自动完成高可用切换。

### 哨兵

负责：

- 监控节点
- 判断主节点故障
- 自动选举新主节点
- 通知客户端

### Cluster

通过哈希槽分片：

```text
16384 个槽位 → 多个主节点
```

同一个 Key 根据哈希槽定位到对应节点。

### 必须能回答

- 主从复制是同步还是异步？
- 哨兵和 Cluster 有什么区别？
- Redis Cluster 为什么是 16384 个槽？
- 跨槽操作为什么失败？
- 如何保证故障转移期间业务可用？

### 实践

- 搭建主从集群
- 模拟主节点宕机
- 观察哨兵故障转移
- 测试 Cluster 的分片和跨槽限制

## 第 6 阶段：分布式锁，2 天

### 基础实现

```redis
SET lock:order:1001 request-id NX EX 30
```

含义：

- `NX`：只有 Key 不存在时才能加锁。
- `EX 30`：30 秒后自动释放。
- `request-id`：标识锁的持有者。

### 解锁必须校验持有者

不能直接：

```redis
DEL lock:order:1001
```

否则锁过期后，旧请求可能删除新请求持有的锁。

应使用 Lua 保证判断和删除原子化：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

### 必须解决

- 锁误删
- 锁过期
- 业务执行时间超过租期
- 服务宕机
- 主从切换导致锁丢失
- 多节点加锁一致性

### 实践

- 实现订单防重复提交
- 实现库存扣减锁
- 模拟持锁服务宕机
- 模拟锁过期和续期

## 第 7 阶段：高并发与性能优化，3 天

### 学习内容

- Pipeline
- 批量命令
- Lua 脚本
- 连接池
- 慢查询
- 大 Key 检测
- 热 Key 检测
- 网络与序列化开销
- 读写分离
- 本地缓存 + Redis 二级缓存

### 关键原则

```text
减少网络往返
减少单次数据量
避免阻塞命令
控制 Key 和 Value 大小
```

### 高风险命令

- `KEYS *`
- `SMEMBERS` 超大集合
- `LRANGE` 大范围读取
- `HGETALL` 超大 Hash
- `DEL` 删除大 Key

可考虑：

- `SCAN`
- `SSCAN`
- `HSCAN`
- `ZSCAN`
- `UNLINK`

### 实践

- 用 Pipeline 对比逐条命令耗时
- 用 Lua 实现库存扣减
- 使用慢查询日志定位问题
- 测量不同 Value 大小的性能

## 第 8 阶段：综合项目，5～7 天

实现一个商品与秒杀系统：

```text
请求
  ↓
本地缓存
  ↓ 未命中
Redis 商品缓存
  ↓ 未命中
MySQL
  ↓
回写 Redis
```

秒杀链路：

```text
用户请求
  ↓
限流
  ↓
Redis 原子扣库存
  ↓
生成订单消息
  ↓
MQ 异步创建订单
  ↓
MySQL 持久化
```

必须加入：

- 缓存穿透防护
- 热点 Key 防护
- 分布式锁或 Lua
- 库存超卖防护
- 消费幂等
- 缓存更新策略
- Redis 宕机降级
- 监控与告警
