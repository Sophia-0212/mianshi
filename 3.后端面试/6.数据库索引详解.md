### **1. 索引的本质与作用**

- **定义**：
索引是数据库中**加速数据检索的辅助数据结构**，类似于书籍的目录。

- **核心作用**：

  - 减少全表扫描，**提升查询效率**（时间复杂度从 O(n) 降到 O(log n)）。

  - 通过唯一索引**保证数据唯一性**。

  - 加速表连接（JOIN）和排序（ORDER BY）操作。

  [表连接（JOIN）](https://flowus.cn/bb646ebb-40e0-4153-8d07-0099be3a2fce)

  [排序（ORDER BY）](https://flowus.cn/ed1fe8d3-4ab3-4b38-abb4-ef2b165111d4)

### **2. 索引的底层数据结构**

#### **(1) B+树（主流选择）**

- **适用场景**：范围查询（`WHERE age > 20`）、排序、前缀匹配（`LIKE 'abc%'`）。

- **优势**：

  - 多叉树结构减少磁盘 I/O（节点存储多个键值）。

  [为什么多叉树结构减少磁盘 I/O？](https://flowus.cn/0c717896-ed27-4d64-b34c-09c0f647f30b)

  - 叶子节点形成有序链表，适合范围查询。

- **示例**：MySQL InnoDB 的聚簇索引和非聚簇索引均基于 B+树。

#### **(2) 哈希索引**

- **适用场景**：等值查询（`WHERE id = 123`）。

- **劣势**：

  - 不支持范围查询和排序。

  - 哈希冲突影响性能。

- **示例**：MySQL Memory 引擎、Redis Hash。

#### **(3) 全文索引**

- **适用场景**：文本内容的模糊搜索（`MATCH(content) AGAINST('keyword')`）。

- **实现方式**：倒排索引（Inverted Index）。

- **示例**：Elasticsearch、MySQL 的全文索引（FULLTEXT）。

#### **(4) 其他结构**

- **R-Tree**：空间索引（如地理位置查询）。

- **LSM-Tree**：写入密集型场景（如 LevelDB、HBase）。

---

### **3. 索引类型（以 MySQL 为例）**

|类型|特点|示例|
|-|-|-|
|**主键索引**|唯一且非空，表数据按主键顺序存储（聚簇索引）|`PRIMARY KEY (id)`|
|**唯一索引**|确保列值唯一，允许 NULL|`UNIQUE KEY (email)`|
|**普通索引**|加速查询，无唯一性约束|`INDEX (name)`|
|**联合索引**|多列组合索引，遵循最左前缀原则|`INDEX (age, city)`|
|**覆盖索引**|索引包含查询所需的所有字段，无需回表|`SELECT id FROM table WHERE age=25`（若索引为 (age, id)）|

---

### **4. 索引的优缺点**

|**优点**|**缺点**|
|-|-|
|加速查询、排序、分组|占用额外存储空间|
|加速表连接（JOIN）|增删改操作需维护索引，降低写性能|
|唯一性约束|不合理的索引设计可能导致查询优化器选错索引|

---

### **5. 索引的设计原则**

1. **高频查询字段优先**：WHERE、JOIN、ORDER BY 的列。

2. **区分度高**：索引列的基数（Cardinality）越高越好（如用户 ID 比性别更适合）。

3. **最左前缀原则**：联合索引中，优先使用区分度高的列作为左前缀。

4. **避免冗余索引**：如已有 (a, b) 索引，单独为 (a) 建索引是冗余的。

5. **小字段优先**：减少索引存储空间，提升内存利用率。

---

### **6. 索引失效的常见场景**

6. **违反最左前缀原则**：联合索引 (a, b)，查询条件仅使用 `b`。

7. **对索引列运算或函数**：`WHERE YEAR(create_time) = 2023`。

8. **隐式类型转换**：`WHERE id = '100'`（id 为整型）。

9. **模糊查询前缀通配符**：`LIKE '%abc'`。

10. **OR 条件未全覆盖**：`WHERE a=1 OR b=2`（若仅 a 有索引）。

11. **数据量过少**：优化器认为全表扫描更快。

---

### **7. 聚簇索引 vs. 非聚簇索引**

- **聚簇索引**：索引与数据共存，如 InnoDB 的主键索引，一张表只能有一个。

- **非聚簇索引**：索引与数据分离（如 MyISAM），叶子节点存储数据地址。

### **8.索引下推（Index Condition Pushdown, ICP）**

- **原理**：在存储引擎层提前过滤索引中的条件，减少回表次数。

- **示例**：联合索引 (age, city)，查询 `WHERE age>20 AND city='北京'`，ICP 会在索引层过滤 `city`。

**传统查询流程（无 ICP）**

对于查询语句 `WHERE age>20 AND city='北京'`，如果没有使用索引下推技术，查询过程如下：

12. **索引扫描**：数据库会先通过联合索引 `(age, city)` 扫描所有 `age > 20` 的索引记录，获取这些记录对应的主键值。在这个过程中，只关注 `age` 列的值是否满足条件，不会对 `city` 列的值进行判断。

13. **回表查询**：根据获取的主键值，回表查询完整的数据行。

14. **过滤操作**：对回表获取的完整数据行应用 `city = '北京'` 这个条件进行过滤，返回满足条件的记录。

**使用 ICP 在索引层过滤 `city` 的流程**

当使用索引下推技术时，查询过程会有所不同：

15. **索引扫描与过滤**：数据库在扫描联合索引 `(age, city)` 时，同时对 `age > 20` 和 `city = '北京'` 这两个条件进行判断。也就是说，在遍历索引记录的过程中，不仅检查 `age` 列的值是否大于 20，还会检查 `city` 列的值是否为 ' 北京 '。只有同时满足这两个条件的索引记录，才会将其对应的主键值保留下来。

16. **回表查询**：只对那些在索引层已经满足 `age > 20` 且 `city = '北京'` 条件的索引记录对应的主键值进行回表查询，获取完整的数据行。



### **9.自适应哈希索引（Adaptive Hash Index）**

- **场景**：InnoDB 自动为频繁访问的索引页构建哈希索引，加速等值查询。

### **10. 执行计划分析**

在 MySQL 中，可以在 `SELECT`、`INSERT`、`UPDATE`、`DELETE` 等查询语句前加上 `EXPLAIN` 关键字来查看该语句的执行计划。例如：

```SQL
EXPLAIN SELECT * FROM employees WHERE age > 20 AND city = '北京';
```


执行上述语句后，MySQL 会返回一个结果集，展示该查询语句的执行计划信息。



#### 1. `type`（访问类型）

- **高效类型（`system`、`const`、`eq_ref`）**

  - `system` 是最理想但极少见的情况，表中仅存在一行记录，数据库能瞬间定位数据，几乎无查找开销。

  - `const` 用于主键或唯一索引的等值查询，数据库将其视为常量处理，通过索引一次即可定位目标记录，效率极高。

  - `eq_ref` 常用于多表连接，借助主键或唯一索引，为驱动表的每行记录在被驱动表中精准匹配一行，避免全表扫描，效率较高。

- **中等效率类型（`ref`、`range`）**

  - `ref` 使用非唯一索引进行等值查询，可能返回多行记录。虽比使用唯一索引稍慢，但仍利用索引快速定位部分数据，效率中等。

  - `range` 在指定范围检索行，利用索引定位范围记录。范围较小时效率不错，范围扩大则扫描索引记录增多，效率有所下降。

- **低效率类型（`index`、`ALL`）**

  - `index` 需扫描整个索引树，即便无需回表（查询字段都在索引中），遍历大量索引记录仍会消耗较多时间和资源，效率较低。

  - `ALL` 是全表扫描，不使用索引，逐行遍历整个表查找匹配记录，在大表中会产生大量磁盘 I/O 操作，效率最差。

这里 `type` 可能是 `ALL`。

#### 2. `key`（使用的索引）

如果 `name` 列上有索引，`key` 字段会显示该索引的名称；如果没有索引，`key` 字段将为 `NULL`。



#### 3. `Extra`（额外信息）

`Extra` 字段包含了一些关于查询执行的额外信息，其中是否覆盖索引是一个重要的关注点：

- **`Using index`**：表示使用了覆盖索引。覆盖索引是指查询所需的数据可以直接从索引中获取，而不需要回表查询完整的数据行。例如：

```SQL
EXPLAIN SELECT age, city FROM employees WHERE age > 20 AND city = '北京';
```

如果 `(age, city)` 是联合索引，且查询只需要 `age` 和 `city` 列的数据，那么可能会出现 `Using index`，说明使用了覆盖索引，查询效率较高。

- **`Using where`**：表示 MySQL 需要在存储引擎返回的结果集上使用 `WHERE` 子句进行过滤。这可能意味着索引没有完全覆盖查询条件，需要进一步优化索引。

- **`Using temporary`**：表示 MySQL 需要使用临时表来处理查询，通常出现在需要对结果集进行排序或分组的查询中。使用临时表会增加额外的开销，可能需要优化查询或添加合适的索引。

- **`Using filesort`**：表示 MySQL 需要对结果集进行文件排序，这也是一个比较耗时的操作。可以通过添加合适的索引来避免文件排序。
